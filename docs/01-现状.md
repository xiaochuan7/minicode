## 0. 一句话结论

在本机（Windows 11 / 2560×1600 / 150% DPI）上，`opencode.ai` 的 zen 通道 + `minimax-m3.1-flash-free`
的「纯文本调用 → 图像 grounding → 真实桌面两级定位」链路**已跑通**；坐标量纲实测为 **0~1000 归一化**。
**没测的是四类边界**（小图标 / UWP 纯视觉 / 同名歧义 / 中文输入，见 §4），开工前不要当它们已经成立。

## 2. 三个坑（本机踩过并确认）

### 坑 1 · 缺 `user-agent` / `x-opencode-client` → Cloudflare 1010

这两个头**必须同时带**：

```
user-agent: opencode/1.0.0
x-opencode-client: cli
```

缺任一个，请求会被 Cloudflare 拦掉，返回 **HTTP 1010**（不是模型侧的错误）。
三个 verify 脚本的 `HEADERS` 里都写死了这两个头——**接入时不要"精简"掉**。

> 🔴 **2026-10-20 复测（M1 集成回归，`python -m minicode.model.regressions`）——上面这句话要按实测改读**：
>
> | 少了哪个头 | 实测结果 |
> |---|---|
> | `user-agent` | **HTTP 403**，响应体是 Cloudflare 的 `Error 1010`（**"1010" 是错误编号，不是状态码**）；仍是边缘拦截，不是模型侧错误体 |
> | `x-opencode-client`（保留 `user-agent`） | **HTTP 200，正常出文本 —— 没有被拦截** |
> | 两个都在 | HTTP 200，正常出文本 |
>
> - 「两个头都必须」这个说法**从未被单独测过**：`verify/test_00_endpoint_matrix.py` 的四组 UA 里，
>   带 `opencode/1.0.0` 的那一组**两个头一直一起带**，没有「只留 user-agent」这一组。
> - 实测结论：**当前只有 `user-agent` 被强制**；`x-opencode-client` 服务端照收不误。
>   客户端仍然**两个头都发**（不精简）——但理由从「必需」降级成「照旧带上，换网关时别丢」。
> - 工单 M1 的 AC「两次调用都必须返回 HTTP 1010」与实测不符，已在 `docs/reviews/M1.md` 记为偏差。

### 坑 2 · free 模型只能走 `/zen/go`，走 `/zen` 会 `FreeTierError`

`minimax-m3.1-flash-free` 在 `https://opencode.ai/zen`（不带 `/go`）上返回 **`FreeTierError`**；
只有 `https://opencode.ai/zen/go` 这条路可用。

### 坑 3 · thinking 关不掉，只能用 `output_config.effort=low` 降延迟

- 发 `{"thinking": {"type":"disabled"}}` → **HTTP 400**，`invalid_request_error`（上游报错）。
  实测响应体：`{"type":"error","error":{"type":"invalid_request_error","message":"Upstream request failed...`（2026-10-20 复跑）。
- 因此**唯一可用的降延迟手段是** `output_config: {"effort": "low"}`。
  首轮实测（2026-10-19/20）：**10.6s → 5.9s**。
- `reasoning_effort: "low"`（另一种写法）**无效**：本次复跑 21.38s，反而是最慢的一档，且行为与默认一致 → 该参数被忽略。
- 🔴 **本次复跑新增的一条实测**：**默认 effort（=max）在 `max_tokens=1200` 时思考链会把预算吃光，结果没有 JSON 输出**——
  三个"默认"档全部 `解析失败`，而 `effort=low` 档都正常返回了坐标。
  → **动作步必须显式设 `effort=low`，且 `max_tokens` 要给思考链留够余量**，否则模型"成功"了但你拿不到坐标。
- **2026-10-20 复测（M1 集成回归）**：被吃光的预算**取决于图有多复杂**——
  合成探针图（800×600）上 `max_tokens ≤ 128` 就会被吃光（`stop_reason=max_tokens`、
  文本为空、思考 token 吃满预算）；给到 200 有时能答完、给到 256 又被吃光（**边界不稳定**）。
  真实桌面 1568 宽那次是 1200 被吃光。**结论不变**：动作步显式设低档并留足余量。

**延迟与精度对照（2026-10-20 复跑，`test_03_latency_effort.py`，目标 = 任务栏「开始」按钮）**

| 变体 | 尺寸 | HTTP | 延迟 | 思考 token | 定位误差 |
|---|---|---|---|---|---|
| 默认(thinking=max) | 1568×980 | 200 | 19.31s | —（预算吃光） | 解析失败，无坐标 |
| **`effort=low`** | 1568×980 | 200 | **16.68s** | 1024 | **5.6 px** |
| thinking disabled | 1568×980 | **400** | 2.73s | — | invalid_request_error |
| reasoning_effort=low | 1568×980 | 200 | 21.38s | — | 解析失败，无坐标 |
| 默认 | 1344×840 | 200 | 15.25s | — | 解析失败，无坐标 |
| **`effort=low`** | 1344×840 | 200 | **13.31s** | 1119 | **3.4 px** |

> 绝对延迟随图片尺寸与思考链长度浮动（首轮 10.6→5.9s 是更小图上的数）；**方向一致：`effort=low` 更快**。
> 无论哪一档，**默认 effort 都不适合动作步**。

## 3. 坐标量纲与两级 grounding（实测）

### 3.1 量纲 = **0~1000 归一化**（已确认，不是假设）

- 合成探针 800×600，四个角放 40×40 黑块；模型输出
  `{"tl":[100,133],"tr":[900,133],"bl":[100,867],"br":[900,867]}`，
  **输出最大值 900.00 → 判为 0~1000 归一化**（若按 0~1 或绝对像素解读，误差会差一个数量级）。
- 换算回像素后与真值比：**平均误差 0.2 px / 最大误差 0.2 px**（PASS，阈值 ≤2px）。
- 真实桌面同样成立：整屏降采样到 1568×980 后模型给 `{"x":409,"y":973}` → 物理像素 (1047.0, 1556.8)，
  UIA 真值 (1049.5, 1564.0) → **误差 7.6 px**。若分母是 999 或绝对像素，对不上这个量级。

> ⚠️ 这只是**本模型在本机**的实测结论。架构备忘 §1.4 要求代码里**不写死分母**，仍需运行时标定探针兜底
> （`src/minicode/coord/calibrate.py` 已实现，50 个单测全绿）。

### 3.2 真实桌面两级 grounding：L0 整屏粗定位 → L1 crop 精定位

目标 = 任务栏「开始」按钮（67×72 px），真值取 UIA `BoundingRectangle` 中心。

| 运行 | L0 整屏粗定位 | L1 crop 精定位 | 两次调用延迟 |
|---|---|---|---|
| 首轮（2026-10-19/20） | **3.4 px** | **2.3 px** | — |
| 本次复跑（2026-10-20） | **7.6 px** | **0.8 px** | 8.68s / 6.66s（合计 15.33s） |

- 流程：整屏 2560×1600 → LANCZOS 降采样到 1568×980（1.633×）→ 模型给粗点 → **从【原图】裁 512×512** → 模型在 crop 内给坐标 → 加 crop 原点映射回物理像素。
- **两次运行 L1 都明显优于 L0，趋势稳定**；但同一目标的 L0 误差在 3.4~7.6 px 之间浮动 →
  **单次数字不能当验收线**，验收要用一组目标的分布。
- 误差量级与架构备忘 §1.1 的分析一致：整屏降采样把目标抹小（E2），crop 后回到亚像素级（E1：512 宽时 1 归一化单位 = 0.512 px）。

# 目标应用任务清单

> **状态**：本地真值来源。本文件是**首批目标应用的具体任务清单**——每一步的「做什么」与「可判定的期望结果」。
> **它是什么**：里程碑「泛化」（架构备忘 §6 的 M3）的**输入**，用来把端到端用例写出来。**它不是工单**，不在这里拆工单。
> **它补的是什么缺口**：`docs/spec.md` §13 只定了**应用**（Windows 设置 → Chrome → 微信 → DSH / Tabbit → cc-switch），没定**任务**；没有期望结果，端到端用例就写不出来，泛化里程碑的验收标准会落空。
> **范围**：5 个应用 × 2~3 个任务。每个应用挑的任务要覆盖它代表性的那一种可访问性形态。
> **顺序**：按「树全空 / 扁平 DOM / 树被门控 / Electron / 完整树」推进，与首批目标应用的顺序一致。

## 0. 判定口径（所有任务共用）

一个任务的「期望结果」必须能被**机器或人明确判真假**，不接受「看起来差不多」。本清单统一用下面三种断言手段，优先级与架构备忘 §L4 一致：

| 手段 | 判什么 | 可靠性 |
|---|---|---|
| **可访问性树**（读控件树） | 状态 / 存在性 / 矩形变化 | 最高 |
| **文本比对**（OCR 或页面结构文本） | 文本是否出现或改变 | 中 |
| **像素差分** | 画面是否变了 | 最低（变化 ≠ 成功） |

**通用判据**：

- **落点精度**：最终落点与目标控件中心的偏差 **≤2 px**（在物理表面空间度量）。测法：控件框中心为真值，追踪记录里的最终落点与之比对。
- **不靠像素判成功**：点错打开错对话框也会「安定」，所以每条任务的期望里必须有一条**结构性**断言，不能只有「画面变了」。
- **通道与失败类型可查**：每一步的追踪记录里必须能读到「走的哪条通道」与「失败类型」（定位失败 / 决策失败 / 执行失败），否则任务跑完了也不知道哪一层出错。
- **危险动作需人工确认**：删除、支付、发消息、改系统设置这类动作，**审批机制在第二波工单**（本轮后置）。本清单中这类任务标注「人工代确认」——执行前由人替系统点一次确认，执行结果照常断言。标注「人工代确认」的任务，在审批上线前**只能手工跑通并记录**，不能算作端到端自动通过。
- **跑不动时算什么**：环境不可达（应用没装、页面没登录、网络不通）→ 该任务记为 **SKIP 并写明原因**，不许记为通过；失败与跳过必须分开统计。

## 1. Windows 设置

> **形态**：XAML island（UWP/WinUI）。本机实测所有相关窗口的控件树元素总数为 **0** → **UIA 通道不可用，强制走视觉通道**。
> **它是视觉兜底层的活体测试**：这条应用通过，才说明视觉通道不是纸面能力。

| # | 做什么 | 可判定的期望结果 |
|---|---|---|
| **W-1** | 打开 Windows 设置，进入「系统 → 显示」，读出当前缩放值并回显 | ① 追踪记录里**通道 = 视觉通道**，UIA 通道的失败类型是**覆盖失败**（树产不出任何候选），不是「目标不存在」；② 读出的缩放值与界面显示一致（文本比对）；③ 落点与目标控件中心偏差 **≤2 px**；④ 能力表里「Windows 设置」这一条记为**不可用**（禁止出现「UWP 一律可用」这类结论） |
| **W-2** | 把缩放从当前值改成 **125%**（改系统设置 → 人工代确认） | ① 改动后重新抓图，界面里能读到「125%」（文本比对）；② 全程**没有**出现把坐标挪到最近显示器的行为（越界一律报错，不夹取）；③ 缩放变更后如果物理映射已变，系统**要么**重新自检后落点仍 ≤2 px，**要么**明确报错要求重新自检——不允许带着旧映射继续点（此时判失败） |
| **W-3** | 对屏幕右下角一块区域执行**放大**动作，再在其中点击一个已知控件 | ① 放大是**回源重抓**（不是把旧图放大），放大后图像的细节来自物理分辨率重抓；② 放大后模型报的是**图内坐标**、**系统加这块区域的物理原点**映射回整屏（**不是** Anthropic 那套「模型仍报整屏坐标」—— M14 实测那套在本机模型上必然越界被拒），落点映射回整屏后与控件中心偏差 **≤2 px**；③ 这一步的期望断言成立（控件状态可读） |

> **W-3 的意义**：把「放大」（动作协议里的一个动作，**回源重抓**）与「裁剪」（两级定位内部的取景，从已抓到的那帧上 1:1 取窗口）分开验收 —— **两者的坐标契约现在相同**（都是「图内坐标 + 原点偏移」，2026-10-21 拍板），但**原点各走各的**（放大的原点是那块区域的物理原点，裁剪的原点是裁剪窗口的物理原点），混用会**静默偏移一整个区域**。

## 2. Chrome（BOSS 直聘页）

> **形态**：Chromium，DOM 扁平。精确交互走**浏览器通道**（页面结构），不靠像素。
> **它是「结构优先」的活体测试**：网页定位既准又便宜。

| # | 做什么 | 可判定的期望结果 |
|---|---|---|
| **C-1** | 打开 BOSS 直聘职位列表页，按职位名点开第一屏的一个职位详情 | ① 定位依据是**页面结构**（可访问性快照里有该职位名），不是像素；② 动作后页面出现「职位描述」区块（文本/结构断言）；③ 动作前后的 DOM 快照差异里，目标链接消失且详情块出现——**不是**只看画面变了 |
| **C-2** | 在搜索框输入中文关键词「前端工程师」并提交 | ① 输入框最终值 == 「前端工程师」（结构断言）；② 中文输入成功，**不需要切输入法**（Unicode 通道或剪贴板通道）；③ 提交后结果列表里每条含该关键词，或页面明确显示「无结果」——两种都算通过，但必须是其中之一；④ 剪贴板通道用过后，**剪贴板内容被恢复**（动作前后一致） |
| **C-3** | 向下滚动 **3 格**并把筛选条件设为「城市 = 上海」 | ① 滚动量以**行**为对外单位：3 行滚动后视口内容变化，但**没有**一次跳过整屏（对照：跳过的行数 ≫ 3）；② 滚动后界面已稳定再继续（惯性未结束时不再取位置）；③ 筛选生效后列表项集合发生变化（结构断言：城市字段 == 上海） |

## 3. 微信

> **形态**：本机微信 4.1.15 的树可用（153 元素 / 40 个可用交互控件），但存在**门控场景**与**弹窗**。
> **它是「门控 + 弹窗」的活体测试**：这三种形态里，只有它会主动挡住你。

| # | 做什么 | 可判定的期望结果 |
|---|---|---|
| **WX-1** | 打开微信，在搜索框输入联系人名并进入聊天 | ① 树处于门控状态时，系统**先尝试解开 + 退避重试**再判定不可用（不把「第一次读不到」直接当成「不支持」）；② 重试成功则能力表记为「可用」，仍不可用则记为「不可用」并按**覆盖失败**切视觉；③ 进入聊天后窗口标题 == 联系人名（结构断言） |
| **WX-2** | 在聊天输入框输入一段中文（含 emoji）并发送（发消息 → 人工代确认） | ① 中文与 emoji 都能正确注入（Unicode 通道逐字符注入，代理对正确）；② 发送后该文本出现在会话里（结构/文本断言）；③ **不可逆动作没有被自动重试**：一次发送只产生一条消息 |
| **WX-3** | 故意让微信弹出「更新提示 / 登录失效」模态弹窗，观察 agent 行为 | ① 检测到模态弹窗后**零动作下发**（弹窗上没有一个像素被点）；② 返回「交接给人」而不是继续往下执行；③ 交接产物可读：当前窗口标题、最后一步动作、已发坐标/已执行动作清单 |

## 4. DSH / Tabbit（Electron）

> **形态**：Electron，扁平树（类名即 CSS 类名、无 AutomationId），且**可能收不到键盘事件**。
> **它是「扁平树 + 输入通道退化」的活体测试**：能不能稳定打字，是它区别于前三个应用的地方。

| # | 做什么 | 可判定的期望结果 |
|---|---|---|
| **E-1** | 在 DSH Web GUI 打开设置面板，把一项设置（例如思考档位）改成低档并保存 | ① 落点落在该控件的控件框内、偏差 **≤2 px**；② 保存后设置面板里该项的值 == 低档（页面结构断言）；③ 追踪记录里能读到这条走的通道与失败类型 |
| **E-2** | 用 Tabbit 在当前页导航到一个已知地址，核对页面标题 | ① 导航后页面标题 == 目标标题（结构断言）；② **结构优先**：页面结构与视觉通道都可用时，选结构那条，并把选择理由记进追踪记录；③ 坐标与动作语义在跨技术栈后不变（同一个动作协议） |
| **E-3** | 在 DSH 会话输入框输入一段中文并发送 | ① 输入成功且输入框内容正确；② 若某条输入通道收不到键盘事件，系统**自动退到另一条输入通道**并记录这次退化（不能整条任务失败）；③ 剪贴板通道用过后剪贴板被恢复 |

## 5. cc-switch

> **形态**：原生窗口，**完整树** → UIA 通道「可用」。它是这条链路的**基准形态**：树在这里最好用。
> **它是「一次任务里改配置并验证结果」的活体测试**（spec user story 63）。

| # | 做什么 | 可判定的期望结果 |
|---|---|---|
| **CC-1** | 在 cc-switch 里把当前配置切到另一个供应商条目 | ① UIA 通道判定为**可用**（能力表里这一条是「可用」）；② 落点落在该条目的控件框内、偏差 **≤2 px**；③ 切换后界面上「当前配置」显示为新条目（文本断言） |
| **CC-2** | 把配置改完之后**核对结果**（读界面上的状态或状态指示） | ① 校验用可访问性树/文本比对拿到，**不是**靠「画面变了」；② 核对不通过时系统判**执行失败**并回报，不是当作成功 |
| **CC-3** | 跨应用：改完 cc-switch 的配置后，到 Chrome 打开一个依赖该配置的页面验证生效 | ① 三步动作各自有断言，链路上任一步失败都能定位到**哪一步**（三类失败分开统计）；② 跨应用过程中坐标口径与动作语义不变；③ 全程没有把坐标挪到别的窗口（目标窗口被遮挡时先置前再操作） |

## 6. 与工单的关系

- 本清单是**里程碑「泛化」工单的输入**，不是工单。工单在 `docs/tickets/` 下，按就绪边顺序编号。
- 端到端工单引用本清单的**任务编号**（如 W-1 / C-2 / WX-3 / E-1 / CC-3），不复制期望结果全文——期望结果以本文件为准。
- 泛化里程碑的通过率口径按**任务**算（本清单共 13 个任务），不按应用算。
- 标注「人工代确认」的 4 个任务（W-2 / WX-2，以及 WX-3 里的弹窗制造步骤与 CC-3 的跨应用确认）在危险动作审批上线前，只能手工跑通并记录；自动通过率要把它们**单独统计**，不许混进自动通过率里充数。

## 7. 还没定的事（写用例时需要拍板）

1. **BOSS 直聘页需要登录态**：没有登录时列表页与详情页的 DOM 结构会变，任务 C-1~C-3 的断言要按「未登录态」另写一版，还是由人先登录好再跑？——本清单按**已登录**写，用例落地时若发现未登录态，任务记 SKIP 并写明。
2. **cc-switch 的具体条目名**：本清单只写「另一个供应商条目」，真实条目名由跑用例的人当场指定；断言只依赖「当前配置显示 == 选中的那个条目」。
3. **DSH Web GUI 的设置项名**：同上，E-1 只要求「一项可改的设置」与「改后值 == 低档」，不钉具体项。
4. **微信联系人名**：WX-1/WX-2 只要求「一个存在的联系人」，不钉具体人。

## Problem Statement

在 Windows 上让程序代替人操作 GUI，一直没有一条能真正走通的路。

**第一，Windows 桌面没有统一的操作接口。** 每个应用的可交互性都不一样：原生 Win32 / WinForms / WPF 控件能通过 UI Automation 树拿到控件名、类型和**物理像素**包围盒；Chromium / Electron 应用虽然也能拿到树，但树是扁平的、类名直接就是页面的 CSS 类名；Windows 设置这类 XAML island 应用**根本没有树**，实测所有相关窗口的元素总数都是 0。唯一对所有应用都成立的手段是截图 + 坐标点击，而这条路在没有统一接口兜底的情况下，任何一次点击都可能落在错误的位置。

**第二，坐标会漂移，而且漂移是静默的。** 本机是 2560×1600 的 150% 缩放屏。如果进程没有声明 per-monitor v2 的 DPI 感知，它拿到的屏幕度量是 **1707×1067** 而不是物理的 **2560×1600**——差 1.5 倍。抓图按物理像素、点击按逻辑坐标下发，整体错位最大可达 **1280 物理像素**，点下去"看起来点中了"，其实点在隔壁。叠加模型侧的不确定性：整屏降采样会把 16 px 的图标压成 7.9 px，而 ScreenSpot-Pro 上目标框平均只占全图面积的 **0.07%**（**数据集统计**）；纯像素路线的定位精度衰减也已被量化——ScreenSpot-Pro 的分数从 ScreenSpot-v2 的 ~90% 掉到 40–60%【底稿 03 L317】。这几类误差**量级差一到两个数量级**，混在一起时，最致命的那一类（坐标系错配）恰恰是**最难被发现的**——因为它不会报错，只会让结果错一点。

**第三，现有方案要么接不上、要么不敢用。** 闭源的官方 computer-use 能力在本机根本连不上（Anthropic 的平台页返回地域封禁提示，OpenAI 的价格页 403，Google 的开发者站连接超时）；可用的开源方案要么卡在单显示器假设、要么没有可用的权重、要么在 150% 缩放下把物理坐标和逻辑分辨率混着用；被广泛引用的那些"实测提升"数字，有相当一部分查不到一手出处。而"从零自己写"这条路上一家公司已经走过一遍、并且失败了：那个项目的交接文档自己承认**性能数据无真实测量**，影子模式只有一个接口而没有任何落盘观察者，还因为把 UI Automation 树原文直接塞进模型上下文，捞出了真实密钥。

**第四，做对了也没有人知道做对了。** 桌面上点错一次，代价可能是发出去一条消息、提交了一笔支付、删掉了一份文件。更糟的是，成功率一掉，你不知道该改哪一层：是没找到元素（定位失败）、选错了动作（决策失败）、还是动作没生效（执行失败）。没有这三类失败的拆分和分段耗时埋点，调优就退化成盲猜。

所以问题不是"怎么让模型点鼠标"，而是：**怎么在 Windows 上建立一个坐标可信、失败可辨、代价可控、并且能被复现和审计的桌面操作底座。**

## Solution

minicode 是**结构优先、视觉兜底**的 Windows 桌面 computer-use agent。

**结构优先**：Windows 上 UI Automation 树能给出精确到物理像素的控件包围盒——微软官方文档明确写「The UI Automation API does not use logical coordinates」。这是相对 Linux 系榜单方案独有的工程红利：零缩放换算、零漂移、零模型成本。官方论文的同榜对照也支持这个方向：在同一张表的四组设置里，**纯可访问性树 12.24 最高，纯截图 5.26 最差，而"截图 + 树"12.17 反而优于纯截图的 SoM 方案 11.77**。所以默认路径是读树、拿控件、在控件上操作，模型只负责**选择**而不是**瞄准**。

**视觉兜底**：但树不是全覆盖的。Apple 对 4,068 个 iPhone app、77,637 块屏幕的人工标注显示，**59% 的屏幕至少有一个可见元素在树里没有匹配，4% 的屏幕树全空，94% 的 app 至少含一块这样的屏幕**（该数字经二手引述，未逐字核原文）。所以"树在"不等于"覆盖得住"，视觉通道必须存在。视觉通道走**两级 grounding**：整屏降采样后粗定位，再从**原始物理分辨率图**上裁一块小窗口放大二次定位。公开工作证明这条路有效且免训练（ScreenSpot-Pro 论文里 OS-Atlas-7B 单轮 18.9% → 裁剪重预测 40.2% → 级联搜索 48.1%；R-VLM 的 ScreenSpot 均值 53.4 → 66.3），而本机实测也复现了这个趋势（同一目标两次运行，L0 误差 3.4 / 7.6 px，L1 误差 2.3 / 0.8 px）。

**坐标可信**：工程端全程物理像素，唯一真值空间是「物理像素 × 虚拟桌面原点」。模型端的坐标量纲**不由代码写死**，而是由运行时标定探针实测判定——同一模型在官方不同渠道的分母就有 999 和 1000 两种写法，读文档不可靠，跑一次探针才可靠。探针必须用 2560×1600、判定容差必须是 1 px，因为 0~999 与 0~1000 对同一原始数值的物理分歧就是 `|物理x / 999|`，在 2560 宽上只有 2.56 px（x 轴）/ 2.86 px（欧氏），容差一放宽就永远分辨不出来。

> **2026-10-21 口径归位（已签字）**：那 1 px **只管「两个候选标度能不能分开」（标度可分辨性）**，**不管模型落点误差**——这是两件事，不许混成一个判据。1 px 本身**不放宽、不放松**（它继续是可分辨安全系数 2.0 的基数）。
> **模型落点误差另设判据**：视觉通道准入 = **落点等价族的最大分歧 ≤ 4 px**（= `SCALE_EQUIVALENCE_TOLERANCE_PX`；0~999 vs 0~1000 的 2.87 px ≪ 96 px 命中区）**且** **K 轮独立问的 96 px 方块命中率 ≥ 0.6**（K = `CALIBRATION_ROUNDS`）。
> 生态里也没有「1 px 绝对像素精度」这个判据：GUI grounding 一律用 **click accuracy（点落在 GT 框内）**。
> 依据：`docs/research/core-function-plan.md` A-1 / A-3。

**失败可辨**：每一步同时记录**三段耗时**（定位 / 决策 / 执行+校验）与**三类失败**（定位失败 / 决策失败 / 执行失败）。定位层区分 coverage failure（树里根本没有这个目标）与 selection failure（树里有但选错了）——**只有 coverage failure 才允许切视觉**，其余一律走错误处理。否则"切视觉"会从罕见兜底退化成每步都付 1.5~5 秒。

**代价可控**：危险动作（删除、支付、发消息、改系统设置、读剪贴板、跑 powershell）必须审批，且审批绑定"意图 + 目标"而不是笼统的"继续"；不可逆动作先 dry-run；遇到 UAC 提权弹窗**零动作下发**，把轨迹交人。

**可复现可审计**：动作日志记录时间、动作类型、目标窗口、屏幕坐标、截图哈希、动作前后状态与结果；截图只落哈希不落原图；UI Automation 树在送模型之前先过脱敏（字段白名单 + 正则脱敏 + 密码框值替换），脱敏器**排在所有通道之前**。

**产品形态**：先把桌面控制暴露成**独立 CLI + HTTP**，协议层稳定后再 MCP 化，宿主（DSH / Claude Code）可直接调用。首批目标应用是 **Windows 设置 → Chrome（BOSS 直聘页）→ 微信 → DSH / Tabbit（Electron）→ cc-switch**，正好覆盖"树全空 / 扁平树 / 树被门控 / Electron"四种真实形态。

## User Stories

### A. 坐标与几何——点得准

1. As a 桌面应用操作者, I want agent 点击的位置落在目标控件的中心, so that 我不会点到旁边的按钮。
2. As a 桌面应用操作者, I want agent 在我这台 150% 缩放的 2560×1600 屏上仍然点对位置, so that 我不用先关掉系统缩放。
3. As a 桌面应用操作者, I want agent 在我接上第二块显示器后仍然点对位置, so that 我扩展工作区不需要重配。
4. As a 桌面应用操作者, I want agent 在目标超出屏幕边界时**报错而不是把坐标挪到最近的显示器**, so that 我不会莫名其妙地点到另一个窗口上。
5. As a 开发者, I want 模型坐标的量纲由运行时标定决定而不是写死在代码里, so that 换模型、换服务商时不用改换算链路。
6. As a 开发者, I want 标定判定为多解**且**存在使物理落点分歧大于标定容差的替代标度时系统**拒绝走视觉通道**（落点等价的等价标度族继续用），而不是猜一个标度继续跑, so that 我不会在一条静默错位的链路上浪费几小时。
7. As a 开发者, I want 同一份原始坐标在不同标度解释下的物理分歧被量化出来, so that 我能判断探针尺寸和容差该取多少。
8. As a 开发者, I want 标定结果落盘（时间、探针图哈希、判定标度、各候选误差）, so that 事后能复盘"当时到底按哪个量纲算的"。

### B. 结构感知通道（UIA）

9. As a 桌面应用操作者, I want agent 默认先读窗口的可访问性树再决定怎么点, so that 操作既快又不需要花钱调用模型。
10. As a 桌面应用操作者, I want agent 在控件树可用且候选唯一时**不调用任何模型**就完成定位, so that 常规操作的延迟在亚秒级。
11. As a 开发者, I want 每个「应用 + 版本」的可用性被逐个探测并记进能力表, so that 我不会用"这类应用都能用"这种以偏概全的结论做设计。
12. As a 开发者, I want 能力表能表达三态——完全可用 / 部分覆盖 / 不可用, so that 「树在但覆盖不全」这个中间状态有地方放。
13. As a 桌面应用操作者, I want agent 能找到被藏在不可见子窗口里的控件, so that 像某些国产聊天应用那样主窗口只有三个边框按钮的情况也能操作。
14. As a 桌面应用操作者, I want agent 在同名控件有多个候选时**先在候选集内消歧**（模型只做指认、不产生新坐标），消歧不成或候选数超过上限时**拒绝执行并把候选报给我**, so that 它不会随便挑一个就点下去。
15. As a 桌面应用操作者, I want 每次动作前 agent 都重新读一遍控件树再定位, so that 它不会用一张过期的结构去点已经变化的界面。
16. As a 开发者, I want 控件树查询返回 0 个节点时被识别为"通道不可用"而不是"目标不存在", so that 静默退化不会被当成"没找到"。
17. As a 开发者, I want 控件树查询有明确的超时上限并且超时被当成通道级失败, so that 一次卡死的查询不会挂住整条流程。
18. As a 桌面应用操作者, I want agent 的界面状态只以白名单字段的形式送进模型, so that 我的聊天草稿和密码不会泄露。
19. As a 桌面应用操作者, I want 送进模型前的文本被正则脱敏（密钥、长 base64、JWT、私钥头）, so that 界面上恰好出现的凭据不会被抄走。
20. As a 桌面应用操作者, I want 密码框的内容在送模型前被替换成占位符, so that 我输入的密码永远不进上下文。
21. As a 安全负责人, I want 截图只以哈希形式落盘而不落原图, so that 敏感窗口的画面不会留在磁盘上。
22. As a 安全负责人, I want 窗口标题命中敏感词表的窗口被拉黑, so that 密码管理器、银行、支付类窗口不会被截图和读取。

### C. 视觉兜底通道

23. As a 桌面应用操作者, I want 在应用没有可用控件树时 agent 仍然能操作它, so that Windows 设置这类应用不是死路。
24. As a 桌面应用操作者, I want agent 在纯视觉路径上也能把点落在正确的小图标上, so that 托盘图标、菜单栏这类小目标不是只能靠运气。
25. As a 开发者, I want 视觉通道在每次启用前先跑一次标定探针确认量纲, so that 坐标不会因为分母猜错而整体偏移。
26. As a 开发者, I want 标定探针用与本机物理分辨率一致的尺寸并包含一个贴在最右边缘的目标, so that 0~999 与 0~1000 这一族可以被分辨。
27. As a 开发者, I want 标定的判定容差独立于动作的越界容差, so that "能不能分辨量纲"和"点击有没有越界"两个问题不会互相干扰。
28. As a 开发者, I want 整屏只做粗定位、最终落点只在放大后的局部图上产生, so that 整屏降采样带来的小目标丢失不会直接变成误点。
29. As a 桌面应用操作者, I want 粗定位不准时能在小窗口里二次精确, so that 目标越大反而越容易点中。
30. As a 开发者, I want 裁剪窗口一定从**原始物理分辨率图**上取而不是从降采样后的图上取, so that 放大是真的提升有效分辨率而不是放大糊图。
31. As a 开发者, I want 裁剪窗口越界时用平移或缩小而不是夹取, so that 目标本身不会被裁出窗口。
32. As a 开发者, I want 二次精定位**默认无条件执行**、但**结果越界或偏离过大就回落到粗定位结果**, so that 多花的那一次模型调用买到的精度不会被「选到相邻的同类控件」吃掉。
    > 📌 **2026-10-22 口径改写（人已拍板）**：本条原为「二次精定位**按需触发**而不是每步都做」，
    > 依据是「无条件做 crop 整体 −0.3pp」——**那条数字至今没有一手出处，一律不引用**。
    > 本机同批实测（42 条 ScreenSpot-Pro 抽样）方向**相反**：
    > **门控开 38.1% / 2.381 次调用**，**门控关 57.1% / 2.000 次调用** —— 门控在
    > **准确率与成本两个轴上同时更差**（它的触发条件「两次独立粗定位不一致」
    > **恰好是精定位前提条件的反面**：不一致 ⇒ 粗点已偏 ⇒ 目标大概率不在 crop 窗内）。
33. As a 开发者, I want 二次精定位失败时能回落到粗定位结果, so that 精定位层不会变成"平均更差"的一层。
34. As a 桌面应用操作者, I want 每次动作都能看到模型自己发出的坐标和它实际看到的图片尺寸, so that 出问题时能立刻判断是模型算错还是我算错。

### D. 决策与动作执行

35. As a 桌面应用操作者, I want agent 把我的目标拆成一段可执行的动作序列而不是一步步问我, so that 多步任务能一次跑完。
36. As a 开发者, I want 决策层产出的是动作程序而不是逐条动作, so that 循环和分支由代码控制而不是每步都问一次模型。
37. As a 桌面应用操作者, I want agent 能点击、双击、右键、拖拽、悬停、滚动、输入文本、按键、截图、放大、读控件树、请求人工, so that 常见的桌面操作都能覆盖。
38. As a 桌面应用操作者, I want 点击是"移动→停→按下→停→抬起"这样带停顿的, so that 需要 hover 才展开的菜单能正常点开。
39. As a 桌面应用操作者, I want 双击和两次独立单击能被区分, so that agent 不会把两次单击误当成双击。
40. As a 桌面应用操作者, I want agent 能直接输入中文和 emoji, so that 我不用先切输入法。
41. As a 桌面应用操作者, I want agent 的滚轮滚动量符合"一格一行"的直觉, so that 长列表滚动不会一次跳过几十行。
42. As a 桌面应用操作者, I want agent 在滚完页面后等界面稳定再继续, so that 它不会在惯性动画里误判元素位置。
43. As a 桌面应用操作者, I want agent 用粘贴方式输入时先备份我的剪贴板并在动作后恢复, so that 我的剪贴板不会被它的输入内容污染。
44. As a 桌面应用操作者, I want agent 在窗口被别的窗口挡住时先把目标置前再操作, so that 它点的是我以为的那个界面。

### E. 校验、反思与可观测

45. As a 桌面应用操作者, I want 每一步动作后 agent 都确认界面确实变了, so that 它不会在一个已经失焦的界面上继续往下点。
46. As a 桌面应用操作者, I want agent 能对我指定的期望结果做断言（比如某个按钮变成不可用）, so that 任务的完成状态不只靠模型自称。
47. As a 桌面应用操作者, I want agent 在重复做同一个无效动作时被强制换策略, so that 它不会在一个死循环里一直点到天亮。
48. As a 桌面应用操作者, I want agent 在整个任务步数达到上限时停下来交给我, so that 失控的流程不会无限继续。
49. As a 开发者, I want 每一步日志同时记录定位、决策、执行三段耗时, so that 变慢时我知道该优化哪一层。
50. As a 开发者, I want 失败被拆成定位失败、决策失败、执行失败三类分别统计, so that 成功率一掉我能定位到层。
51. As a 开发者, I want 动作日志能完整回放每一步, so that 出事故后能看到"它当时以为自己在干什么"。
52. As a 开发者, I want 模型自评的置信度**不被**用作危险动作的放行条件, so that 高置信度的错误不会变成不可逆操作。

## Implementation Decisions

### 1. 架构与组成

- **分层**：L5 安全与审计 / L4 校验与反思层 / L3 决策层 / L2 视觉定位层 / L1 结构感知层 / L0 设备与坐标层。自建两个缺口：**crop 精定位回路**与**校验与反思层**；其余复用成熟实现。
- **复用组合（方案 B）**：harness 骨架用 `microsoft/UFO`（MIT、Windows 原生、UIA + 原生 API **混合动作通道**，其坐标系天然就是 UIA 物理像素）；UIA 通道用 Windows-MCP / mcp-windows / 微软 winapp CLI 之一；**浏览器通道**用 Playwright MCP；大脑用 MiniMax M3.1 Flash。
- **不采用其余两个候选方案的原因**：UI-TARS-desktop 路线只支持单显示器、150% DPI 下不替你解决截图与点击的坐标错配，且 UI-TARS-2 **至今没有权重**（其"只支持单显示器"等负面证据来自单一博客，按媒体级处理）；MCP 化起步路线动作集被裁剪（没有按住键/修饰键点击）、纯像素通道的坐标漂移仍在、成熟度未经长期验证。
- **UFO²/UFO³ 全仓没有 crop/zoom 动作**（逐文件核实，16 处命中全部是把 UIA 元素框裁出来做 CLIP 匹配）→ 拿它当骨架，crop 精定位这层必须自建。
- **ScreenSpot-Pro 官方评测仓库自带 5 个可运行的 coarse-to-fine 基线**，形状与本方案一致（整屏 → 粗框中心裁 → crop 内第二遍 → 映射回全图），本方案的 crop 窗口尺寸是**运行时参数**（生产默认 **192**，见 §4 的口径改写），评测脚本可直接复用做同表对比。

### 2. 坐标系契约

- **唯一真值空间 = 物理像素 × 虚拟桌面原点**。模型坐标永远留在帧内（正数），负坐标只存在于执行层。
- **模型端量纲 = 0~1000 归一化（本机实测确认）**，但**代码里禁止出现任何写死的 1000 或 999**，分母一律来自运行时标定结果；**禁止**用"数值大小"猜坐标系。
- **crop 契约 = 「crop 内坐标 + 原点偏移」**。
  - 与 **Anthropic 契约的差异**：Anthropic 的官方实现要求「模型在放大图里仍报**整屏坐标**」——官方源码原文是「The model keeps emitting coordinates in screenshot pixels afterwards; the zoom image itself is never a coordinate frame」，即放大图**不是坐标系**，放大只是给模型看清楚，坐标映射由模型自己承担；SDK 只校验 region 是 4 个非负整数后原样交给驱动，**完全不参与任何 crop 偏移变换**。
  - **本方案不同**：所用的 Qwen3-VL / M3.1 Flash 未被训练过那套契约，因此让模型报 crop 内坐标，由 harness 加 crop 原点偏移映射回全屏物理像素。独立实现佐证：ScreenSpot-Pro 的双模型一致性路由实现用的就是 `abs2_x = x1 + (step2[0]/1000.0)*(x2-x1)`。
  - **两套混用必错**：模型报整屏坐标而 harness 又加偏移 → 落点偏一整个 crop。
  - **责任方三分**：crop 内 → 整屏由模型完成（Anthropic 契约下）/ 由 harness 加偏移完成（本方案契约）；整屏 → 物理由 harness 完成；SDK/驱动不参与。
- **换算链路必须单一来源**：缩放系数、标度、crop 偏移都只有一个真值来源，不允许文档写一套、代码写另一套。
- **坐标适配器的方法面**（每层可单独调用、单独断言）：模型→相对、相对→截图像素、截图像素→物理、物理→截图像素、模型→截图像素、模型→物理（完整链路）、物理→模型（逆，用于真值编码与往返自检）、模型空间合法区间查询、越界判定、白名单判定。

### 3. 运行时标定探针

- **探针尺寸必须是 2560×1600**（与目标机物理宽一致），不能用 1280×720。
- **判定容差必须是 1.0 px，且独立于动作协议的 2 px 越界容差**（原型早期把两者合成了一个默认值，已拆开）。**它只管「两个候选标度能不能分开」（可分辨性）**——模型落点误差由下面「落点等价判据」那一条的**命中率**管（见本文「坐标可信」一节的 2026-10-21 口径归位）。
- **分歧公式**：同一原始值 `n` 在 0~999 与 0~1000 两种分母下的物理差 = `n × W × (1/999 − 1/1000)`，等价于 **`|物理x / 999|`**。
  - 2560 宽探针：x 轴单轴分歧 **2.56 px**，欧氏距离（右下角目标）**2.86 px** → 1 px 容差下留 2~3 倍余量。
  - 1280 宽探针：单轴 **1.28 px**，欧氏 **≈1.30 px** → 2 px 容差下与容差同量级，必然漏判。
- **四个目标必须包含一个贴在最右边缘的**（n≈1000）：分歧随 n 线性增长，中部 n≈780 只有 2.00 px。
- **容差为什么必须小**：Windows 的「点击即命中」容差通常只有 2–4 px，而 0~1000 映射回 2560 宽时 1 个归一化单位 = 2.56 物理 px。容差一放宽到"差不多能点中"的量级，标度错误就永远暴露不出来——所以宁可"标定失败拒跑"，也不猜一个标度继续跑。
- **标定要判 5 种标度**：0~1 / 0~999 / 0~1000 / 截图像素绝对 / 模型输入像素绝对。
- **越界判定必须先判模型空间**：把 0~1000 的 953 当 0~1 读时，模型空间那层会立刻判定越界；标定器必须捕获该异常并记为无穷大误差，否则第一个候选就中断整个标定流程。
- **两种"绝对"标度在"模型输入尺寸 == 截图尺寸"时不可区分**：必须显式暴露两个维度——**标度判定**（唯一命中 / 多解）与**落点等价**（容差内等价 / 分歧），不可区分就如实报多解并给出等价标度列表。
- **落点等价判据**：标定探针给出候选标度族；**落点等价族 = 判定标度 ∪ {与判定标度的物理落点分歧 ≤ 落点等价容差（4 px）的候选标度}**。**视觉通道准入 = 两条同时成立**：① 落点等价族的最大分歧 ≤ 4 px（`SCALE_EQUIVALENCE_TOLERANCE_PX`）；② **K 轮独立问**的 96 px 方块命中率 ≥ 0.6（`CALIBRATION_ROUNDS` / `CALIBRATION_MIN_HIT_RATE`，命中半径 = 探针方块边长的一半 = 48 px）。不成立 → 视觉通道不可用（此时**回落 UIA 通道**或直接报错）。**模型落点误差由命中率判，不再由 1 px 判**（1 px 只管可分辨性）。
> **前提**：探针必须含最右边缘目标（C-03 已要求）——0~999 与 0~1000 的物理分歧随 x 线性增长、最大值在右边缘，探针不覆盖最坏情况则本判据悄悄失效。
> ⚠️ **已知弱点（如实记）**：落点等价族按「分歧 ≤ 4 px」定义 → 条件 ① **按定义恒成立**，真正起闸门作用的是**命中率**（依据：`docs/research/core-function-plan.md` A-1）。要条件 ① 也能拒绝，族必须改用「按拟合」定义 —— 那是另一次口径变更，需人拍板。
- **标定结果必须落盘**：时间、探针图哈希、判定标度、容差、各候选最大误差、**标度判定（唯一命中 / 多解）与落点等价（等价 / 分歧）两个字段**、**落点等价族与其容差**、**轮数 / 命中率 / 落点误差分布（中位、p90）**。

**原型产出的类型形状（来自 coord 原型，编码了"量纲由标定决定、唯一性必须显式"这个决定）**：

```text
ModelScale      := RELATIVE_0_1 | RELATIVE_0_999 | RELATIVE_0_1000
                 | ABSOLUTE_CAPTURE | ABSOLUTE_MODEL_INPUT
CalibrationResult := detected_scale | candidates | confident | unique
                  | equivalent_scales | divergence_px | roundtrip_ok | notes
```

### 4. crop 精定位

- **两级 grounding**：整屏截图按物理 1:1 抓取 → 降采样到模型输入尺寸（保持宽高比）→ 模型输出**粗点**（本轮起**出框**，落点取框中心）→ 以粗点为中心取 **crop 窗口**（**物理像素**、1:1 不缩放；**尺寸是运行时参数**，生产默认 **192×192**，见下面的口径改写）→ **从原始物理分辨率图裁剪** → 模型在 crop 内输出坐标 → 按标定出的标度换算成 crop 内物理像素 → 加 crop 原点 → 最终物理像素坐标。
- **最终落点只在 crop 尺度上产生**，整屏归一化坐标只用来"选哪块区域"，永远不直接点击。
- **crop 必须从原始物理分辨率图裁**。依据：Anthropic 的两套官方实现都从物理分辨率重截裁剪、zoom 从不接触降采样产物；而且**官方自己踩过这个坑**——2025-11-24 的初版从已降采样的截图裁、却用物理坐标算偏移，只要发生缩放就错位，直到 2026-08-21 才改为裁物理捕获。按来源裁剪是唯一真正增加有效分辨率的方式；同一帧裁剪再上采样不增加任何新像素；在降采样图上裁剪则细节上限被卡死。
- **越界策略用 shift / shrink**（平移保尺寸、尺寸不足时缩小），**不夹取**——夹取会把目标裁出窗口。官方两套实现在这一点上本身就不一致（一套静默放大、一套静默夹取），本方案取 shift。
- ⚠️ **2026-10-22 口径改写（人已拍板）——「必须门控」这条作废**：
  - **crop 精定位默认无条件执行**；门控**降级为「记录器 + 回落判据」**（四条判据照判、照落盘，**不再决定开不开**）。
  - **原依据「无条件做二次精定位整体变差（−0.3pp）」一律不引用**（无一手出处）。本机同批实测方向**相反**：门控开 **38.1% / 2.381 次**，门控关 **57.1% / 2.000 次**（42 条 ScreenSpot-Pro 抽样）——门控在**准确率与成本两个轴上同时更差**。根因：门控的触发条件（「两次独立粗定位不一致」）**恰好是精定位前提条件的反面**。
  - **保留的硬闸门**是**事后几何验收**：精定位落点**越界**或**偏离 crop 窗口中心 > 50 px**（判据是**严格大于** —— 代码 `ground/channel.py` 写的是 `deviation > 50.0`，**恰好 50.0 px 不回落**；阈值来源：ZoomClick Table 11，最优 50.7 px、分类准确 91.8%，原文「错误对中位 **>50 px**」）→ **回落**到整屏粗定位点。
  - **禁止**再用「再问模型一次算一致性」当触发条件（公开同构实现 zoom-consistency 路由本身是 **null result**：+0.8%，McNemar p=0.19）。
- **crop 尺寸**：**运行时参数**，生产默认 **192×192 物理像素**（`ground/channel.py::DEFAULT_CROP_WIDTH_PX`；冻结原型 `coord/crop_refine.py` 的 512 **一个字没动**）。⚠️ **不照抄论文的 1024** —— 330 条分层抽样、七个尺寸**全集**、**A 半调 / B 半评**的实测是**中间最好**：A 半 128 35.2% / **192 43.0%** / 256 43.0% / 512 42.4% / 768 42.4% / 1024 41.8% / 1280 40.0%（**1024 比 512 还差**）；192~768 彼此差 ≤1 条样本（= 噪声），按 A 半中位误差破平也是 192 最低，且它的精定位图像 token 只有 49（512 是 361）。
- **必须能粗定位回落**（crop 精定位失败时退回粗定位结果）。
- **门控埋点与回落率必须有统计**；在 ScreenSpot-Pro 上与 5 个基线同表跑。⚠️ **硬判据改成三臂同批可对比**：门控记录器 / 无条件两段式 / **只用粗定位**（基线，1.00 次/目标）。
- **命名避坑**：`sespoir/ReGround` 与 ScreenSpot-Pro 论文里的 ReGround 基线是同名不同物。

### 5. UIA 通道

- **`BoundingRectangle` 是物理像素**（前提：进程已声明 DPI 感知）；官方文档明确写「The UI Automation API does not use logical coordinates」，并且非 DPI 感知的客户端在非 96-dpi 环境拿不到正确结果——**UIA 客户端自己也必须 DPI 感知**。
- **包围盒必须按 4 个 int 读**。按 double 读会得到 1e-311 量级的非规格化数，四舍五入后全为 0，表现为"候选全都没有坐标"——**纯静默失败**，因为 0,0 看起来像一个合法的左上角。
- **能力表三态**：完全可用 / 部分覆盖 / 不可用（+ 应用版本）。**禁止**出现"Chromium 一律失效"或"UWP 一律可用"这种类别级结论——实测 Chromium 应用能拿到 205~345 个元素（含整页 Document、具名 Hyperlink、地址栏 Edit，类名直接是页面 CSS 类名），而实测 Windows 设置的所有 XAML island 相关窗口元素总数都是 0。
- **判定姿势**：递归子窗口 + 看 UIA 的 ClassName，**不是数候选数**。旧项目实测：某聊天应用主窗口只有 3 个边框按钮，真正的 162 个元素藏在不可见子窗口里；树没挂出来时边框按钮照样能读到，只按"候选数 ≥ 3"判会得到**假阳性**。
- **同名候选用 id 区分**（AutomationId / runtime id）；**候选不唯一时先做消歧**：在 UIA 候选集内让模型**只做指认**（候选唯一时零模型调用；指认必须落在候选集内且恰好一个）。消歧失败、**候选数超过上限**（默认 8）、或指认不唯一 → 走 L4 错误处理并回报候选集，不许随便挑一个。**任何情况下都不切视觉。**
- **元素 id 每次观测重新生成**，**执行前必须重读控件树重新定位**，定位不到就失败——宁可不动，也不能把动作打到看起来相似的另一个控件上。
- **查询后必须检查是否返回 0 节点**（0 节点 = 静默退化，不是"没找到"）；**超时阈值放宽到约 5 秒**；只做定点查询，禁止全树 dump。
- **性能数字必须分档引用**：带属性条件的桌面级查询 **416 ms / 401 命中（本机实测）**；无条件全树遍历约 1000 元素 **≥8 秒（社区实测）**；UIA 通用查询延迟 **1.6~1.9 秒（底稿二手）**。三者语义不同，**不可混用**。社区那个"8 秒"很可能是 Python 包装层开销而非 UIA 固有成本，因此**访问层用 comtypes 直连**，不用纯 Python 包装。
- **UIA 调用必须在独立线程**，否则可能死锁。
- **只做定点查询 + 缓存请求**：先用缓存请求把控件类型、名字、包围盒、是否离屏一次拉回；**先读名字**（绝大多数元素没有名字，读到空就放弃，省掉后面多次 COM 往返）。
- **已知门控**：部分应用需要活的辅助技术进程才能挂上树；某些 Qt 应用启动期树未就绪，**必须重试**（先激活窗口 + 指数退避）再判定不可用。

### 6. 设备与坐标层（L0）

- **进程第一行**声明 per-monitor v2 的 DPI 感知（`SetProcessDpiAwarenessContext(-4)`），必须在创建任何 UI 之前、任何依赖 DPI 感知的 API 之前调用；**mss 与 pyautogui 都必须在它之后 import**——pyautogui 在 import 时会设成 System-aware、mss 在构造时会设成 V1，谁先 import 谁把进程模式锁死，之后再设 V2 会失败。
- **启动自检断言**（任一不成立直接中止进程，不进入动作层）：屏幕度量必须是物理的 **2560×1600**（返回 1707 说明感知没生效，整条坐标链不可信）；设备 caps 的逻辑 DPI 必须是 **144**；截图尺寸等于 2560×1600 且**不为 0×0**；光标回读与下发坐标一致且**不返回 (−32000, −32000)** 哨兵值。
  - 注：官方文档页脚对 `GetSystemMetrics` 有"在 per-monitor 感知线程不应使用"的措辞，因此断言以**设备 caps 交叉验证**为准，不单靠它。
- **不设 DPI 感知的代价（本机实测）**：同一台机器上，DPI-unaware 进程拿到 1707×1067 / 96 DPI，PMv2 进程拿到 2560×1600 / 144 DPI——**所有屏幕度量被 ÷1.5**。
- **鼠标下发**走 `SendInput`（`mouse_event` 官方已标注 superseded）：绝对坐标归一化 `nx = round((x − vx) * 65535 / (vw − 1))`，**分母必须是 (维度 − 1)**，否则最后一个像素永远点不到；**必须带 `MOUSEEVENTF_VIRTUALDESK`**，否则归一化只映射到主显示器。本机实测 6 个目标点 × 12 次采样，`round(x*65535/(W−1))` 误差全为 0。
- **禁止用相对移动做坐标校正**——官方文档明确相对移动会被鼠标加速曲线放大到 4 倍。校正方式只能是再发一次绝对移动。
- **`SendInput` 返回 0 有两种原因**（UIPI 阻断 / `cbSize` 错），且 `GetLastError` **两种都不指示** → 必须检查返回值等于注入条数。
- **ctypes 的输入结构体必须是 union**。写成两个独立成员时 x64 下大小变成 64（正确是 40），`SendInput` 因 `cbSize` 不匹配**直接返回 0 且不报错**，所有点击静默失效。必须显式声明参数与返回类型，否则 64 位下的句柄会被截断。
- **键盘**：Unicode 码点注入通道**绕过输入法与键盘布局**（中文、emoji 都能打）；**每个字符单独一次注入**，按下与抬起放同一个数组里可能一个字符都不产生；非 BMP 字符要拆成代理对；`KEYEVENTF_KEYUP` 只加在抬起事件上。**剪贴板通道**最稳，但必须**写前备份、动作后恢复**（用 `finally` 保证），且某些应用（终端、密码框）不接受粘贴 → 退回 Unicode 通道。Chromium/Electron 可能注入返回成功却完全收不到按键事件（该条无一手出处、未在本机复现）→ 这类应用改走浏览器自己的输入通道。
- **滚轮**：一次滚动量常量是 120，而多数 GUI 框架的"滚动一格"是 1 行 → 本项目**统一按 ×50 换算**（该修补来自旧项目一手文档转述的同类 agent 硬编码，非 Windows API 事实）。滚完等 **300–600 ms** 再截图，规避滚轮惯性。
- **点击时序**：`移动 → 停 60 ms → 按下 → 停 40 ms → 抬起`。三条理由：很多 UI 要先收到移动消息才认点击；双击阈值的默认时间约 500 ms、矩形约 4 px（两次独立单击则要 >500 ms，**具体值应运行时查询实际系统参数**）；提权弹窗切安全桌面需要几十到几百毫秒建好再注入。Windows 定时器精度 15.6 ms，断言用 `>=` 而非 `==`。
- **截图选型**：GDI 抓屏是默认（物理像素、免授权、单帧 5~30 ms 量级），Windows Graphics Capture 只在必须抓被遮挡/最小化/硬件加速窗口时才上（需要用户点一次系统选择器），**禁止用 `PrintWindow` 兜底**（硬件加速/分层窗口会返回黑或空白）。
- **多屏与哨兵**：归一化基准必须用虚拟桌面度量族而不是主屏度量；副屏在主屏左侧/上方时虚拟桌面原点为负；`-32000` 是 Windows 对最小化窗口的哨兵值不是坐标；间接显示驱动虚拟显示器会让抓屏拿到 0×0 画面并返回哨兵坐标 → 遇到就跳过该捕获源或改用不需要坐标的控件调用；`MAKELPARAM` 按 16 位无符号打包，负坐标会回绕成约 65500（点击落到右下角而不是左上）。这些多条来自公开 issue 的二手转述、**未在本机复现**。
- **pyautogui 的四个函数空间不一致**（尺寸返回逻辑分辨率、截图返回物理像素、查找在物理空间、点击按逻辑解释），且越界点击会被静默夹到非负 → **绝不把查找结果直接喂给点击**。

### 7. 动作协议

- 统一在**截图像素空间**（整数，左上原点），每帧携带物理变换元数据；DPI 与多屏在抓图层解决，不污染动作层。
- **12 个动作**：截图（可带区域）/ 点击 / 移动 / 拖拽 / 输入文本 / 按键 / 滚动 / 等待 / **放大** / 读控件树 / 执行代码 / 请求人工。
  - **放大 ≠ 裁剪**：**放大**是动作协议里的一个动作（把指定区域回源重抓后送模型看清楚）；**裁剪**是两级 grounding 内部的取景操作（从原始物理分辨率图上取一块窗口，再由 harness 加偏移映射回全屏）。两者服务于不同环节，**不可混称**。
    > 📌 **2026-10-21 口径改写（M14 实测，人已拍板）**：放大的坐标契约**也**是
    > **「图内坐标 + 物理原点」** —— 模型报的是**那张放大图里**的位置，
    > 系统加这块区域的物理原点映射回整屏；**提示词里不许出现原点**
    > （出现了模型就会改报整屏坐标，两套契约混用会静默偏移一整个放大区域）。
    > 依据：本机模型在放大图里报的是**那张图的像素**，照整屏口径解会**系统性越界**
    > （模型的合法区间是整屏的尺寸）→ 动作被拒；改成图内坐标后偏差 14.0 px
    > （对包围盒中心 1.1 px）。**契约服从实测**。
    > ⚠️ 注意：这与 Anthropic 那套「放大后模型仍报整屏坐标」**不同**——
    > 本项目用的模型没被训练过那套（本方案 crop 内坐标的理由同理）。
- **放大动作必须回源重抓**（不放大旧图）。
- **越界不夹取，直接报错**（容差 **2 px**）+ 安全区域白名单；物理层越界**不许**自动挪到最近的显示器（那等于点到别的窗口），应报"被桌面裁切"。
- **每动作可带期望断言**；没有期望时也要做默认校验（帧差分：变化率低于 1% 且持续两帧 → 报"界面无变化"）。但**"无变化 ≠ 失败"**、**"像素变化 ≠ 成功"**（点错打开错对话框也会"安定"）。
- **危险动作带审批标记**。
- **停止条件由 harness 强制**（轮次硬上限 + 同一动作哈希连续 ≥3 次且帧无变化 → 强制换策略）。**协议里没有"完成"这个动作值**——模型自称完成不算数（"a model's terminate(success) action is not proof of real-world success"）。
- **每步回显模型自己发出的坐标与实际发送尺寸**，让模型能对账自己的坐标。
  > 📌 **2026-10-20 补充（M4）**：**UIA 通道的消歧模型不产坐标**（它只在候选集内指认）——回显里给的是**选中项**（候选行号 + 控件名）与**实际发送的图片尺寸**，**不许伪造成坐标回显**（工单 M4 AC 9）。坐标回显是**视觉通道**的形态。

### 8. 校验 / 反思层

- **三段耗时 + 三类失败必须拆开埋点**（定位 / 决策 / 执行+校验；定位失败 / 决策失败 / 执行失败），每步日志同时记录。旧项目缺这个埋点，是它"调了半年不知道该改哪" 的根因。
- **切视觉只认 coverage failure**：UIA 通道**产不出任何候选**（无 provider / 树被门控 / 目标不在树里）。候选不唯一（先按 §5 做消歧）、被遮挡、尺寸异常、查询超时、名称匹配不上——这些**禁止切视觉**，一律走错误处理。否则切视觉会从罕见退化成每步都付 1.5~5 秒。
  > 📌 **2026-10-20 口径澄清（M4）**：「名称匹配不上」指**名字条件没匹配上、通道还有退路**的情形（定点查询退到「控件类型条件 + 名字包含过滤」）；**退路也找不到 → 候选集为空 = 覆盖失败**（允许切视觉），**候选集非空但选不出 = 选择失败**（禁止切视觉）。判定口径以工单 M4 AC 6 为准：两类失败**标识不同、互不混淆**，**只有覆盖失败**被标记为允许切视觉。
- **四类卡死检测器**：帧无变化、重复动作、进度停滞、轮次硬上限。
- **效果验证三手段按可靠性排序**：可访问性树（查状态/存在性/矩形变化）＞ OCR 文本比对 ＞ 像素差分（判"画面变了没有"，最快最通用，但变化 ≠ 成功）。判据用三者的或，且刻意不让模型当裁判。
- **像素差分的可执行参数**：动作前抓基线帧；动作后轮询（首次立即 + 100 ms 内 15 ms 节奏 + 之后 20 Hz）；比较用 8×8 像素块 + 32 位精确比较；判定顺序是"有反应 → 安定 → 返回"；阈值取 1% 像素变化。
- **重试策略**：只重试可逆动作（移动/滚动/聚焦），发消息、支付、删除**不可自动重试**；重试带退避与上限（3 次，200/500/1200 ms）；**每次重试前必须重新感知**（复用旧坐标 = 误点）；用状态机而不是脚本；不可逆动作前先 dry-run。
- **模型置信度不得作为危险动作的放行条件**。旧项目实测存在**高置信度的错误**（自评 0.95 仍然错），且答对时的置信度均值反而低于答错时（均值倒挂）→ 绝对值不可当把握度，排序可用；二元阈值最优在 0.4 而非 0.5。

### 9. 安全与审计

- **脱敏必须排在所有通道之前**。旧项目实测：UI Automation 树会真实读到聊天正文与未发送草稿，本机捞到过草稿里的真实密钥；另有 API key 明文躺在配置文件里并已进入会话日志。
- **最低要求**：字段白名单（控件名与类型可保留，正文类文本默认不外发）；对值/名字/帮助文本/标识做正则脱敏（密钥前缀、长 base64、JWT、长十六进制串、私钥头）；密码框的值一律替换为占位符；脱敏在送模型之前执行且脱敏器本身要有单测；截图只落哈希不落原图，敏感窗口按标题关键词与对话框类名拉黑名单。
- **危险动作清单**：删除、支付、发邮件/消息、注册、改系统设置、运行命令行、安装软件、改注册表、提权弹窗、读剪贴板、截含敏感窗口的屏。**审批必须绑定"意图 + 目标"**。
- **动作日志字段**：时间、动作类型、目标窗口句柄与标题、屏幕坐标、截图哈希、动作前后状态、结果。

### 10. 模型接入

- **端点与协议**：Anthropic Messages 兼容协议，基础地址 `https://opencode.ai/zen/go`，模型 `minimax-m3.1-flash-free`。
- **必需请求头**：`x-api-key`、`anthropic-version: 2023-06-01`、`x-opencode-session`，以及**必须同时带**的 `user-agent: opencode/1.0.0` 与 `x-opencode-client: cli`。
- **图片内容块**：base64 的 PNG，按 Anthropic 内容块形状发送。
- **响应解析**：读内容块的文本；用量看输出明细里的思考 token 数。

**四个坑（本机实测，全部是症状 → 成因 → 正确做法）**：

| # | 症状 | 成因 | 正确做法 |
|---|---|---|---|
| ① | 请求被拦，返回 **HTTP 1010**（不是模型侧错误） | 缺 `user-agent` 或 `x-opencode-client`，被 Cloudflare 层拦 | 两个头**必须同时带**；接入时不要"精简"掉 |
| ② | 免费档模型在不带 `/go` 的地址上返回 **`FreeTierError`** | 该档位不在那条通道上 | 免费档**只能走 `/zen/go`** |
| ③ | 发"关闭思考"参数 → **HTTP 400**（无效请求） | 该模型要求自适应思考，思考不可关闭 | 唯一可用的降延迟手段是 `output_config.effort = low`（实测 10.6s → 5.9s）；另一种写法 `reasoning_effort` **无效**（实测 21.38s，反而最慢，行为与默认一致 → 参数被忽略） |
| ④ | **模型返回 HTTP 200 但没有 JSON 输出** | 默认档（= 最高档）在 `max_tokens=1200` 时**思考链把预算吃光**，输出为空 | **动作步必须显式设 `effort=low`，且 `max_tokens` 要给思考链留够余量**——否则模型"成功"了但你拿不到坐标 |

- **模型客户端统一读仓库的 `.env`**，不读用户目录下的凭据文件。当前原型脚本读的是后者（同一把密钥），接入主链路时必须统一到仓库配置。
- **思考档位五档**（低/中/高/极高/最高），**缺省即最高**。动作步必须显式设低或中；高只用于规划/反思步；**任何一次调用未显式设档位即判不合格**，判据是每条请求日志里都有显式的档位字段。
- **模型不承担 grounding**（决策不变；证据换成可逐条打开核对的那一组）：
  ① **精度衰减已被量化**——ScreenSpot-Pro 的分数从 ScreenSpot-v2 的 ~90% 掉到 40–60%【底稿 03 L317】。
  ② **像素路线的 grounding 错误是静默的**——DOM 点击会大声失败，像素点击不会，因此错误会一路混过校验层【底稿 03 L320】。
  ③ 所有被测模型在 SoM 下的 OSWorld-G 都 <30；且端到端原生 grounding 的跨基准方差巨大（Claude Sonnet 4.5：OSWorld-G 69.0 → ScreenSpot-Pro 35.0）【底稿 03 L361–L362】。
  ④ **我们自己的实测**——真实桌面上同一个目标，模型就是 M3.1 Flash：整屏粗定位误差 7.6 px，crop 精定位误差 0.8 px【现状·实测 §3.2】。这一条比任何官方榜天花板都更直接，因为它量的是**我们要用的那个模型**。
  另有一条口径论据：partial score 会系统性掩盖 grounding 失败（点偏了但任务部分完成也算分）。
  → **大脑用 M3.1 Flash，定位用 UIA + crop 精定位**。
- **延迟预算**：UIA 命中时**每步 0 模型调用、0 成本**；视觉兜底单次约 **5.9~16.7 秒**（思考档位=低，图片越大越慢：1568 宽约 16.7 秒、1344 宽约 13.3 秒）。默认档的对比数字不可用作"同等任务完成"的比较，因为它那一档根本没拿到坐标。
- **成本主控杆是历史截图长度，不是模型单价**：留最近 4 张完整截图会让每步输入从 3,147 涨到 9,735 token，月费从 ¥32.37 涨到 **¥91.68（×2.83）**。→ 历史用**结构摘要 + 按需截图**，只保留最近 2~4 张完整图。
- **成本口径的诚实边界**：所有月费数字都是**估算**（统一假设 6000 步/月、每步 1 张图 + 1500 文本 token + 150 输出 token），图像 token 数按各家官方公式实算但步数是假设。
- **M3.1 Flash 的成绩口径**：官方博客自评的 61.7 是 **partial score**，不是 binary 完成率，且**官方榜无该模型条目**；对外背书改用上一代 M3 的官方榜 **75.19%**。任何地方写 61.7 必须带上"partial score · 厂商自评 · 官方榜无条目"，且**不与 binary 口径并列**。
- **权重**：官方博客只说"稍后发布"且无日期，官方模型页却已称其为 open-weight；截至 2026-10-20 在模型托管平台上未找到该模型条目 → 按"未开源"处理。

### 11. 三条硬红线

以下三条是跨层硬规则，违反其一即判实现不合格：

1. **L1 → L2 的通道切换只认 coverage failure，不认任何错误**。候选不唯一（先按 §5 做消歧）、被遮挡、尺寸异常、查询超时、名称匹配不上，都**禁止**切视觉，必须走 L4 的错误处理。理由：把"切视觉"当通用兜底，会让每步都付 1.5~5 秒，架构优势全丢。
   > 📌 **2026-10-20 口径澄清（M4）**：本条的判定口径以**候选集空不空**为准——**候选集为空 = 覆盖失败**（可切视觉），**候选集非空但选不出 = 选择失败**（禁止切视觉）。「名称匹配不上」若还有退路（控件类型条件查询）就还没到覆盖失败；退路也没有才是（见 §8 的同条澄清与工单 M4 AC 6）。
2. **换算链路必须单一来源**。缩放系数、标度、crop 偏移都只能有一个真值来源；不允许文档写一套、代码写另一套、靠注释兜住。旧项目真正的病灶不是"写死了某个缩放值"，而是**换算链路分了叉**。
3. **三段耗时 + 三类失败必须拆开埋点**。否则任务掉了不知道该改感知层、决策层还是执行层。

> 📌 **2026-10-21 口径改写（人已拍板；依据 `docs/research/blocker-resolution.md` §卡点一）**：
> 架构备忘追加的第四条同源规则（「crop 精定位必须按需触发，不能每步必做」——「兜底要罕见」）
> **作废**。现在是：**crop 精定位默认无条件执行**；**门控降级为「记录器 + 回落判据」**，**不再决定开不开**。
> **依据**：同批 42 条 ScreenSpot-Pro 抽样上，**门控开 38.1% / 2.381 次调用**，**门控关 57.1% / 2.000 次调用**
> —— 门控在**准确率与成本两个轴上同时更差**；根因是门控的触发条件（「两次独立粗定位不一致」）
> **恰好是精定位前提条件的反面**（不一致 ⇒ 粗点已偏 ⇒ 目标大概率不在 crop 窗内）。
> **保留的**是**事后几何验收**（偏离量 + zoom consistency）—— 那是**回落判据**，不是闸门。
> 「兜底要罕见」这条原则仍然成立，但它的落点是**通道切换**（§11 第 1 条）与**危险动作审批**，不是 crop 精定位。

### 12. 引用与许可纪律

- **只引用官方仓库 README 正文里的两组数**（换 harness **+19.6 分 / 步数 −53%**、代码执行 vs 同等 GUI+CLI 权限 **+6.1 分 / 步数 −14.8%**）。另一组更宽的区间**不在官方 README 正文**，要用必须先回查论文消融表并标出表号。
- **不引入 OmniParser 做实时 grounding**（架构上禁止）：其官方模型卡自报 ScreenSpot-Pro 准确率仅 39.6%，端到端 0.6~0.8 秒/帧，且许可口径混合（仓库 CC-BY-4.0、**模型权重许可待查**、检测器是 YOLOv8 导出的 ONNX 而其自身许可未记录）→ 闭源商用前必须逐项核许可。
  > 📌 **2026-10-22 待澄清（本轮拍板第 3 条）**：这条禁的是「**当实时 grounding 主链**」，**不禁**「候选源里的**低频像素级预筛**」。
  > 但**本轮不引入任何像素级检测器** —— 只做「**UIA 主表 + OCR 附加表 + IoU 0.1**」的合并
  > （**那是算法规则，不是那个模型**）。
  > **待办（未拍板）**：候选源能不能接像素级预筛（UFO² 的 `clip-ViT-B-32`，`CONTROL_FILTER_TOP_K_ICON: 15`，
  > 88 M 参数、CPU 可跑）——**本轮不做**，留作 spec §12 的一处澄清待办。
- **可商用许可已核清**：UFO、winapp CLI、mcp-windows（MIT）、Playwright MCP、OpenGCUA（Apache-2.0）、pywinauto（BSD-3）。
- **copyright / 闭源组件不进主链路**：copyleft 许可的自动热键与自动化平台、闭源商业自动化工具。
- **评分是人工评分不是实测分**：方案对比里的 0~10 分只能用来排序，不能当"这个方案有多强"读；同一行里的"官方榜分数"才是实测/自报量纲，两者不可混读。
- **部分方案的数字在底稿里完全查不到**（双打分表的 59 个方案中有 16 个块），只作选型线索，不作验收依据。

### 13. 首批目标应用

**Windows 设置 → Chrome（BOSS 直聘页）→ 微信 → DSH / Tabbit（Electron）→ cc-switch**。

选这五个是为了**覆盖四种不同的可访问性形态**：Windows 设置是 XAML island（**树全空**，走纯视觉路径）、Chrome 是 Chromium（**扁平树**，精确交互走 DOM/CDP）、微信是**树被门控**（需解开后重试）、DSH/Tabbit 是 Electron（**扁平树**且可能收不到键盘事件）、cc-switch 是原生窗口（**完整树**）。

## Testing Decisions

### 1. 唯一的测试缝：动作执行缝

**位置**：感知/决策 与 真实世界 之间的一条线。缝以上是任务循环、**决策层（L3）**、校验与反思层、安全审批、动作日志；缝以下是抓屏、DPI 感知、输入注入、控件树查询、模型 HTTP 调用——**全部注入假实现**。
> 📌 **正式名称**：这条缝是本项目**唯一的测试缝**，叫**动作执行缝**。**决策层（L3）不在缝内**——模型的规划能力由端到端评测负责，不进单测。

**端口形状**：

```
输入：目标描述（自然语言）
    + 一帧截图（物理像素）
    + 可选的控件树快照
输出：动作（种类 + 物理像素坐标 + 修饰键/文本参数）
    + 最终落点 + 意图
    （窄返回类型）
```

**为什么缝定在这里**：这是唯一一条不打真桌面、不花钱、又能覆盖标定唯一性、裁剪源、裁剪门控、树脱敏这四条红线的缝。这四条红线全部落在感知到执行的范围内。若把缝抬到任务级，决策层与模型也进缝内，就必须把模型和整个循环一起假造一遍——那是在测假模型而不是测系统，还要额外维护一套假循环与假重试。

**代价（明确承担）**：决策层（模型规划）**没有单测覆盖**。分工是——**单测负责感知到校验各层的确定性行为，端到端评测负责全链路**。两层分工写在本节，不假装单测能覆盖规划质量。

### 2. 只测外部行为的标准

- **只断言契约字段，不断言内部算法**。
  - **允许断言**：最终落点必须落在被选中的控件候选框内；**K 轮独立问的 96 px 方块命中率低于命中率下限（0.6）**时，追踪记录必须标记视觉通道不可用；**落点等价族的分歧都在落点等价容差（4 px）内且命中率达标**时，追踪记录必须标记落点等价（不标记通道不可用）；**精定位失败或偏离过大时追踪记录里必须有回落与回落原因**（门控降级为记录器后，精定位默认无条件执行，**不再有「门控未触发 → 没有裁剪记录」这条断言**）；追踪记录里不得出现密码字段的值；动作序列与时序符合协议；越界时报错而不是夹取；脱敏后送模型的文本不含密钥模式；同一动作哈希连续 3 次且帧无变化时强制换策略。
  - **不允许断言**：必须用某一种缩放算法、必须先取整数倍裁剪、必须按某顺序调用某几个函数、内部数据结构的长相。
- **追踪记录走可注入的旁路 sink，不进主返回类型**。主返回保持窄（动作 + 最终落点 + 意图）；追踪是**观测数据，不是控制流数据**——这样以后换定位后端（从树换成纯视觉）时，上层调用方不用改。
- **追踪记录的内容**：控件候选集、被选中项、**标度判定（唯一命中 / 多解）与落点等价族**、粗定位点、裁剪计划、最终落点、三段耗时、三类失败类型。

### 3. 假实现清单

| 假实现 | 替掉什么 | 注入点 |
|---|---|---|
| 假截图源 | 真实抓屏 | 产出固定帧（含已知物理尺寸的合成图） |
| 假控件树 | 真实控件树查询 | 产出预设的候选集与包围盒（含"0 节点""同名多候选""超时"三种边界态） |
| 假输入注入 | 真实输入注入 | 记录注入序列与时序，供断言 |
| 假模型响应 | 真实模型 HTTP 调用 | 返回预置的坐标/动作/思考档位；可预置"思考吃光预算导致无输出"的失败形态 |

**所有测试都不需要真桌面、不需要 API key、不产生任何费用。**

### 4. 被测模块

坐标适配器（各层换算与越界判定）、标定探针（量纲判定、标度判定与落点等价、落盘）、裁剪精定位器（窗口计划、门控、回退、映射回物理像素）、树通道（候选选择、消歧、唯一性拒绝、重读、0 节点、超时）、视觉通道（降采样、粗点、裁剪、映射）、动作执行器（时序、键盘、滚轮换算、剪贴板备份恢复）、**动作记录（截图只落哈希不落原图）**、校验层（期望断言、无变化检测、循环熔断、停止条件）、审计日志（字段完整性、审批记录）、脱敏器（白名单、正则、密码框——只管控件树文本）、能力表（三态与缓存）。

### 5. 已有先例（直接复用，不另起炉灶）

- **坐标原型的 50 个单元测试**：测纯函数换算，**不引入任何假实现**，是更低层的补充，**不构成第二道缝**。已钉住的包括：标定容差默认值必须是 1.0 且能分开 0~999/0~1000（2560 宽探针）、窄探针在 2px 容差下静默判错这一失败模式、往返自检、裁剪边界不裁掉目标。
- **执行层自检**：一条命令跑完 5 项（DPI 感知生效、输入结构体大小与注入返回非零、截图是物理像素、按名定点查询命中、点击时序），**在真机上跑**，是设备层的实测回归。
- **4 个实测脚本**：文本调用、真实探针图像 grounding、真实桌面两级 grounding、思考档位与延迟对照。它们**真调 API**，属于集成回归，不属于单测缝。

### 6. 端到端评测（覆盖全链路）

- **与 5 个现成基线同表跑 ScreenSpot-Pro**：**三臂同批可对比**（门控记录器 / 无条件两段式 / **只用粗定位**基线）；门控埋点（命中原因 / 不可判定项）与**回落率**有统计。⚠️ 门控已降级为记录器 → 硬判据不再是「门控开 ≥ 门控关」（降级后两臂**行为相同**，那条判据恒成立），而是「**无条件两段式 ≥ 只用粗定位**」这条**真正能区分出精定位有没有用**的判据。
- **真实任务回放**：覆盖首批目标应用的端到端流程。
- **端到端评测负责单测不覆盖的部分**：规划质量、跨应用流程、失败恢复的真实表现。

## Out of Scope

- **控制 UAC 安全桌面**。安全桌面无法截图、无法注入输入、控件树枚举不到，这是 Windows 的硬边界不是缺陷。本项目的处理是检测到提权场景时**零动作下发并交人**；**降低系统提权安全级别**（关闭安全桌面提示）属于本 spec 范围外，且必须由用户书面同意才能开启——默认永不开启。
- **全盘录制回放**。不做"录一段屏幕再回放"式的动作重放；回放能力只保留为**动作日志**层面的可回溯。
- **自研 grounding 模型**。不训练、不微调定位模型，也不把 OmniParser 之类检测器放进逐步动作链（许可未核清 + 精度不够）。
- **跨平台**。仅支持 Windows。不做 Linux / macOS 的移植与适配。
- **多显示器热插拔**。支持多屏的坐标与归一化语义，但**不支持运行期热插拔显示器**（不处理运行中插拔导致的分辨率/DPI 变化与重标定）。
- **替代人工完成最终提交**。支付、发消息、删除这类不可逆动作永远需要人工确认，agent 不得自行越过。
- **闭源商业组件**。不引入 copyleft 或闭源商业自动化组件进主链路。
- **多用户 / 远程桌面 / 会话切换**下的行为保证。
- **训练专用数据管线与自建评测集**（复用现成公开基准，不自建标注体系）。

## Further Notes

### 本机已实测、可以当事实用的

- 接入配方与四个坑全部在本机跑通（详见「现状·实测」）。
- 坐标量纲实测为 **0~1000 归一化**：合成探针四角 40×40 黑块，模型输出最大值 900.00，换算回像素平均误差 0.2 px / 最大 0.2 px；真实桌面整屏降采样后同样落在 0~1000。
- 真实桌面两级 grounding：目标为任务栏「开始」按钮（67×72 px），真值取自控件树包围盒中心；首轮 **L0 3.4 px → L1 2.3 px**，复跑 **L0 7.6 px → L1 0.8 px**；两次调用延迟 8.68s / 6.66s。**两次运行 L1 都明显优于 L0，趋势稳定，但同一目标的 L0 在 3.4~7.6 px 之间浮动 → 单次数字不能当验收线，验收要用一组目标的分布。**
- 执行层自检 5 项全过：DPI 感知生效（物理 2560×1600 / 缩放 1.5 / caps 144）、输入结构体大小正确且注入返回非零、截图是物理像素、按名定点查询命中任务栏控件、点击时序达标。

### 还没测的（是"没测过"，不是"测过不行"）

1. **小图标（≤16 px）**——本轮测的目标是 67×72 px 的任务栏按钮；16 px 级图标在整屏降采样后只剩约 8~10 px，是定位的主战场。
2. **UWP 纯视觉路径**——实测控件树完全为空，必须走截图 + 视觉，但这条路径一次都没跑过。
3. **同名歧义**——"候选不唯一先做消歧、消歧不成才拒绝执行"这条规则只在文档里，尚未在真实应用上验证。
4. **中文输入**——Unicode 注入通道与剪贴板通道都没测过，输入法干扰完全未验证。

### 引用纪律（三条会被反复用到的）

1. **partial score 与 binary 成功率不并列**；厂商自评 61.7 必带口径，外部背书用官方榜的 75.19%。
2. **只引用官方仓库 README 正文里的两组 harness 增益数**；更宽的那组区间禁止引用，除非能指到论文消融表的表号。

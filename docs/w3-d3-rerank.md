# W3 d3 逐候选重排报告：调用可用性解决，判定质量是新的瓶颈

> 2026-11-04 定稿。A/B 对照（V5 的 8 条 canvas 视觉必需任务，真机）：
> 组 A = 无候选源无重排（现状），组 C = 候选源 + **逐候选 yes/no 重排**（W3 新制）。
> 原始日志：`runs/w5/group-c-d3-calls.jsonl`（客户端调用日志，20 条）、
> `runs/w5/group-c-d3-percandidate.jsonl`（逐候选判定日志，20 条）、
> `runs/w5/ab-summary.json`（汇总）。

## 一句话结论

**逐候选模式把 d3 的「调用可用性」问题解决了**（20 次调用 18 次 HTTP 200、
零超时零网关 400，判定延迟中位 619ms——对比 V4 整包模式的 8 次里 3 超时 +
3 网关 400 + 2 低置信）；**但「判定质量」成为新的瓶颈**：18 个有效判定里
yes 概率全部 0.008~0.381（中位 0.081），**全部低于 0.6 阈值 → fail-closed
拒绝**——C 组 0/8，与 V4 的 C 组同分，但失败原因从「调用不可用」变成了
「模型明确说不」。对照组 A 同批 8/8（2 次视觉调用/任务）。

## 逐候选判定拆账（20 次调用）

* **HTTP 200**：18 次（90%）；其余 2 次失败 → 该任务降级为启发式 top1
  （`rerank_unavailable`，W3.6 的降级路径按设计工作）；
* **yes 概率分布**：min 0.008 / 中位 0.081 / max 0.381 —— **没有一次接近
  0.6 阈值**；18 个有效判定**全部** `low_confidence` → 不点（fail-closed）；
* **零 429**；判定延迟中位 619ms（单题小而快，与整包模式 120s 超时形成对照）；
* 候选序号 1~3 都被问到（K=3 截断生效）。

## 读法与定性

1. **W3.1~W3.5 的机制目标全部兑现**：调用形状（noul）、K 截断、fail-closed
   阈值、永不输出坐标（落点取候选框中心）、结构化逐候选日志——全部按设计
   工作，且有 31 个单测覆盖。
2. **降级语义（W3.6）按设计工作**：2 次调用失败的任务没有整条失败，而是
   落到启发式 top1（但 canvas 场景的启发式匹配不到画布内容 → top1 是任意
   候选 → 仍 miss）。
3. **瓶颈转移到判定质量**：d3 对「画布里写着『乙』的深蓝色按钮」这类
   canvas 提议候选**明确回答「不是目标」**（yes ≈ 0.08）。候选描述来自
   检测器/图标提议的**同质化标签**（V6 的结论在逐候选模式下依旧成立：
   d3 的可用性取决于候选描述的信息量）——这是候选源与 d3 之间的**语义
   落差**，不是重排机制的问题。
4. **闸门兑现为「不点」是正确行为**：C 组全部失败但**零错误点击**——
   与「宁可不点也不点错」的设计口径一致。

## 对后续的建议

* 逐候选机制保留（调用层已可靠）；要让 d3 在 canvas 类任务上有正贡献，
  先解决**候选描述的信息量**（检测器标签 → 富描述），否则 d3 只会持续
  说「不」；
* 在 UIA 候选**有真文字**的场景（正是候选源的主战场），逐候选判定是否
  有判别力，值得在候选描述有区分度的任务上再测一轮——本轮 canvas 任务的
  候选描述天然无区分度，是 d3 最不利的场景。

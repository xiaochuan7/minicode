## 2. 方案 B 的组成（拼装 + 自建两个缺口）

**一句话**：不重写、也不直接用别人的成品，而是**拼装成熟骨架 + 只补两件别人没有的东西**。
依据：2026 年的胜负手在 harness 而不在 checkpoint（OpenGCUA 同一批 8 个模型只换 harness，OSWorld-v2 平均部分分 **45.3→64.9**，步数 **−53%**）。

### 复用（不自己写）

| 角色 | 选型 | 说明 |
|---|---|---|
| **骨架** | `microsoft/UFO`（MIT，Windows 原生） | UIA + Win32/WinCOM/MCP 混合动作空间；坐标系天然就是 UIA 物理像素 |
| **UIA 通道** | `Windows-MCP` / `sbroenne/mcp-windows` / 微软 `winapp CLI` | ⚠️ 接入前必须按架构备忘 §1.5 自查坐标空间（Windows-MCP 有过物理/逻辑坐标混用的 bug） |
| **浏览器那一半** | `microsoft/playwright-mcp` | 走 DOM/CDP，不碰像素 |
| **大脑** | **MiniMax M3.1 Flash**（`minimax-m3.1-flash-free`） | ✅ **可编程 API 已实测可用**（zen 通道 HTTP 200，见 `docs/01-现状.md`）；原生多模态、1M 上下文 |

### 自建（两个缺口，别的地方没有）

1. **两级 grounding 的 crop 精定位回路** —— 全行业只有 Anthropic 把 zoom 做进了官方协议。
   - 现成可抄：`ScreenSpot-Pro-GUI-Grounding` 自带 5 个 coarse-to-fine 实现，形状与本方案完全一致（整屏 → 粗 bbox 中心裁 → crop 内第 2 遍 → 映射回全图）。

   - ⚠️ 必须**按需触发**（无条件做 crop 实测反而更差：ScreenSpot 上整体 −0.3pp）。
2. **校验 / 反思层** —— expect 断言、无变化检测、循环熔断、**三段耗时埋点**。

## 3. 坐标契约（三层，**不许混用**）

```
模型空间          相对空间          截图像素            物理表面空间 ★唯一真值
0~1000 归一化  →  [0,1]×[0,1]  →  截图的像素    →  物理像素 + 虚拟桌面原点
（量纲由运行时标定决定，代码里不写死）
```

| 规则 | 内容 |
|---|---|
| **唯一真值** | **物理像素 × 虚拟桌面原点**。模型坐标永远留在 frame 内（正数），负坐标只存在于执行层 |
| **模型端量纲** | 实测为 **0~1000 归一化**（`docs/01-现状.md` §3.1），但**分母不得写死在代码里** —— 由运行时标定探针决定 |
| **工程端** | 全程物理像素。DPI 感知之后**整套换算里不需要出现缩放系数**；`capture_to_physical_scale` 默认 1.0，非 1.0 必须打警告 |
| **crop 契约** | **crop 内坐标 + 原点偏移**（本方案）。⚠️ 不是 Anthropic 那套"模型在放大图里仍报整屏坐标" —— M3.1 Flash 没被训过那套，混用必错 |
| **落点产生位置** | 整屏归一化坐标只用来"选哪块区域"，**永远不直接点击**；**视觉通道内**最终落点只在 crop 尺度上产生，**UIA 通道的落点直接取控件框的物理像素中心**（不经过 crop） |
| **门控未命中时的例外**（M7） | **门控开**时，命中门控 → crop 精定位 → 落点在 crop 尺度上产生；**不命中** → 直接拿**整屏粗定位点**落点（省一次模型调用）。**这是上条规则的一条例外**，只在这一条路径上成立：门控关（`always`）、精定位失败**回落**、粗定位为空/越界时的**整屏第二遍**成功，情况同上 |
| **换算实现** | `src/minicode/coord/coordinates.py`（`CoordinateAdapter`）与 `crop_refine.py`（`CropRefiner`），50 个单测全绿 |

## 4. 三条红线（架构备忘 §2.5「三条跨层硬规则」）

> 这三条是**硬规则**，不是注意事项。实现时最容易做错的就是它们。

**① L1（UIA）→ L2（视觉）的切换只认「coverage failure」，不认「任何错误」。**
> coverage failure = UIA **产不出任何候选**（无 provider / 树被门控 / 目标不在树里）。
> 候选不唯一（先做**消歧**：在 UIA 候选集内让模型只做指认，候选唯一时零模型调用）、被遮挡、尺寸异常、树读取超时、名称匹配不上 —— 这些**禁止切视觉**，必须走 L4 的错误处理。
> 理由：把"切视觉"当通用兜底，会让每步都付 1.5~5 秒，架构优势全丢。

**② 换算链路必须单一来源。**
> 缩放系数、标度、crop 偏移都只能有**一个**真值来源。旧项目在文档里写 `physicalX = pixelX / dpiScale`、
> 代码里故意不换算、靠注释兜住 —— 这类分叉会让文档与代码各说各话。§1.3 的换算式与 §1.4 的标定值
> 必须是**同一个对象的两个方法**。

**③ 三段耗时 + 三类失败必须拆开埋点。**
> 三段耗时：定位（UIA 查 / 视觉推理）｜决策（模型）｜执行+校验（动作+截图+断言）。
> 三类失败：定位失败 ｜决策失败 ｜执行失败。每步日志必须同时记这三项。
> 理由：旧项目缺这个埋点，"调了半年不知道该改哪一层"。

> 📌 架构备忘后续**追加了第 4 条**（§2.5 ④）：**crop 精定位必须按需触发，不能每步必做**。
> 它与 ① 同源 —— 两者都在说"**兜底要罕见**"。

## 6.2 M1 模型客户端（2026-10-20 新增）

业务代码落在 **`src/minicode/model/`**（新目录，纯标准库，不动三个冻结原型）：

| 模块 | 作用 |
|---|---|
| `config.py` | **凭据的唯一来源**：仓库 `.env` 的六项（端点/密钥/模型/会话标识/两个必需头）；缺项或为空 → 显式报错点名；免费档通道（`/go` 后缀）是**可测的规则** |
| `effort.py` | 思考档位五档枚举 `low/medium/high/xhigh/max`（缺省即最高，所以**省略即报错**） |
| `client.py` | 模型客户端：请求构造（纯函数）+ 响应解析；模型侧错误如实回传；**HTTP 200 但没有文本输出 → 显式失败**；坐标**原样透传**（不乘分母、不猜量纲） |
| `request_log.py` | 请求日志：每条请求一条（档位/模型/端点/HTTP 状态/耗时/输入输出 token/思考 token），JSONL 落盘 |
| `fakes.py` | 假模型响应，含「**思考吃光预算导致无输出**」的失败形态（供单测在动作执行缝上用） |
| `regressions.py` | **四个坑的真调 API 集成回归**（单独入口：`python -m minicode.model.regressions`；不被单测命令带跑） |

**实测结论（2026-10-20，与工单假设有出入，详见 `docs/01-现状.md` §2）**：
坑① 去掉 `user-agent` → **HTTP 403**（响应体是 Cloudflare `Error 1010`，「1010」是错误编号不是状态码）；
去掉 `x-opencode-client` → **HTTP 200，服务端已不再强制这个头**（此前「两个头都必须」从未被单独测过）。
坑②③④ 三条与工单一致（FreeTierError / HTTP 400 invalid_request_error / 思考链吃光预算 → 没有文本输出）。

| `report.py` | **脱敏计数**：密码框替换数 / 正则命中数 / 丢弃正文类字段数 / 输出长度（+ 一个 fail-closed 的丢弃字段计数） |

缝内接线（`src/minicode/action/`）：动作执行缝多一个 `model_context_config` 注入点
（**不是回调**——缝自己持有脱敏器 → 模型侧文本没有第二个出口）；
**缺省 = 这条通道不把控件树送模型**（零模型调用的通道不受影响）。
追踪记录里带一份**已脱敏**的模型侧视图与脱敏计数；追踪记录里的**值**不落（密码框留占位符）。

**四条与工单假设不同的现实（2026-10-20）**：

1. **冻结原型的 UIA 元素不暴露敏感属性**：`exec/uia.py` 的 `Element` 只给
   `name` / `automation_id` / `class_name` / `rect` / `control_type` 等，
   **没有 `Value` / `IsPassword` / `HelpText`** —— 真机接线（UIA 通道，M3）
   必须自己读 COM 属性，否则密码框规则在真机上永远不触发。
2. **控件名与控件框在追踪记录里保持原值**：脱敏只改「要外发的表示」。
   值不落追踪记录（密码框留占位符，其余为空），连 `repr` 都不带值；
   **控件名里的密钥明文仍会进日志**（落盘前的日志清洗是 M17 的活）。
3. **正文类控件的判定用类型子串**（`edit` / `document` / `text`），
   不是枚举查表——真机上的类型名带厂商后缀（`RichEdit`、`Document2`）时也能命中。
4. **工单的「配置层」此前没有对应的仓库配置项**：仓库唯一配置源是
   `model/config.py` 装载的 `.env`；本轮补了两个**可选**键
   （`MINICODE_SEND_TREE_TO_MODEL` / `MINICODE_REDACTION_ENABLED`），缺省都是关（fail-closed）。

## 6.4 M3 UIA 通道（2026-10-20 新增）

业务代码落在 **`src/minicode/uia/`**（新目录，纯标准库 + ctypes COM，不动三个冻结原型）：

| 模块 | 作用 |
|---|---|
| `ports.py` | 四个端口：定点查询 / 消歧指认 / 解门控 / 可用性探测 |
| `elements.py` | **控件框的唯一读法**（按 4 个 int 读；1e-311 那种形态判成无效坐标）+ 元素身份 + 名字包含匹配 |
| `capability.py` | **能力表**：三态（usable / sparse / unavailable）+ 键「应用 + 版本」+ 静态缓存 + 退避重试 |
| `channel.py` | 通道本体：定点查询 → 丢无效候选 → 名字匹配 → 唯一 / **消歧** → **执行前重读重定位** → 落点 |
| `windows.py` | 真机适配器：COM 读 `Value` / `IsPassword` / `HelpText`（冻结原型不暴露）、~5s 超时、Invoke 优先、能力探测 |
| `fakes.py` | 四个端口的假实现（无条件全树查询直接拒绝；每次观测重新生成元素 id） |

缝内接线（`src/minicode/action/`）：动作执行缝多两个注入点 ——
**控件定位端口**（缺省 = M0 的老路径）与 **Invoke 端口**；
定位通道自己完成「唯一性拒绝 / 消歧 / 执行前重读」，缝只负责执行与记录。
新错误码两个：`too_many_candidates`（候选超上限）、`relocate_failed`（重定位失败），
两者都归「**定位失败**」（M4 又加了 `channel_disabled` 与 `invalid_target`，见 §6.6）。

**真机实测（2026-10-20，一条命令）**：

```
$env:PYTHONPATH="src"; python -m minicode.uia --target "开始" --window Shell_TrayWnd --out runs
窗口锚点：hwnd=263062 应用=explorer.exe 版本=10.0.26100.9711
能力表  ：usable（递归子窗口见到可交互的 UIA ClassName，且没有同名撞车）｜探测次数=1
动作结果：ok=True 落点=(1049, 1564)
定点查询：最近一次 31.2 ms（要求 < 1000 ms）
三段耗时：定位=180.4ms 决策=0.0ms 执行+校验=131.5ms
说明    ：控件不支持 Invoke，改用坐标点击
落点复验：与控件框中心偏差 0.0 px（要求 ≤2）｜落点落在控件框内=True
```

> 「候选上限 / 允许切视觉 / 每步回显」三行；上面的方框是 **M3 当时的真实输出**，
> M4 之后的输出见 §6.6。

**五条与工单假设不同的现实（2026-10-20）**：

1. **`IsPassword` 的属性 ID 不是 30043** —— 照抄来的 30043 读出来**恒为 True**
   （那是别的布尔属性），会让**所有控件都被当成密码框**。
   本机实测（临时造一个 `ES_PASSWORD` 编辑框与一个普通编辑框逐个 ID 对照）：
   **30019** 才是「密码框 True / 普通框 False」的那个。
2. **「门控解不开」与「从未可用」在真机上分不开** —— 本机 `SystemSettings.exe`
   （UWP / XAML island）的树**本来就是空的**，但因为「激活窗口」这一步也失败了，
   能力表把它记成 `gated-unlock-failed`（解开失败）而不是 `no-tree`（从未可用）。
   两种结论都判「不可用」✓，但**归因**依赖解锁动作的成败，不是独立证据
   （同一个 `cc-switch.exe` 两次探测分别被记成 `no-tree` 与 `gated-unlock-failed`）。
3. **同名撞车必须去重** —— 递归子窗口时，同一个元素会**同时**出现在父窗口与
   子窗口的子树里；不去重会把「同名撞车」数虚（未去重时任务栏数出 34 处，
   去重后 0 处 —— 任务栏因此从 sparse 变回 usable）。
4. **冻结原型的 `Element` 不暴露值类属性** —— 只能取它的原始 COM 指针
   （`element._ptr`）自己读 `GetCurrentPropertyValue`（vtable 下标 **10**，
   由冻结原型记着的 `FindFirst=5` / `FindAll=6` / `GetCurrentPattern=16` 自洽推出）。
5. **冻结原型的 AND 条件路径在本机崩** —— `build_condition()` 在**两个条件并存**
   时走 `CreateAndCondition`，本机实测抛 access violation（进程直接挂）。
   → M3 的查询一律用**单条件**查询 + Python 侧的名字过滤
   （自动化标识 → 精确名字 → 控件类型，前者查不到才退到后者）。

## 6.5 M21 动作协议缺口（2026-10-20 新增）

改动落在 **`src/minicode/action/`**（不动三个冻结原型）：动作种类集合收敛到
**架构决策备忘 §3 的 12 个**，并补齐 `screenshot` 与 `wait`。

| 模块 | 改动 |
|---|---|
| `protocol.py` | `ActionKind` = 12 个（`screenshot`/`wait` 补齐、`double_click`/`right_click` 删掉、`type_text` 改名 `type`）；`click` 的参数 `button`（1/3）与 `click_count`（1/2），**协议层是这两个参数的唯一读法**（`parse_click_params`）；`ActionResult` 加 `captured`（观察到的帧，**只落摘要**） |
| `ports.py` | 两个**新**端口：`ScreenshotPort`（抓一帧，region 可选）/ `RegionCaptureSource`（能抓指定区域） |
| `capture.py`（新） | `CapturePort`：把若干截图源接成**一个**截图端口（整屏 / 区域；跳过只拿到 0×0 画面的源）——缝内唯一的抓屏入口 |
| `executor.py` | `click` 按参数分流（左键/右键/双击）；`screenshot`（走截图端口）与 `wait`（走可注入的 sleeper）两个新动作 |
| `seam.py` | `run()` 新增截图/等待的独立分支（这两个动作没有最终落点，但**返回形状一致**）；点击的意图动词由参数决定；**region 越界不夹取**（报 `clipped_by_desktop`） |
| `records.py` | 动作记录新增 `params`（**输入文本的正文不落**）；追踪记录的帧字段收成 `frame_fields()` |
| `geometry.py` | 新增 `rect_size()`：**矩形 → 尺寸的换算只有一份**（`right-left` / `bottom-top`）；`VirtualDesktop.contains_rect()` |
| `fakes.py` / `windows.py` | 假截图源支持区域抓取；真机适配器按冻结原型的 `capture.grab_frame((left, top, width, height))` 抓区域 |

**防漂移闸门**：`test_action_protocol.py` 里逐字抄了架构备忘 §3 的 12 个名字，
断言「协议的动作种类集合 == 那 12 个」——多一个或少一个都判失败。

**协议版本口径**：**只增不改**地在 v1 上加字段（如 `ActionResult.captured`）**不升版本**；
**改已有字段的含义或删字段**才升版本。

**真机核对（2026-10-20，按 `.scratch/desktop.lock` 拿锁 → 跑 → 释放；只抓屏、零注入）**：

```
整屏：2560x1600 left=0 top=0 backend=mss
区域 (100, 200, 500, 600)：400x400 left=100 top=200 backend=mss source=region
```

→ 真机适配器里 `(left, top, right, bottom)` → `(left, top, width, height)` 的换算正确。

**七条与工单假设不同的现实（2026-10-20）**：

1. **工单说「M0 已接线 12 个里的 10 个，只缺 `screenshot` 与 `wait`」——实际不止缺两个。**
   M0 的动作种类集合与架构备忘 §3 **对不上**：多出 `double_click` / `right_click`
   两种（它们后来被收敛成 `click` 的参数），`type` 当时叫 `type_text`。
   本轮实际动的是**三处**：补 2 种、删 2 种、改 1 个名字。
2. **端口的形状不许变** —— 区域截图塞不进既有的 `CaptureSource.capture()`（无参）。
   本轮**新增**两个端口而不是改既有端口的形状（`CONTEXT.md` 的端口条款）。
3. **动作记录原来不带参数** —— 双击与两次单击原先靠**动作种类**区分。
   收敛成 `click` 的参数后，记录必须带上参数才仍能区分（`click_count=2` vs 缺省）。
4. **`button` 的 1/3 是协议自己的口径**，不是 Win32 的 `MK_*` 标志位
   （Win32 的右键是 `MK_RBUTTON=2`）。按工单写死为 1 = 左键、3 = 右键。
5. **截图与等待没有最终落点** —— 缝原本只接受「需要一个落点的动作种类」。
   本轮把它们单列成一类（`STANDALONE_KINDS`），落点为 `None`，
   但**返回形状与既有动作一致**（动作 + 落点 + 意图 + 结果），同样产出恰好一条记录。
6. **真机区域抓取的矩形口径与冻结原型不同** —— 冻结原型的 `capture.grab_frame` 收的是
   `(left, top, width, height)`，本项目的矩形一律是 `(left, top, right, bottom)`；
   换算收到 `geometry.rect_size()` 一处。
7. **协议版本口径原先写死了「不在 v1 上加字段」** —— 与本轮给 `ActionResult` 加 `captured`
   冲突；口径已改成「只增不改不升版本」。

## 6.6 M4 候选选择（2026-10-20 新增）

改动落在 **`src/minicode/uia/`** 与 **`src/minicode/action/`**（不动三个冻结原型）：
**模型只负责「选」，不负责「瞄」** —— 消歧请求里只有「从候选清单里选哪一个」
这一项任务，落点始终来自**控件框的物理像素中心**。

| 模块 | 改动 |
|---|---|
| `uia/pointer.py`（新） | **消歧指认**：`ModelCandidatePointer`（接模型客户端端口）；提示词只问「行号」；**行号 → 元素 id 的映射在本地做**；`parse_chosen_numbers()` 是模型回答的**唯一**读法 |
| `uia/channel.py` | **脱敏闸门**（脱敏没上线 → 通道被拒绝启用、零模型调用）；**失败分类**（覆盖失败 / 选择失败 / 通道被拒绝启用，标识不同）；**允许切视觉**标记（只有覆盖失败为真）；**候选数上限**与其来源进结果；**重定位**改成「身份族 + 离原位置最近」 |
| `uia/ports.py` | `PointerRequest` 加 `frame`（送模型当上下文）；`PointerResult` 加 `echo`（每步回显） |
| `action/ports.py` | 新类型 `SelectionEcho`（**每步回显**：选择结果 + 实际发送图片尺寸，**不含坐标**）；`LocateRequest` 加 `frame`；`LocateResult` 加 `selection_echo` / `allows_visual_fallback` / `candidate_limit` / `candidate_limit_source`；`CapturedFrame` 加 `pixel_format` |
| `action/image.py`（新） | **帧 → PNG**（**纯标准库**：zlib + 通道交换），`encode_frame_base64()` 是送模型那张图的唯一编码处 |
| `action/records.py` | 追踪记录与动作记录带 `selection_echo` / `allows_visual_fallback` / `candidate_limit` / `candidate_limit_source` |
| `action/seam.py` | 把那一帧**传进定位**；定位结果里的回显、标记与上限**进追踪记录**（主返回类型不变） |
| `action/errors.py` | 新错误码 `channel_disabled`（**通道被拒绝启用**：硬闸门拦下，如脱敏未上线） |
| `action/windows.py` | 真机抓屏标出像素排布（`bgr` / `bgra`），编 PNG 时不把颜色弄反 |
| `uia/__main__.py` | CLI 加 `--disambiguate`（接上模型做消歧；凭据与两个脱敏开关**只从仓库 `.env` 读**） |

**两类失败的判定口径（已同步进 spec / 架构备忘 §2.5 ① / ADR-0004）**：

| 情形 | 判定 | 允许切视觉 | 错误码 |
|---|---|---|---|
| 候选集为空（0 节点 / 目标不在树里） | **覆盖失败** | ✅ 是 | `target_not_found` / `locate_failed` |
| 候选集非空但选不出（消歧失败 / 超上限 / 重定位失败） | **选择失败** | ❌ 否 | `ambiguous_target` / `too_many_candidates` / `relocate_failed` |
| 脱敏没上线 | **通道被拒绝启用**（策略拒绝，不是找不到） | ❌ 否 | `channel_disabled` |

**真机消歧（2026-10-20，按 `.scratch/desktop.lock` 拿锁 → 跑 → 释放）**：

```
应用：explorer.exe 10.0.26100.9711（窗口锚定查询）
同名候选：7 个「同名文件夹」（面包屑 + 标签 + 内容区），能力表 sparse（同名撞车 11 处）
消歧请求：模型只答行号 → 回显 模型选择=[2] 名字=['同名文件夹'] 实际发送图片尺寸=2560x1600
落点：(606, 269) = 被选中候选（TabItem 框 420,245,792,293）的中心
落点复验：与控件框中心偏差 0.0 px（要求 ≤2）｜落点落在控件框内=True
模型请求：effort=low，HTTP 200，输入 3805 token，耗时 5745 ms（请求日志一条）
```

**候选数上限的真机核对**：13 个同名候选 > 上限 8 → `too_many_candidates`，
**模型调用 0 次**（请求日志没有新条目）、**零输入注入**、回报 13 个候选。

**八条与工单假设不同的现实（2026-10-20）**：

1. **端口形状不许变 vs 消歧必须送画面** —— `LocateRequest` / `PointerRequest` 都得带上那一帧，
   否则模型看不到「哪个是哪个」。本轮**只加字段、给默认值**（既有实现照旧能用），
   没改任何既有字段的含义（协议版本口径：只增不改不升版本）。
2. **脱敏没上线原本报的是「选择失败」** —— 那是**假话**（模型压根没被问）。
   按工单 M4 AC 7 改成**明确拒绝启用**（新错误码 `channel_disabled`），
   M3 的那条单测随之改了断言。
3. **M3 的重定位靠「身份 + 位置重叠」，与 M4 AC 8「控件移动过也要用新框」互斥** ——
   位置重叠判据会把「移动过的那个」判成重定位失败。本轮改成
   **身份族 + 离原位置最近**：族里个数变了（控件没了 / 多了一个同名）→ 认不准 → 拒绝动作。
   ⚠️ 残留的固有歧义：同名同型且**没有 AutomationId** 的控件被「换掉」时，
   移动与替换在信息上不可分（本轮按 AC 8 选了「移动 → 用新框」这一侧）。
4. **帧的像素排布不是固定的** —— 抓屏后端有 numpy 时给 **BGR**（3 字节/像素），
   没有 numpy 时给 **BGRA**（4 字节/像素）；编 PNG 前必须分清，否则颜色是反的
   （`CapturedFrame.pixel_format`）。
5. **「名称匹配不上」在架构备忘里与 coverage failure 的定义互斥**（两处字面打架）：
   实现按**候选集空不空**判（空 = 覆盖失败），并已把这条口径写进
   `docs/spec.md`、架构决策备忘 §2.5 ① 与 ADR-0004，文档与实现不再互斥。
6. **回显口径原先只写了坐标** —— 架构备忘 §3 与规格 §7 都写「每步回显模型自己发出的**坐标**」，
   但 UIA 通道的消歧模型不产坐标。两处已改成「模型发出的内容（坐标或选中项）+ 实际发送尺寸」。
7. **模型调用的 token 预算不能太小** —— `max_tokens=512` 时真机直接吃了**坑③**
   （「HTTP 200 但没有文本输出：思考链把预算吃光」）。已提到 **2000**；
   并且**模型侧失败不再抛穿整条链路**——通道把它变成**选择失败**（错误如实写进消息），零动作下发。
8. **真机上「同名候选」可能落在别的窗口底下** —— 缝的**遮挡判定**（M0 的老逻辑）会先拒绝执行
   （报「目标窗口置前失败」），动作不下发。这是既有行为，本轮只记录。

**八条与工单假设不同的现实（2026-10-20）**：

1. **服务端会把大图缩小** —— M1 的口径「取实际发出的那张图的宽高」当绝对像素候选的基准，
   在本机**不成立**：MiniMax 端点把 2560×1600 的图缩到约 **2048×1280** 再喂给模型，
   模型回的绝对像素落在**缩小后那张图**上。按发送尺寸当基准 → 误差 **571.79 px**；
   把缩小后的尺寸声明进来（`--model-input`，量出来的、不是猜的）→ 判定标度从
   `absolute_capture` 变成 `absolute_model_input`，误差降到 **2.66 px**。
   → 绝对像素候选的基准是「**模型实际看到的那张图**」，不是「我们发出去的那张」。
2. **1 px 的标定容差对真 VLM 不可达** —— 即使基准改对，模型自己在 2560 宽画面上的定位误差是
   **2.66 ~ 27.19 px**（同一探针两次真调，差异来自模型本身），远超 1 px 容差 →
   按工单 M5 AC 9 如实记为**标定失败**（视觉通道不可用），**没有放宽判定容差**。
   后果：**本机当前的视觉通道是「不可用」的**；M6/M7 要么把探针目标做大、
   要么改用别的容差口径 —— 那是后票的活，本轮不擅自改口径。
3. **文本路径的标定能过，但它测的不是图像 grounding** —— 文本路径没有画面，
   模型是把「离右边 64 像素」算成绝对像素（2448）答的，因此它测出的是模型在
   **纯文本**上下文里的坐标习惯（`absolute_capture`，0.00 px）。
   它**不能**替代图像路径的标定，两条路径的分母仍然各自独立。
4. **工单 AC 2 的两条断言与「1× 容差」判据互斥** —— AC 2 要求
   「2560 宽 + 容差 2.0 → 0~999 进等价列表」与「1280 宽 + 容差 1.0 → 判为等价」，
   而两处的真实分歧是 **2.87 px**（2560 宽）与 **1.43 px**（1280 宽）——
   按「分歧 ≤ 容差」的 1× 判据，两条都判**不等价**（2.87 > 2.0、1.43 > 1.0），AC 2 必然失败。
   实现改用**可分辨安全系数 2.0**（分歧 ≥ 2× 容差 才算探针能分辨）：
   2.87 < 4.0 ✓、1.43 < 2.0 ✓，两条断言都成立；
   真实配置（2560 宽 + 1 px）2.87 ≥ 2.0 → 仍能分开 0~999 与 0~1000 ✓。
   这条口径已写进 `docs/tickets/README.md` 与架构决策备忘（dated 注）。
5. **AC 1 的「该点」只能是最坏点** —— 最右目标的 x 分歧在 2560 宽的探针上最多是
   2560/999 = **2.562 px**，所以「该点欧氏 ≥ 2.5 px」只有在**最坏点**（右下角，y 也大）才成立
   （2.87 px；架构备忘 §1.4 给的 2.86 px 正是这个点）；右上角那个目标的欧氏只有 2.45 px
   （y 方向几乎没差）—— 按最坏点读。
6. **等价标度列表必须含判定标度自己** —— AC 5 要求「两种绝对标度同入等价标度列表」，
   因此列表 = **{判定标度} ∪ {探针排除不掉的标度}**；「唯一命中」= 列表里只有判定标度自己。
7. **探针尺寸的唯一真值来源是启动自检量出来的物理表面尺寸**（M0 的 `GetSystemMetrics` 路径，
   PMv2 下 2560×1600），不是常量；`calib/probe.py` 里没有 1280×720 这样的默认值
   （单测逐文件扫）。
8. **目标方块的边长取 96 px（不是原型备忘里的 48 px）** —— 真 VLM 在 2048 宽的视图里
   要看得见这些方块；边长 48 px 更看不清。边长只影响「模型看不看得见」，
   不影响落点分歧（分歧由目标的**位置**决定）。

缝内接线（`src/minicode/action/`）：动作执行缝多两个注入点 ——
**视觉通道端口**（两级 grounding）与 **放大通道端口**；
追踪记录多四个字段（**粗定位点 / 裁剪计划 / 每步回显 / 回落与回落原因**）；
协议层多一类**观察型动作**（`OBSERVATION_KINDS`：放大不注入任何输入）。

**坐标契约（两条，不许混用）**：

| | 裁剪（两级定位内部） | 放大（动作协议里的一个动作） |
|---|---|---|
| 画面 | 从**已抓到的那一帧**上 1:1 裁 | 指定区域**回源重抓** |
| 模型回答 | **crop 内坐标** → 系统加裁剪原点偏移 | **整屏坐标** → 系统不加任何偏移 |
| 裁剪计划 | 有 | **恒为无**（`ZoomResult.crop_plan is None`） |

**真机分布回归（2026-10-20，测量台，`python -m minicode.ground`）**：

```
=== 标定（image 路径）｜探针 2560×1600｜模型输入 2048×1280 ===
判定标度：absolute_model_input｜标度判定：unique｜最大误差 2.14~22.24 px（各轮不同）
视觉通道准入：不可用 —— 标定失败：最大误差超过标定容差 1.0 px
=== 目标（17 个，来自 explorer.exe 的 UIA 树；其中 ≤16 逻辑 px 的小图标 3 个）===
粗定位：N=17 中位数=13.53~38.55 px p90=50.62~70.53 px
精定位：N=17 中位数=5.83~9.15 px  p90=51.48~202.01 px
判定：精定位分布不劣于粗定位（三轮里两轮达标，一轮 p90 被离群点拉高 —— 见下）
```

**九条与工单假设不符的现实（2026-10-20）**：

1. **工单 AC 3 写「模型在 crop 内报 0~1000 归一化的坐标」，本机模型报的是绝对像素** ——
   标定探针（提示词**不许带量纲暗示**）判出的标度是 `absolute_model_input`，
   生产提示词同样不带量纲 → 约定一致，换算走同一条链路。**契约本身（crop 内坐标 + 原点偏移）不受影响**，
   实现是**标度无关**的：crop 内坐标按标定出的标度解释。
2. **服务端把整屏图缩到约 2048×1280** → 整屏那一级的换算基准必须是**模型实际看到的那张图**
   （= 标定记录里的 `model_input_width/height`）；裁剪那一级默认 1:1（512×512），
   本机 token 计数佐证（精定位请求 ≈ 450 token = 图像 336 + 文本，与 512 图未被缩放一致）。
3. **1 px 标定容差对本机模型不可达** —— 五轮真调的最大误差在 **2.14 ~ 22.24 px** 之间
   （同一张探针、同一模型，波动来自模型本身）→ 按工单 M5 AC 9 如实记为**标定失败**，
   **生产路径的视觉通道仍然不可用**（M5 的硬闸门没动，也没放宽容差）。
   AC 9 的分布回归因此跑在**测量台**上（它只用标定**判出的标度**做测量，并如实报告准入判定）。
4. **粗定位那一级的精度是「图宽的百分比」** —— 整屏图（模型看到 2048 宽）上误差中位数
   13.5~38.6 px（≈0.7%~1.9% × 图宽）；裁剪图（512 宽）上同一模型的误差中位数只有 5.8~9.2 px
   （≈1.1%~1.8% × 图宽）→ **裁剪的收益就是「同一相对精度落在小得多的物理尺度上」**，
   这也是两级 grounding 值得做的原因（架构备忘 §2 自建缺口一）。
5. **精定位偶尔会在 crop 里选中「相邻的同类控件」** —— 任务栏上一排相似按钮时，
   模型可能指向邻居（实测出现过 191 px 与 283 px 的离群点）。这不是换算错，
   是模型选错目标 —— **治它的是 M7 的「结果偏离粗定位 → 回落」门控**（工单 M7 AC 3 明确要求），
   本单（无门控）不擅自加，因此**尾部跨轮次不稳定**：三轮回归里两轮达标、一轮 p90 不达标。
6. **本机 UIA 树里没有「≤16 物理 px 的有名小图标」** —— 任务栏托盘里确有 24×24 物理 px
   （= 16 逻辑 px）的小图标，但它们**没有名字**（模型没法按名字找）。
   已纳入的是**最短边 ≤16 逻辑 px** 的有名目标 3 个（`显示桌面` 12×48、
   天气文字 `19°C` / `多云` 23×16）—— 这条口径已登记进 `docs/tickets/README.md`。
7. **同一个元素在 UIA 树里会出现两次**（父窗口与子窗口各报一次）—— 按控件框去重后再判
   「同名撞车」，否则 `19°C` / `多云` 会被误判成同名而丢掉（小图标样本就少了）。
8. **「目标是否完整包含」在生产路径恒为真** —— 两级 grounding 的粗定位**只给点不给框**，
   没有半径就判不了框；裁剪计划保证的是**粗定位点完整落在窗口内**
   （`target_fully_contained` 属性按半径判定，半径是构造参数，缺省 0）。
9. **放大路径的「整屏坐标」有空间口径的坑** —— 提示词里给的区域原点必须换算到
   **模型自己的坐标系**（否则模型加的偏移与它回的坐标不同套），本实现用标定出的标度换算；
   提示词**不写**「0~1000」「归一化」这类答案单位（量纲只由标定判定）。

**门控的三个状态**（`CONTEXT.md` 的「门控」词条只说了命中/不命中）：

| 状态 | 含义 | 生产接线上的实际情况 |
|---|---|---|
| 命中 | 至少一条条件成立 → **开**第二遍精定位 | 只有「粗定位为空或越界」这条在生产上**可判定** |

**真机实测（2026-10-20，测量台，两臂各一轮；只截图、零输入注入；按 `.scratch/desktop.lock` 拿锁 → 跑 → 释放）**：

⚠️ **两臂是两次独立真调**，粗定位那一列的差异含**轮次噪声**

**九条与工单假设不符的现实（2026-10-20）**：

1. **门控在生产接线上基本是「哑」的** —— 四条条件里只有「粗定位为空或越界」
   可判定，另外三条（占比 / 置信度 / 一致性）在 17/17 个样本上都是**不可判定**：

   结果：门控开 = 只做粗定位（省一次模型调用，也丢掉精定位的收益）。
   → 要让门控真正起作用，得让粗定位**额外报目标框**（改 M6 的口径 + 重测），
   这是**需要人拍板**的口径问题，本单不擅自改。
2. **本机上「门控关」比「门控开」好**（同一轮内：粗定位中位数 25.20 px →
   精定位中位数 12.50 px，p90 86.54 → 79.06 px）。这与 C-16 引用的
   ScreenSpot-Pro 证据（无条件做 crop 精定位整体 −0.3pp）**方向相反** ——
   差异很可能来自**样本集**（本机 17 个任务栏控件 vs ScreenSpot-Pro 的 1581 条）与
   **模型**（M3.1 Flash vs 论文里的 Qwen 系）。**M8 同表跑才是裁决点**。
3. **「偏离粗定位 → 回落」这条判据抓不住「粗定位本身就偏」的情形** ——
   实测有一个目标（`Everything 已固定`）粗定位偏 124.52 px，精定位偏 207.00 px
   （选中了相邻的同类控件），但两落点相距在阈值内 → **没有回落**。
   偏离判据量的是「精定位离粗定位多远」，不是「离真值多远」；粗定位本身就偏时，
   两者会同向漂移。阈值 128 px 是本单定的工程值（512 裁剪窗口边长的 1/4），
   **未验证**（M8 才能用真值调它）。
4. **工单 AC 1 说「粗定位为空或越界时开的是一次整屏重定位」，AC 3 说
   「粗定位本身为空或越界时必须报定位失败」** —— 两句只有一种读法能同时成立：
   整屏第二遍**成功**就落它的点，**失败**才报定位失败（此时没有可回落的结果）。
   本实现取的是这一读法（AC 1 否则无意义），并且那一遍**不是逐字重发**同一条
   请求（提示词里带上「上一次没能给出可用的位置」）→ 不是 AC 3 禁止的「静默重试」。
   ⚠️ 它也**不是重新感知**（用的是同一帧）—— 这是「一次定位里的第二遍」，
   不是 `CONTEXT.md` 说的动作**重试**（重试要重新感知）；真要重新感知，
   得给通道接截图口（后票）。
5. **ShowUI 的网格值是 1000，不是 999** —— 实际脚本 `main/eval_screenspot.py`
   的 `get_bbox` 写的是 `int(item * 1000)`，系统提示词也写「scaled from 1 to 1000」。
   底稿里「0–999/1000 两说」的传闻**到此为止**（已写进注释与单测）。
6. **ShowUI 的 GT bbox 也是宽高形式**（`x1, y1, w, h = bbox`）—— 与 CCF 仓
   ScreenSpot-v2 脚本一样；两家的 GT 形状相同、point 形状不同。
7. **「接了官方脚本但分数全 0」是可以自己造出来的** —— 把像素点当归一化喂给
   ScreenSpot-Pro 官方脚本，命中率**恰好是 0**（不报错）。防假象自检
   （GT 中心当预测点 → 命中率必须 ≈100%）因此是**必做项**，已落成
   `eval.formats.self_check_hit_rate`。
8. **四个目标脚本的 GT 与 point 形状是**两两独立**的** —— 不能靠「都是坐标」蒙混：
   SSPro 官方（归一化 point + xyxy bbox）、ZoomClick（像素 point + xyxy bbox）、
   CCF（像素 point + **xywh** bbox）、ShowUI（**网格** point + **xywh** bbox）。
   宽度形式当 xyxy 读会让同一个点的命中结论**反过来**（单测钉死）。
9. **门控的参数全是运行时参数，但生产上没人喂** —— 占比阈值的来源
   （ScreenSpot-Pro 的**数据集统计** 0.07%，**未验证的阈值**）已按 AC 2 标注；
   置信度与一致性阈值**当前没有可靠来源**（模型不报置信度、没做第二次粗定位），
   它们的来源串里写的是「工程阈值·未验证」。

## 6.10 M10 决策层：代码执行 harness（2026-10-20 新增）

决策层的产出形态是**一段动作程序**，不是逐条动作（ADR-0005）。改动落在
**`src/minicode/action/program.py`**（受控执行环境）与
**`src/minicode/decision/`**（新目录，决策层本体）：

| 模块 | 作用 |
|---|---|
| `action/program.py` | **受控执行环境**：动作程序只能调用动作协议暴露的动作；任意系统调用与任意文件写入**在执行前**就被静态拒绝（`import` / `open` / `eval` / `exec` / 双下划线属性 / 含双下划线的字符串常量），被拒时**零动作下发**。⚠️ **不是操作系统级隔离**（白名单 + 静态扫描挡的是「程序直接做坏事」） |
| `action/errors.py` | 新增错误码 `program_rejected`（**只加不改**，协议版本不升） |
| `action/test_action_program.py` | 受控执行环境的外部行为单测（工单 M10 AC 6） |
| `decision/harness.py` | 主循环：规划步（高档位）→ 受控执行 → **标准输出 + 新观察回灌** → 反思步（高档位）；停止条件只由 harness 侧承载 |
| `decision/api.py` | 动作程序能看到的接口（`click` / `find` / `type_text` / `press_key` / `wait` / `screenshot` / `ask_user`）—— **只有协议暴露的动作** |
| `decision/context.py` | 上下文窗口：**完整图只留最近 2~4 张**，更早的压成**结构摘要**（尺寸 + 截图哈希 + 那一轮发生了什么） |
| `decision/prompt.py` | 规划步 / 反思步的提示词 + 程序源码提取 |
| `decision/__main__.py` | **端到端评测**入口（真模型 + 假桌面），落 `decision-report.json`、`model-requests.jsonl` 与 `action-records.json`（动作记录） |

**三条硬规矩**：

| 规矩 | 落点 |
|---|---|
| **协议里没有「完成」** | 动作协议的取值集合里没有完成类动作；harness 的停止原因只有 `asked_human` 与 `max_rounds`，**不拿模型自称完成当停止判据**（只计数） |
| **思考预算（effort）显式** | 规划步 / 反思步 = `high`；**动作步**（消歧指认）在动作路径里 = `low`（`uia/pointer.py` 的 `DEFAULT_EFFORT`）；每次请求都显式给档位，请求日志逐条带档位字段 |
| **上下文成本可控** | 完整图保留张数上限 3（可配 2~4）；更早的帧压成结构摘要 |

**端到端实测（2026-10-20，真模型 M3.1 Flash + 假桌面；`python -m minicode.decision`）**：

```
=== 跑 A：目标=点开名为「开始」的控件（5 轮，保留 3 张完整图）===
token 曲线（步序, 上下文总输入 token）：3870 → 7287 → 10714 → 10799 → 11034
  ↑ 前三轮每轮 +3417 / +3427 token（= 一张 2560×1600 完整图）
  ↑ 第 4、5 轮只 +85 / +235 —— 完整图到 3 张就封顶，之后每轮只多一行结构摘要
保留 3 张｜淘汰成摘要 3 张｜档位分布 {'high': 5}｜未传档位 0
注入事件：move(140,120) → button_down → button_up（**真的走了动作执行缝**）
动作记录：10 条（1 张初始截图 + 1 次点击 + 8 张每轮截图）

=== 跑 B：目标里明写「做完打印 STATUS: DONE」（3 轮）===
token 曲线：3870 → 7242 → 10587
模型在三轮里都打印了 STATUS: DONE → 自称完成 5 次
停止原因 = max_rounds（**没有因为模型说完成而停**）
```

⚠️ **口径**：这两次跑的是**假桌面**（假截图源 / 假控件树 / 假输入注入）——
它证明的是**回路机制**（程序 → 执行 → 回灌 → 继续）与**成本曲线形状**，
**不是**任务成功率。端到端评分的活儿在 M14/M15。

**与工单假设不符的现实（2026-10-20）**：

1. **低档位也会写程序，但会猜错接口约定** —— 实测：同一提示词在 `low` 档下也给出
   带 `if/else` 的 11 行程序，但它写成 `click(located.get('point'))`（把**落点**当参数
   传给 `click`），而我们的 `click` 收的是**目标描述**。程序没崩（参数被 `str()`
   兜住，动作失败返回 `ok=false`），但这一步做的是错的事 → **提示词里的接口说明要更硬**。
2. **「一次跑完，不用每步问一次用户」在程序内部成立，但轮次之间仍有模型往返** ——
   每轮一次规划调用（`high` 档，约 2~12 s）+ 程序执行（毫秒级）。
   轮次上限（默认 4）就是**成本刹车**。
3. **模型会避免重复点击，但仍跑满轮次** —— 跑 A 的第 2 轮起模型读了自己的标准输出
   就不再点（假画面**永远不变**，它判断「已点过」），但**它没有停止**（跑满 5 轮）。
   这条说明：**停止条件不能靠模型自觉**，只能靠 harness 侧的判据（M11/M12）。
4. **「上下文不随步数线性膨胀」只在图片这一项上成立** —— 文本部分
   （结构摘要）仍然每轮线性增长；图片部分被 `keep_frames` 封顶后，每轮的边际成本
   从约 3400 token 掉到约 100~200 token。**反事实外推**（按实测每图约 3420 token）：
   若不裁剪、第 5 轮带 5 张图，上下文约 **11.0k + 2×3.4k ≈ 17.8k token**（外推值·非实测）。
   **成本主控杆是图片长度**，这条与 `CONTEXT.md` 的口径一致。
5. **模型端只收一张图这件事差点让 AC 5 落空** —— 端点**支持多图**
   （实测两张 PNG 一并发得通），但**第一次用 1×1 的非法 PNG 试时返回 400**，
   差点误判成「端点不支持多图」。模型端口因此**加了一个可选项** `images_base64`
   （**真实现与假实现同时加** —— 换注入点时端口对替身仍然一致；
   协议本身是**加字段**，不升版本）。
6. **决策层**没有单测覆盖**是明确承担的分工**（工单 AC 7），不是遗漏 ——
   但受控执行环境的契约（能不能 import / 能不能写文件）**有**单测，
   它测的是**受控执行环境本身**（协议里的 `execute_code` 动作**仍未接进执行器**）。
7. **`ask_user`（请求人工）是目前唯一的人机交回出口** —— 程序调它，harness 停止。
   工单没要求更多，但 M16 的审批闸门要落在动作下发路径上（后票）。
8. **文本与按键不产追踪记录** —— 缝的契约里这两种动作「请直接用动作执行器」，
   因此它们**没有动作记录**（点击 / 截图 / 等待有）。**已知欠账**，M11/M17 补齐。
9. **沙箱不是操作系统级隔离** —— 评审实测出一条逃逸路径
   （`"{0.__class__}".format(x)`：AST 里看不见属性节点，运行期却解析出
   `__class__`）→ **已堵**（含双下划线的字符串常量也拒）；真要把动作程序当
   不可信代码跑，得另做进程级隔离（后票）。

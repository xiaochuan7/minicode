## 0. 一句话结论

**红线落成了机器可判的规则**：错误码 → **失败类型**（覆盖 / 选择 / 执行 / 通道级）→ **允许切视觉**，
映射只有一份、红线只有一处，且 `LocateResult` 构造时就检查两者一致 —— **非覆盖失败不可能切视觉**；
真机实测在 Windows 设置上跑通了「覆盖失败 → 切视觉 → 落点 → 真点击」，落点偏差 **2.2 px / 6.7 px**（两轮），
但**验收线 ≤2 px 没有稳定达成**，且**生产路径上视觉通道此刻仍不可用**（标定没过 M5 的硬闸门，
本轮 6 次标定的误差在 **1.06 ~ 67.07 px** 之间）。

## 2. 红线是怎么落成「机器可判」的

工单的红线是三句话：**只有覆盖失败允许切视觉**；候选不唯一 / 被遮挡 / 尺寸异常 / 查询超时 / 名称匹配不上
一律走错误处理；**视觉通道的调用次数必须是 0**。本轮把它拆成三层，每层只有一处：

```
错误码（协议层，一个码一件事）
  └─ 失败类型（四个：coverage / selection / execution / channel）—— action/errors.py:146 的 FAILURE_TYPE_BY_CODE
       └─ 允许切视觉？—— action/errors.py:180 的 allows_visual_fallback（**只有 coverage 为真**）
```

**红线不可绕过**：`LocateResult.failure_type`（`action/ports.py:404`）是**唯一**的判据，
`allows_visual_fallback` 是**推导出来的属性**（`action/ports.py:425`、`action/records.py:154`、
`action/records.py:275`）—— 也就是说**没有第二份数据**可以跟它打架。
谁想给一个「选择失败」开切视觉的口子，得先改那张映射表 —— 改动会出现在 diff 里。

### 2.1 「名字没匹配上」与「目标不在树里」怎么分开

这是本轮最需要说清楚的一处：工单把「名称匹配不上」列进**禁止切视觉**，
而 README 的口径说「名称匹配不上若还有退路（控件类型条件查询）就还没到覆盖失败」。
两条并不互斥 —— **候选集空不空**才是判据：

| 情形 | 判据 | 失败类型 | 允许切视觉 |
|---|---|---|---|
| 名字对得上，但控件框全 0 / 零面积（**尺寸异常**） | 候选**在**，只是定不下来 | selection | ❌ |
| 条件查询找到候选，却没有一个与描述对得上（**名称匹配不上**） | 候选集**非空**，选不出 | selection | ❌ |
| 树能读、也查过了，确实没有这个目标 | 候选集**空** | coverage | ✅ |
| 树里一个节点都没有（0 节点 = 静默退化，C-09） | 通道产不出候选 | coverage | ✅ |

「条件查询找到候选却没匹配上」这个数由**端口**报（`uia/ports.py:78` 的 `unmatched_count`），
真机实现填在 `uia/windows.py:338-352`（逐次尝试累加「被名字条件否掉的元素数」）。

### 2.2 查询超时为什么单独一个码

它原来和「0 节点」共用 `LOCATE_FAILED`，而 `LOCATE_FAILED` 是**覆盖失败**（允许切视觉）。
这正是工单禁止的那一类（架构备忘 §2.5 ①：「树读取超时」在禁止清单里）。
本轮把超时拆成独立错误码 `QUERY_TIMEOUT`（`action/errors.py:63`、`uia/errors.py:45-52`），
归**通道级**失败 → 禁止切视觉。**0 节点的语义没变**（仍是覆盖失败，仍允许切视觉，C-09）。

## 4. 与工单假设不符的现实（12 条）

1. **工单的前提「Windows 设置的控件树元素总数为 0」今天不成立** —— 2026-10-21 实测：
   该窗口（ApplicationFrameHost.exe 10.0.26100.9549）的 UIA 树**有 138 个元素**，
   侧栏、卡片、标题栏按钮全在树里。能力表因此判成 **`sparse`** 而不是工单要的「不可用」。
   → **AC5 的第一句（「Windows 设置 = 不可用」）在本机不成立**。
   早先（M3 轮）测到的「树是空的」很可能锚在了**另一个窗口**
   （同名 `ApplicationFrameWindow` 有好几个：`FindWindowW` 按类名会撞车，
   本轮实测按标题「设置」才找到对的那个，锚错窗口时能力表是 `unavailable (no-tree)`）。
2. **切视觉的活体目标必须自己挑**：树里有的元素走 UIA 通道（不切视觉），
   树里没有的（这里是头像圆圈）才走视觉通道。真值只能**从画面量**（UIA 树里没有它）。
3. **目标描述含糊就会点错**：同一目标，写「用户头像」时模型点了**另一个**头像（偏差 1270.9 px），
   写「Windows 设置窗口左上角的用户头像圆圈」才落在目标上（2.2 / 6.7 px）。
   → 视觉通道对**描述的区分度**极度敏感（工单没提这一条）。
4. **生产路径上视觉通道此刻不可用**：本轮 6 次标定（image 路径，模型输入 2048×1280）的最大误差
   **1.06 / 1.78 / 2.14 / 2.83 / 17.12 / 38.83 / 67.07 px**，**一次都没到 1.0 px 容差** →
   按 M5 的硬闸门永远不可用 → **AC1 的切视觉只能在「测量口径」下演示**（与 M6 的测量台同一做法）。
5. **标定是「抽签」**：同一张探针、同一模型，误差跨两个数量级（M8 已记，本轮复现）。
   → 「标定失败即视觉通道不可用」这条规则，在本机等价于「视觉通道**永远**不可用」。
6. **落点偏差达不到 ≤2 px 的稳定达成**：两轮 2.2 / 6.7 px（真值自身 ±0.5~1 px）。
   模型在**整屏**（2048 宽的缩图）上定位一个 90 px 的圆，误差量级与 M6/M7/M8 实测一致
   （粗定位中位数 13~38 px）。**≤2 px 是 UIA 通道的精度量级，不是视觉通道的**。
7. **「查询超时」原来与「0 节点」共用一个错误码** —— 而那个码是覆盖失败（允许切视觉）。
   工单禁止切视觉的清单里有「查询超时」，所以必须拆码（本轮拆了）。
8. **「候选尺寸异常」原来被当成「目标不在树里」**（全 0 的候选被丢掉 → 候选集空 → 覆盖失败 → 允许切视觉）。
   C-08 要求丢掉全 0 的候选，但丢掉之后**不能**当成「找不到」→ 本轮拆出 `INVALID_GEOMETRY`。
9. **能力表的键（应用 + 版本）分辨不了同一应用的不同窗口**：任务栏与文件资源管理器
   都是 `explorer.exe 10.0.26100.9711` → 同一个键、第一次探测的结论会被复用。
   本轮的分表/共表两种口径都测了（`.scratch` 脚本，未入库）。
10. **Chromium 应用在真机上不是「一律失效」**：豆包 = usable、DSH = sparse →
    类别级结论（无论正向还是负向）都写不进去，这正是 C-08 想要的。
11. **测「窗口置前」会让真机画面变**（点任务栏「开始」后任务栏从 `EnumWindows` 里消失，
    M0 已记的现象，本轮复现）。
12. **工单 AC2 的「名称匹配不上一律禁止切视觉」与 README 的口径有出入**（Spec 轴 P3）：
    「候选集空不空」才是判据 —— 没有控件类型退路时，名字查不到只能判「覆盖失败」
    （允许切视觉）。**这与工单字面冲突**，本轮按 README（晚出的统一口径）实现。

## 5. 需要人拍板的事

> 📌 **2026-10-21 收尾轮**：本节条目已汇总进 `docs/tickets/README.md` 的「待拍板清单」——
> **表 1**（P-01 / P-02 / P-03，已按推荐改 AC 措辞）、**表 2**（L-01 / L-02，已拍板）、
> **表 4**（D-03，仍需人拿主意）。

1. **AC5 的「Windows 设置 = 不可用」要不要改口径**：本机实测是 `sparse`（树在、138 个元素）。
   而且「设置」这个应用在能力表里有**两个条目**（`SystemSettings.exe` = unavailable /
   `ApplicationFrameHost.exe` = sparse —— 两个进程）。
   是改工单的期望值，还是把「Windows 设置」这条判据换成**另一个真的没树的 UWP 应用**？
   （改工单 = 改规格，要你点头。）
2. **AC1 的 ≤2 px 要不要按通道分别定**：UIA 通道的落点天然是控件框中心（偏差 0.0 px），
   视觉通道在本机是 2~7 px（三轮实测 2.2 / 6.7 / 6.1）。一个验收线套在两条精度差
   两个数量级的通道上，建议拆成「UIA ≤2 px / 视觉 ≤N px（按分布定）」。
3. **「名称匹配不上」的判据**（Spec 轴 P3；README 口径 vs 工单 AC 2）：
   本轮按 README（「退路也找不到 = 覆盖失败」）实现 —— 后果是**没有控件类型提示时，
   名字查不到仍会切视觉**。要不要改成工单字面（「名字查不到一律禁止切视觉」）？
   改了的话，切视觉只剩「0 节点」一种入口（Windows 设置那种整个树都读不到的情况）。
4. **失败类型多列了两类**（`channel` / `decision`，AC 7 字面是「三类」）：
   本轮按「不许混淆」的原则保留，并把口径写进了 `docs/tickets/README.md`。

   要不要给视觉通道加一步「描述消歧」（用模型确认指的是哪个）？那是新工单量级的事。

   改容差 = 改 M5 的硬闸门（C-03），**本轮没擅自改**。

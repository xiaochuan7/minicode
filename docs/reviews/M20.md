## 2. 设计

### 2.1 一处判定，三处落点

```
                      ┌──────────────────────────────────┐
   动作执行缝 ───────→│  SensitiveWindowGuard.check()     │──→ PrivacyVerdict
   （抓帧之前问一次）  │  枚举屏幕上看得见的窗口           │      （被拦下 / 放行）
                      │  逐个对黑名单（标题 / 类名）      │
                      └──────────────────────────────────┘
                                 │
        ┌────────────────────────┼────────────────────────┐
        ↓                        ↓                        ↓
  seam.py:331              seam.py:727              seam.py:849
  定位那一帧              放大的回源重抓            截图动作
  （等待不拍 → 不问）
```

* `privacy/policy.py` —— **策略本体**：黑名单 + 四组条款（每条带实现位置）；
* `privacy/guard.py` —— **硬闸门**（判定）+ `windows_guard()`（真机接线**只有这一份**）；
* `privacy/document.py` —— **文档渲染** + `resolve_implementation`（条款 → 实现位置）；
* `privacy/__main__.py` —— `python -m minicode.privacy`（生成 / `--check` 核对）。

### 2.2 黑名单的两条判据

| 判据 | 取值 | 判什么 |
|---|---|---|
| **标题命中敏感词表** | 26 条（密码管理器 / 银行 / 支付 / 凭据四组，中英文） | 窗口**在做什么** |
| **窗口类名命中对话框类名** | 4 条（`#32770` = Win32 标准对话框、Windows 凭据对话框） | 窗口**是什么种类**（精确匹配，不做前缀猜） |

**命中即生效**（fail-closed）；**词表带取值来源串**（仓库规矩：词表要能说清词是哪来的）；
⚠️ **词表是工程阈值·未验证**（没有语料统计过误报率）。

### 2.3 硬闸门 vs 人工放行（与 M16 的分工）

| | M16 的「截含敏感窗口的屏」 | M20 的敏感窗口黑名单 |
|---|---|---|
| 形态 | 危险动作 → **人工放行**（批了就拍） | **硬闸门**（根本不许拍） |
| 判据在哪 | M16 给**判据的位置**（`approval/ports.py::SensitiveWindowPolicy` 端口） | **M20 给词表**（README 已写死） |
| 生产路径 | ✅ **已接上（M24）** —— 端口不再空置 | 闸门**永远在** |

⚠️ **两者互斥**：把 M20 的黑名单接进 M16 的闸门，会出现「人点了头就能拍敏感窗口」的路，
与工单 M20 AC 1「根本不许拍、不许发」冲突 → **本单故意不接**（见 §5 ①）。
✅ **M24 起已接上**（2026-10-21 修票落地）：**顺序是「更严的一侧胜出」** ——
**黑名单先行**（命中就在**抓帧之前**拒绝，零抓帧、零像素，**不走到审批闸门**），
M16 那一类退成**二次确认**（黑名单没命中但请求属那一类 → 仍出审批请求，没批则零动作下发）。
**十一类不变**（那一类保留，不删），只改**接线与触发路径**；两层是**两个不同的错误码**。
见 `docs/reviews/M24.md`。

### 2.4 文档由实现生成

```
privacy/policy.py::default_policy()      ← 条款（每条带 实现位置）
        ↓
privacy/document.py::render_policy_document()
        ↓
docs/privacy-policy.md                    ← 仓库里那份（单测钉住与渲染结果逐字相同）
```

`resolve_implementation("模块:符号")` 让「每条都能在实现里找到对应行为」**可机器核对**。

## 4. 与工单假设不符的现实（8 条）

1. **工单没说「敏感窗口」是哪一个窗口** —— 字面读是「被拉黑的窗口」，
   但抓的是**整屏**帧：前台背后的密码管理器窗口**也在那一帧里**。
   只判前台窗口 = **静默漏判**（隐私面最不能要的那种漏）→ 改成**枚举屏幕上
   看得见的窗口**（`approval/windows.py:80`）。⚠️ 代价：窗口标题里带
   「银行」「支付」等词的**后台**窗口也会挡住这一步（真机实测：BOSS 直聘、
   微信、CC Switch 这些窗口都不在黑名单里，没挡住）。
2. **工单 AC 1 写的是「动作日志里记录」，词汇表说的是「动作记录」** ——
   本单落在**动作记录**上（`privacy` 字段 + 一条 note）：记录是逐条的那一份，
   动作日志是它的集合（`CONTEXT.md` 把「动作日志」列为「动作记录」的 avoid 词）。
3. **「与脱敏器一致」这条 AC 需要脱敏器**多给一个出口** —— 文档要引用
   「脱敏的边界」（占位符、正文类控件清单、敏感模式类目），而这些常量住在
   `redact/patterns.py` / `redact/redactor.py`。若在策略侧直接 import 那些常量，
   会撞上 M2 的**单点出口守卫**（那两个占位符的名字只允许出现在三个已知模块里）。
   → 在**脱敏器这一侧**加一个 `redaction_boundary()`（`redact/redactor.py:151`），
   **谁定义规则，谁描述规则**；策略侧只引用它。⚠️ 这是本轮**唯一一处改了别的
   工单的实现**（M2），改的是**新增**（不改既有行为，既有单测一处未改）。
4. **M16 的「截含敏感窗口的屏」在生产路径上仍然不触发** —— M20 的黑名单
   **故意不接** M16 的审批闸门（§2.3），于是 M16 的那个端口**继续空置**。
   ⚠️ README 与 `CONTEXT.md` 仍把「截含敏感窗口的屏」列在十一类危险动作里 ——
   本轮**如实记下**并改了口径说明（README 口径清单 + §5 ①），但**十一类本身没删**
   （那是 M16 的清单，删它属于改别的工单的合同）。
   ✅ **这一条已被 M24 落地**（2026-10-21）：黑名单**接进**了 M16 的闸门（端口不再空置），
   **顺序是黑名单先行、M16 退成二次确认**；**十一类仍然一条没删**。
   这一类**第一次在生产路径上真的会被触发**。
5. **敏感窗口的判定需要「窗口类名」—— M16 的窗口读取只读标题** ——
   `approval/windows.py` 的 `WindowInfo` 多了 `class_name` 字段
   （`approval/ports.py:45`），真机实现补了 `GetClassNameW`。
   ⚠️ 这**改了 M16 的端口形状**（`WindowInspector` 多了一个方法
   `visible_windows`，`approval/ports.py:62`）：M16 的闸门仍用 `foreground()`，
   既有行为不变。
6. **闸门只接三条真机路径是不够的** —— 两轴审查后把**七条会抓真屏的入口**全接上
   （命令行 / HTTP / MCP 共用的 `uia/desktop.py:167`、动作 CLI `action/cli.py:124`、
   UIA 活体测试台 `uia/live.py:241`、端到端评测台 `e2e/real.py:542` 与
   `e2e/apps.py:752`/`:1312`、浏览器通道命令行 `browser/__main__.py:145`）——
   漏接一处就是一处隐私洞。**接线只有一份**（`privacy/guard.py:112` `windows_guard()`）。
7. **自带的一帧也会进模型上下文** —— 消歧那一步会把调用方给的那一帧送给模型，
   所以闸门**不只挂在「我们自己抓帧」那条路上**：定位路径上**先问闸门再决定
   用哪一帧**（`action/seam.py:331` 在 `if frame is None` 之前）。
8. **词表的误报面没有语料** —— 「银行」「支付」这类词在中文标题里很常见
   （真机上就有一个「BOSS直聘」窗口）。**命中即拉黑**意味着误报会让这一步**直接停下**
   （fail-closed 的代价）→ 词表标成**工程阈值·未验证**，等按真实任务日志校一遍。

## 5. 需要人拍板的事（4 条）

> 📌 **2026-10-21 收尾轮**：本节条目已汇总进 `docs/tickets/README.md` 的「待拍板清单」——
> **表 4**（D-43 / D-44，仍需人拿主意）。
> ⚠️ 本单 §5 ①② **方向已定**：十一类**不变**（「截含敏感窗口的屏」那一类保留，不删），
> **M20 的黑名单接进 M16 的闸门**（M20 先拦、M16 退成二次确认，更严的一侧胜出）→ 修票 **M24**。

1. **M20 的黑名单要不要接进 M16 的审批闸门？**（§4.4 / §2.3）
   现在是**两套口径**：M16 说「截含敏感窗口的屏要人点头」，M20 说「根本不许拍」，
   M20 的黑名单**不接** M16 的端口 → M16 那一类在生产上**不触发**。
   → 两条路：**(a)** 维持现状（黑名单更严，M16 那一类留作「另一种敏感窗口」的机制）；
   **(b)** 把黑名单降级为「需审批」，让 M16 的闸门接管（那 AC 1 的「根本不许拍」就要改写）。
   本轮按 (a) 实现（更严的一侧胜出），**待人拍板**。

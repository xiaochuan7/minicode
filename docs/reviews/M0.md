### 【低】23. **【第 3 轮新增】双击的"按下—按下"实测间隔漏算了窗口内必然的 100 ms 固定开销**

- 位置：`src/minicode/action/executor.py:174`（`gap_s = min(0.080, params.time_ms / 2000.0)`）、
  `src/minicode/action/executor.py:181`（实测间隔 = 第二次按下 − 第一次按下）。
- 事实：两次按下之间必然包含——第一次按下的 hold（40 ms）+ 请求的 `gap_s` + 第二次按下前的 settle（60 ms）
  = **100 ms + `gap_s`**。而 `gap_s` 的上限是 `time_ms / 2`，
  所以只有 `time_ms > 200 ms` 时实测间隔才落在系统双击窗口内。
- **第 3 轮实测**（虚拟时钟，`DoubleClickParams(time_ms=…)` 逐档）：

  | `time_ms` | 请求间隔 | 实测按下—按下间隔 | 是否落在系统窗口内 |
  |---|---|---|---|
  | 500 | 80.0 ms | **180.0 ms** | ✅（余量 320 ms） |
  | 400 | 80.0 ms | 180.0 ms | ✅ |
  | 300 | 80.0 ms | 180.0 ms | ✅ |
  | 250 | 80.0 ms | 180.0 ms | ✅ |
  | 200 | 80.0 ms | 180.0 ms | ✅（余量 20 ms） |
  | 150 | 75.0 ms | 175.0 ms | ❌ **超出 25 ms** |
  | 100 | 50.0 ms | 150.0 ms | ❌ **超出 50 ms** |

- 影响：**本机无影响**（`GetDoubleClickTime()` = 500 ms，余量 320 ms）；但公式把"系统双击时间的一半"
  当成可用预算，漏掉了窗口内必然存在的 100 ms。系统双击时间被调小、或后续工单把 settle/hold 调大时，
  记录里会写着 `double_click`，而 Windows 并不认这次双击。
- 违反：工单第 33 行（AC 14"双击 = 两次单击间隔小于 500 ms"）—— 当前机器满足，但**保证条件写错了**。

### 【信息】24. **【第 3 轮新增】冻结原型自己的标定路径把探针容差当成了越界容差**

- 位置：`src/minicode/coord/calibrate.py:497` 与 `src/minicode/coord/calibrate.py:599`：
  `CoordinateAdapter(scale, out_of_bounds_tolerance_px=self.tolerance_px)` —— 探针的 `tolerance_px`

- 事实：工单第 29 行明确"探针容差不得被当作越界容差使用"。**M0 的动作层遵守了**这条
  （`surface.py:66` 用 `DEFAULT_OUT_OF_BOUNDS_TOLERANCE_PX = 2.0`，来自 `coordinates.py:64`；
  动作包对 `minicode.coord.calibrate` 的引用只在 `test_action_protocol.py:22`），
  但**冻结原型的标定路径违反了**。
- 范围：这两处在 `12d31cd` 之前就存在，**不在本次改动区间**（冻结原型只改了 import 路径），
  因此**不改变检查项 4 的"通过"结论**，也不改变 AC 10 的判定。
- 为什么要记：① `src/minicode/coord/README.md:234` 已经写明"注意两种容差语义不同，不要再混用"，
  文档与实现不一致；② 说明"两个容差独立"这条约束**在仓库层面没有被真正执行**，

## 4. 总体结论

**M0 的 20 条验收标准不能整体判为达成。**

- **无保留达成（16 条）**：第 1–5、7–15、18–19 条。本轮重点复核的 8 条
  （C-01 / C-02 / C-11 / 越界 2px / 只落哈希 / 单一缩放来源 / 哨兵值 / 假实现注入点）
  **全部通过**，每条都有 `文件:行号` 级证据，且有可复现的假实现/单测支撑。
  第 2、3 轮还把真机适配器（`windows.py` 全 437 行）与冻结原型的真实接口逐个对照过，**接口用法无一处不匹配**。
  第 3 轮把前两轮的全部结论重新复现过一遍（§0.2.1 的重验表），**无一条被推翻**。
- **部分达成（1 条）**：
  - **第 20 条（已知欠账如实写进记录）** —— 鼠标通道达成（`INJECTION_BLOCKED` + C-07 欠账说明入记录）；
    **键盘通道不满足**：`SendInputError`（`exec/input.py:101`）既不是 `InjectionBlocked` 也不是 `ActionError`，
    直接穿出 `executor.py:140-150` → `seam.py:250-253` → `runner.py:102`，
    表现为进程抛栈，**没有错误码、没有动作记录**（§2-1）。
- **未达成 / 不能判为达成（3 条）**：
  1. **第 6 条（落点误差 ≤2px + 回读偏差 0）** —— 需要真机复核，而实现的判定本身有三处缺口：
     复验在"重读控件树里找不到同名候选"时被静默跳过（`cli.py:113-129`）、复验超差不改已落盘的记录、
     回读容差用了 2px 而非要求的 0（`executor.py:40`，本轮实测 1px/2px 偏差仍判成功）。
     按工单原文"此项不过即不得声称闭环打通"，当前实现**不足以保证**"不过就不声称打通"。
  2. **第 16 条（粘贴不污染剪贴板）** —— 只备份文本格式；剪贴板里是图片等非文本内容时，
     恢复路径执行 `EmptyClipboard()`，内容丢失且无法还原（`windows.py:364-382`、`executor.py:236-252`）；
     本轮同构替身实测复现。读剪贴板失败时更糟：即使没粘贴也会清空剪贴板。
  3. **第 17 条（目标窗口被遮挡时先置前）** —— 句柄口径不一致：控制器按**根窗口**置前，
     缝却拿**候选（可能是子窗口）句柄**去比前台窗口，于是"置前成功"被判成"置前失败"并中止动作
     （`seam.py:237-238` vs `windows.py:424-430`、`windows.py:407-409`、`windows.py:199-207`）；
     本轮用**真机控制器代码**复现：候选是子窗口 → `ok=False / execute_failed / 注入 0 次`。
     之所以至今没暴露，是因为任务栏「开始」按钮的 `native_window_handle` 为 0、恰好回退成顶层窗口；
     且假窗口控制没有复刻"归一"语义，单测因此假绿（§2-7）。
- **另有 17 项问题**（§2 第 8–24 项）：其中 15 项是【低】/【信息】级 —— 越界边界口径与文案不一致、越界判定两份实现、
  C-11 停顿无余量、C-01 抓图尺寸按虚拟桌面比主屏度量（多屏机必然误判）、自检与动作层各抓一次屏、
  `--fake` 路径 stdout 不切 UTF-8、执行器自身不拦越界坐标、双击位移参数查而不用、
  双击间隔预算漏算 100 ms、缝对 type_text/key 抛 `ValueError`、`--fake` 假几何与真机差 32.5px、
  冻结原型标定路径混用探针容差等；另 2 项是【中】级 —— §2-21（抓屏后端抛异常时崩进程）与
  §2-22（未知键名崩进程），它们没有推翻任何一条验收标准，但同样需要修。

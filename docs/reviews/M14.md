## 2. 设计

### 2.1 这一层只管「怎么判」，不管「怎么跑」

| 模块 | 职责 |
|---|---|
| `e2e/tasks.py` | 工单的**形状**与两条不变量（每步要有结构断言、工单至少一步） |
| `e2e/runner.py` | **判定口径**：四个判定取值 + 人工代确认短路 + 跳过短路 + 停止条件 + 条款判定 |
| `e2e/checks.py` | **验收条款的判据**（每条返回「成立吗 + 差在哪」） |
| `e2e/wave1.py` | 第一波的六张票（把 `docs/target-tasks.md` 的期望拆成「步 + 断言 + 条款」） |
| `e2e/report.py` | 报告（逐张判定 + 自动通过率 + 人工代确认 + 跳过原因） |
| `e2e/real.py` | 真机执行器（Windows 设置 / 任务栏、Chrome） |

**为什么判定与执行分开**：判定口径必须能被**假执行器**单测钉住（不碰真桌面、不花模型钱），
真机执行器只负责「把这一步跑起来并把外部可观察的结果如实报上来」。

### 2.2 四个判定取值（不多不少）

```
pass           通过
fail           失败（**含「判不了」** —— 判不了不是通过）
skip           跳过（环境不可达；**永远不算通过**）
pending_human  待人工确认（「人工代确认」的任务；**不自动执行**、不混进自动通过率）
```

**「判不了」为什么落在 fail 而不是单开一档**：工单只要「通过 / 失败 / 跳过」三档；
判不了既不是通过也不是失败的具体形态（它连「不成立」都不是），
所以落在 fail 里、但原因写明是**判不了**（`e2e/runner.py:356`）——
这样「不许把判不了记成通过」这条守住，报告里也读得出区别。

**「缺测量」与「不成立」也分开**：条款要的读数**上下文里没有** → 判「**没测过**」
（`e2e/checks.py:146`），不许当成「测了，结果不成立」——
那会把缺测量伪装成产品缺陷（`CONTEXT.md` 的「静默失败」）。

### 2.3 真值从**树里**取，不写死像素

每一步可以给 `truth_element`（控件名）+ `truth_control_type`（类型提示）：
执行器在**动作之前**按名字+类型查一次控件框，取它的中心当真值
（`e2e/real.py:388`）。控件挪了位也不失效。
查不到 → 真值为 `None` → 落点偏差**判不了**（`e2e/checks.py:117`）——
**不拿 0 冒充「偏差为 0」**。
真值**从哪来**要写进报告（`truth_source` 字段：`e2e/runner.py:96`）。

> ⚠️ 定点查询端口**优先用名字条件**，所以「同名控件有好几个」时拿到的可能是第一个；
> 执行器因此改成**按类型查、按名字在本地筛**（`e2e/real.py:392`）——
> 否则 W-1 的真值会取到「屏幕」那张**卡片**（552~1838）而不是它的**标题文本**（646~688）。

### 2.4 放大是观察型动作：它的结构断言是**坐标结构**

放大不改变界面状态，因此它没有「界面状态」可断言。
它的结构断言是**坐标结构**：回答落在放大区域里（= 目标确实在那一块里被定位到），
由执行器判（`e2e/real.py:225`），报告里也如实写成这句话。

### 2.5 多步任务有**停止条件与交接**（工单的阻塞边 M12）

执行器把 **M12 的停止条件 + 卡死检测器**装在动作执行缝的追踪记录出口上
（`MultiTraceSink` 扇出，`e2e/real.py:404`）——**与动作日志看的是同一份数据**。
每跑完一步就报一次轮次边界（`e2e/real.py:166`）；
撞到停止条件（熔断用尽 / 轮次上限 / 请求人工）就停下来，
并把 **M12 的交接产物**交出去（`e2e/real.py:150`）。
⚠️ 「目标级期望成立」**不据此停** —— 那是 harness 层的语义，
端到端评测里**每一步都有自己的期望**（`e2e/real.py:139`）。

## 4. 与工单假设不符的现实（9 条）

1. **放大的坐标契约在本机模型上是错的（最重的一条）** —— 提示词把区域原点换算到
   **模型坐标系**（`ground/prompt.py:136`），而模型在放大图里报的位置是**那张图的像素**
   （1:1 物理像素）。模型把两者相加 → 答案 = 模型空间的原点 + 物理像素的相对位置
   → **系统性偏一个缩放因子**。实测（区域 (1900,1400)-(2560,1600)，真机一次对比）：

   | 契约 | 模型回答 | 落点 | 与时钟中心的偏差 |
   |---|---|---|---|
   | A 现契约（原点给模型坐标系） | (2126, 1273) | **越界 → 被拒**（模型的合法区间是 2048×1280） | — |
   | B crop 那一套（问图内位置、系统加物理原点） | (603, 165) | (2503, 1565) | **14.0 px**（对「时分两行文字」的包围盒中心是 **1.1 px**） |

   模型在两套契约下**相对位置几乎一样**（(606,153) vs (603,165)）→ 模型的定位能力没问题，
   **错的是我们把两套口径混着加**。
   ⚠️ `docs/00-现状.md` §3 已经写着「crop 契约用 crop 内坐标 + 原点偏移，
   **不是** Anthropic 那套『模型在放大图里仍报整屏坐标』—— M3.1 Flash 没被训过那套」，
   而**放大**动作用的恰恰是后者 → **本轮实测证明这条在放大上也成立**。
   **本轮没有改 M6 的契约**（那是口径变更，见 §5 待拍板 ①）。
2. **Windows 设置里的卡片叫「屏幕」，不叫「显示」** —— 本机 build 26100 的系统页上
   那张卡片的标题是「屏幕」（副标题：显示器、亮度、夜间模式、显示器配置文件）。
   工单字面写「显示」，本轮**照工单字面**写目标描述（「显示」不在树里 → 覆盖失败 →
   切视觉，正是 W-1 要验的那条路径），真值取「屏幕」那张卡片的标题文本中心。
3. **缩放值在可访问性树里读不到** —— 显示设置页的树里有「缩放」（Group + Text +
   ComboBox + Button），但**百分比不在控件名里**，「缩放」那个下拉框的 **Value 也是空的**
   → `e2e/real.py:434` 如实记空并记下原因。
   → **W-1 ②「读出的缩放值与界面显示一致」在本轮判不了**（本层没有 OCR）。
   若要判得成，得给校验层接 OCR（M11 §5 的第 ⑤ 条待拍板）或读下拉框的选项集合。
4. **能力表里 Windows 设置不是「不可用」** —— 是 `sparse`（138 个元素、同名撞车 9 处）。
   M9 已记过同一条（`docs/00-现状.md` §6.12：「AC5 的『Windows 设置 = 不可用』不成立」）。
   **W-1 ④ 在本机不可能达成**，除非能力表改判「不可用」——那与实测矛盾，不改。
5. **本机任务栏的 UIA 树读不出节点** —— 任务栏窗口（`Shell_TrayWnd`）在树里**任何**
   控件类型都返回 0 个（Text / Button / ToggleButton / Custom / Pane 全是 0）。
   这是 `docs/00-现状.md` §6 记过的**环境效应**（真机上点过任务栏「开始」之后，
   任务栏的树变空，重启 explorer 才恢复）。
   → W-3 里「控件状态可读」这一条**判不了**（0 节点 = 通道不可用，C-09）；
   W-3 的真值因此**从画面量**（亮像素包围盒，报告里写明 `truth_source`）。
6. **「显示」这个目标描述会让模型点中卡片的副标题** —— 卡片标题是「屏幕」，
   副标题里出现「显示器」；模型按「显示」去匹配，落到了副标题那一行（偏 27~30 px）。
   → **≤2 px 这一条与「通道 = 视觉通道」这一条在本机互斥**：要落准就得用「屏幕」
   （UIA 树里有 → 走 UIA 通道，1.0 px）；要切视觉就得用树里没有的名字（「显示」），
   模型就会挑到相邻的那行字。
7. **标定是「抽签」，生产口径的准入门时开时关** —— 同一张探针、同一模型：
   本轮三次跑分别是 **66.28 px** / **1.90 px** / **28.61 px** 的最大误差
   （都 > 1.0 px 容差）→ 三次生产路径都被准入门拦下。
   M8 已记过「标定是抽签」（3456×2160 上 1063 px vs 2.6 px）。
8. **BOSS 直聘需要登录态，而浏览器通道起的是全新会话** —— Playwright 的
   `new_context()` **不继承**用户的 Chrome 配置 → 打开职位列表页直接被重定向到登录页。
   要跑 C-1~C-3 得走**用户的真实 profile**（`launch_persistent_context`）或由人先登录，
   两者都要人拍板（§5 待拍板 ④）。
9. **工单说「进入『系统 → 显示』」，本机没有「显示」这个导航项** —— 系统页上是
   「屏幕」卡片；侧栏是顶层项（系统 / 蓝牙和其他设备 / 网络和 Internet / …），
   没有「显示」子项。所以「系统 → 显示」在本机是「系统 → 屏幕卡片」。

## 6. 本轮留下的欠账

* **W-2 的三条条款一条都没验过**（人工代确认 → 执行器一次都没被调用）。
  人代跑的结果可以用 `--manual` 记录进来（格式见 §2 与 `e2e/__main__.py:106`），
  但**本轮没有人代跑**，所以那三条仍然是「没测过」。
* **C-1~C-3 的步骤实现没有在真机上跑过**（未登录 → 全部跳过）：
  浏览器通道那侧的「点击 / 输入」只写到能跑的形状，**没有真机证据**；M15 会用到它们。
* **浏览器通道没有滚动动作**（M13 只做了点击与文本输入）→ C-3 的滚动步**显式失败**
  （`e2e/real.py:797`）。要跑 C-3 得先给浏览器通道补一个滚动动作。
* **真机的落点真值有一处是画面量的**（W-3 的时钟），其余都从树里取；
  真值来源写进每一步的 `truth_source`。
* **Chrome 那条「未登录」的环境原因没有更细的分类**（应用未装 / 网络不通各是另一种写法）；
  本轮只实现了「打不开页面」与「被重定向到登录页」两种。

## 0. 一句话结论

M19 的三条验收标准**全部达成**：MCP 侧是**薄适配**——三个工具（一次动作 / 一段动作程序 /
读观察）都只调 `serve/service.py::ActionService` 这**一份**实现（与命令行、HTTP 共用），
协议版本核对只有**一份**（`serve/protocol.py::checked_protocol_version`），
版本对不上明确报错且**零动作下发**，错误码全部取自动作协议那一份。
本轮抓到**两个真 bug**（stdio 协议流被横幅污染、Windows 管道默认 GBK 编码），
两轴 code-review 各查出一条**硬违规**（集合写了两份、文档零更新）与两条**实现得不对**
（程序工具丢停止信号、观察读不到目标却报成功），都已修并补了单测钉住。

## 2. 设计

### 2.1 一份实现，三个前端（MCP 只是第三个壳）

```
                    ┌──────────────────────────────┐
 命令行前端 ───────→│  ActionService               │
 HTTP 前端  ───────→│  execute / execute_program / │──→ 动作执行缝 ──→ 落点 + 动作记录
 MCP 前端   ───────→│  observe（唯一的一份）        │        │
                    └──────────────────────────────┘        ↓
                                                      动作日志（ActionLog）
```

* `serve/protocol.py` —— 动作请求 / 动作响应 / 程序请求 / 观察请求的外部形状
  + **唯一一处版本核对**（`:92`）+ 三个响应的**公共部分**（`ResponseBase`，`:193`）；
* `serve/service.py` —— **唯一入口实现**（`execute` / `execute_program` / `observe`）；
* `mcp/server.py` —— JSON-RPC 2.0 的 MCP server 本体（**只认信封与方法名**）；
* `mcp/tools.py` —— 工具目录（**只做「取参数 → 调服务 → 交出载荷」**）；
* `mcp/__main__.py` —— `python -m minicode.mcp`（stdio 传输 + 真机锁）。

### 2.2 MCP 协议（stdio，JSON Lines）

| 方法 | 行为 |
|---|---|
| `initialize` | 回 `protocolVersion`（MCP 协议版本 `2025-06-18`）+ `capabilities.tools` + `serverInfo`（**动作协议版本** `cua.action/1`） |
| `notifications/*` | 通知：**不回**（`mcp/server.py:119-121`） |
| `ping` | 回 `{}` |
| `tools/list` | 三个工具的名字、说明、入参 JSON Schema |
| `tools/call` | 调工具 → `content`（JSON 文本）+ `isError`（动作失败时为真） |

**错误分两层**（与 HTTP 前端同一套口径）：**JSON-RPC 错误码**是传输层的说法
（`-32700` 解析错 / `-32601` 方法不存在 / `-32602` 参数不对），
**动作协议错误码**是动作语义（在工具结果的载荷里）。

### 2.3 三个工具

| 工具 | 入参 | 出参 | 走的路 |
|---|---|---|---|
| `minicode_action` | `protocol` / `action` / `target` / `params` | 动作响应（与 CLI / HTTP **同一形状**） | `ActionService.execute` → 动作执行缝 |
| `minicode_program` | `protocol` / `program` | 程序响应（`stdout` / `stderr` / `calls` / `records` / **停止信号**） | `ActionService.execute_program` → 受控执行环境（`action/program.py`）→ **同一条缝** |
| `minicode_observe` | `protocol` / `name` | 观察响应（截图摘要 / 已脱敏控件树 / 脱敏计数） | `ActionService.observe` → 截图走缝 + 控件树走**定点观察端口** |

⚠️ **动作程序由调用方给**（宿主的模型写那段程序）：本层**不生成**程序，也**不调模型**。

## 4. 与工单假设不符的现实（7 条）

1. **工单说「MCP 侧是薄适配」，但没说「薄适配」落到哪一层** —— 本轮把**唯一入口实现**
   放在 `serve/service.py`，MCP 侧只有「认信封 → 派方法 → 渲染」三件事
   （`mcp/server.py`）与「取参数 → 调服务」（`mcp/tools.py`）。
   ⚠️ **代价**：`serve` 这一层现在**多了两种调用**（程序 / 观察），
   而命令行与 HTTP 两个前端**还用不到**它们（命令行仍只有 `action` / `log` / `http`）。
2. **工单没说要暴露哪些工具** —— AC1 只说「至少覆盖『执行一段动作程序』与『读观察』两类」。
   本轮给了**三个**：`minicode_action`（一次动作，AC1 没点名，但**没有它，宿主连单步都做不了**，
   而且 AC2 的「与 CLI / HTTP 同一请求」就是在说它）、`minicode_program`、`minicode_observe`。
3. **「执行一段动作程序」的程序由谁写？工单没说** —— 本轮的口径：**由调用方给**
   （宿主的模型写那段程序，minicode 只在**受控环境**里执行）。
   本层**不生成**程序、**不调模型**（那会把「对外形态」变成「决策层」）。
   ⚠️ 代价：**审批在 MCP 这一层没法交互**（见 §4 ⑤）。
4. **「读观察」读什么，工单没说** —— 本轮读两样：**截图摘要**（尺寸 + 哈希，
   与「截图只落哈希」同一条红线）+ **定点读到的控件树**（**已脱敏**）。
   ⚠️ **观察是定点的**（必须带名字条件）：协议里的 `inspect`（读控件树）动作种类
   **至今未实现**（`action/protocol.py::DEFERRED_KINDS`），
   而**全树 dump 被 C-09 禁止** —— 所以观察走的是**定点查询**，
   宿主得先知道要找什么（见 §5 ①）。
5. **MCP 的 stdio 形态下，危险动作一律走不通** —— 审批人在**命令行**里问人
   （`approval/console.py::ConsoleApprover`），而 MCP 的标准输入是**协议流**（不是终端）
   → `isatty()` 为假 → **非交互一律不批**（fail-closed，`approval/console.py:81-87`）。
   即：**十一类危险动作在 MCP 这一层永远拿不到批准**，会被 `approval_denied` 拦下、
   **零动作下发**。→ 见 §5 ②。
6. **动作程序里的「输入文本 / 按键」不产动作记录**（M10 的欠账） ——
   `decision/api.py` 里这两种动作**直接用动作执行器**（缝不接它们），
   因此**没有追踪记录**、**没有动作记录**（`decision/api.py:191-251` 的注释已记着这笔账，
   `docs/reviews/M10.md` §3 第 8 条）。
   ⚠️ 本轮把它**暴露到了对外形态上**：MCP 的程序工具能在真机上敲字，而动作日志里没有这一条。
   （决策层那条路上一直是这个样子，**不是本轮引入的**；但对外形态上它第一次被看见。）
   → 见 §5 ③。
7. **stdio 的两个流都得固定成 UTF-8** —— Windows 上**管道**的默认编码是 GBK，
   而 MCP 的消息流是 UTF-8 的 JSON：中文目标描述会变成乱码。
   本轮真机跑之前就踩到了（`UnicodeDecodeError`），已在 `mcp/server.py:229` `_force_utf8` 里钉住。

## 5. 需要人拍板的事（4 条）

> 📌 **2026-10-21 收尾轮**：本节条目已汇总进 `docs/tickets/README.md` 的「待拍板清单」——
> **表 4**（D-41 / D-42，仍需人拿主意）。
> ⚠️ 本单 §5 ① 与 §5 ③ **方向已定**：读观察改走动作执行缝（`inspect` 从延后挪到已接线）、
> 输入类动作补动作记录 → 修票 **M26** / **M25**。§5 ③ **是真 bug**（违反 M17 的字段完整性）。

1. **「读观察」要不要做成协议里的 `inspect` 动作？** 现在观察走的是
   **定点观察端口**（校验层同一个形状：`verification.layer.StateObserver`），
   **不经过动作执行缝** —— 因为协议里的 `inspect` 动作种类**至今未实现**
   （`action/protocol.py::DEFERRED_KINDS`），而动作执行缝不接它。
   → 两条路：**(a)** 补上 `inspect` 动作（走缝、产动作记录、成为协议里的第 13 个「已接线」种类）；
   **(b)** 维持现状（观察是**只读**的，不算动作，不产动作记录）。
   本轮按 (b) 实现（改动最小、不新增动作语义），**待人拍板**。
2. **MCP 这一层怎么让危险动作拿到批准？** 现在**永远批不下来**（§4 ⑤）。
   → 两条路：**(a)** 走 MCP 的 **elicitation**（协议自带的「问用户」机制，本轮没实现）；
   **(b)** 危险动作**只走命令行 / HTTP**（那里人能点头），MCP 只做安全动作。
   本轮按 (b) 的现状实现（fail-closed 是对的），**待人拍板**。
3. **动作程序里的「输入文本 / 按键」要不要补动作记录？**（§4 ⑥）
   → 补的办法是让这两种动作也走缝（缝现在不接它们），
   或者在 `decision/api.py` 那侧直接产追踪记录。**待人拍板**（M10/M11/M17 的欠账）。
4. **MCP 要不要也暴露 HTTP 传输（streamable HTTP）？** 本轮只做了 **stdio**
   （宿主把本进程拉起来，DSH / Claude Code 都支持）。
   → 要不要补 HTTP 传输（会让「同一个 server 两种传输」这件事多一份接线）？**待人拍板**。

## 7. 测试与评测的分工

* **单测**（`src/minicode/mcp/test_mcp.py`，**18 条 + 8 个 subtest**）覆盖三条验收标准的

  ⚠️ 其中**三条是本轮两轴审查后才补的**：① 程序请求交还给人 → 停止信号看得见；

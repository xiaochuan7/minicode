## 0. 一句话结论

**落点从「元素矩形中心」改成「可见文本的实际包围盒中心」**（行盒中心），
文本度量拿不到就**判不了**（不回落到矩形中心）。

**真机实测偏差 ≤2 物理像素**（两条独立路径量）。

⚠️ **2026-10-21 口径补写**：**没有文本子节点**的元素（输入框 / 按钮这类 ——
屏上的字来自 `value` / `placeholder` / 默认标签，**不是文本节点**）
→ 落点取**它自己的矩形中心**（**元素框本身就是它的真值**，不算回退）。
这一条已落进实现与工单 AC。

## 3. 与工单假设不符的现实（4 条）

1. **工单说「元素没有可见文本」，实际有一类元素「有可见文字但没有文本节点」**：
   `<input placeholder="姓名">` 的可访问性名来自 **placeholder**，它在屏上**看得见**，
   但它不是文本节点 → 文本度量量不出来。
   ✅ **2026-10-21 已拍板**：**接受这个回退**，但**补一条 AC** —— **没有文本子节点的元素
   落点取它自己的矩形中心**（元素框本身就是它的真值，**不算回退**）。
   本单的落点规则与工单已按这条改写（见 AC6）。
2. **「可见文本的实际区域」有两个不同的框**：浏览器给的**行盒**（`Range.getClientRects`，
   行高）比屏上**墨迹**（字形实际覆盖）高 ~3 CSS px。
   ✅ **2026-10-21 已拍板：取行盒中心**（与桌面通道「控件框中心」同类；墨迹中心随字体
   渲染与抗锯齿抖动，行盒是稳定的布局盒）。实测验收线**已经 ≤2 px**，两种取法都达标。
3. **落点与真正的点击位置原先会分家**：浏览器通道的动作走**浏览器自己的输入通道**
   （CDP `Input.dispatchMouseEvent`），原先点的是**元素框中心**。只改落点会留下
   「记录的落点 ≠ 真的点下去的地方」。→ `cdp.py` 的 `invoke()`（`:271`）也改成点
   **可见文本区域的中心**（与落点同一处；读不到时退回元素盒子 —— 那时定位本来就判不了，
   不会走到这里）。真机验证里点击仍然生效（页面状态「尚未提交」→「订单已提交」）。
4. **一次 CDP 往返不够**：第一版里，JS 对**非元素节点**（文档节点）抛异常 → CDP 返回的
   `result` 里没有 `value` 键 → 抛 `KeyError: 'value'`。而且最初把「盒子」和「文本区域」
   绑在一起返回，导致**量不到文本时元素整个从快照里消失** → 「姓名」被报成
   `target_not_found`（覆盖失败，**允许切视觉**）—— 这是错的（元素明明在页面上）。
   已改成：**盒子与文本区域分开**（`cdp.py:391` `_node_geometry`），
   量不到文本时盒子照样给、元素照样在快照里，只是文本判不了 → 报 `invalid_geometry`
   （选择失败，禁止切视觉）。真机 `last_error` 现在是空。

## 4. ⚠️ 被改掉的既有用例（原样抄录，2026-10-21 口径要求留痕）

本单**改写了一个与新 AC 冲突的既有用例** —— 旧用例断言的正是**本单要推翻**的行为
（落点取元素矩形中心）。**改的理由**：工单 M28 的核心就是把落点从「元素矩形中心」
改成「可见文本的实际区域」，旧断言与新 AC **直接互斥**，两者不可能同时成立；
留旧断言就是让单测红着。

**原始版本（`59f4abd` 之前，`src/minicode/browser/test_browser_channel.py`）**：

```python
    def test_the_landing_point_is_the_element_rect_center_in_physical_space(self):
        channel = _channel([_snapshot(_element(rect=(300, 200, 400, 240)))])
        result = channel.locate(
            LocateRequest(target_description="提交订单", anchor=_ANCHOR)
        )
        self.assertEqual(result.landing_point, (350, 220))
```

**改成**：

```python
    def test_the_landing_point_is_the_visible_text_box_center_in_physical_space(self):
        """工单 M28：落点取**可见文本的实际包围盒**的中心。"""
        channel = _channel(
            [
                _snapshot(
                    _element(
                        rect=(300, 200, 400, 240),
                        text=_text((310, 210, 350, 230)),
                    )
                )
            ]
        )
        result = channel.locate(
            LocateRequest(target_description="提交订单", anchor=_ANCHOR)
        )
        self.assertEqual(result.landing_point, (330, 220))
```

**断言值的变化**：`(350, 220)`（元素矩形中心）→ `(330, 220)`（文本区域中心）。
**元素矩形 (300,200,400,240) 本身没变**，变的只是**落点取自哪个矩形**。

⚠️ **同时改了一个测试辅助函数**：`_element()` 的默认 `text` 从「没有 text 字段」改成
`TextMeasurement(rect=element.rect)`（**文本区域铺满控件框**），这样**其余既有用例的
落点断言一个字都不用改**（默认情况下文本区域 = 控件框 → 落点 = 控件框中心）。
这是为了让新层**显式化**，而不是**放松**任何断言。

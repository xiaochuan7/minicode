## 3. 与工单假设不符的现实

1. **`IsPassword` 的属性 ID 不是 30043** —— 照抄来的 30043 读出来**恒为 True**
   （那是别的布尔属性），会让**所有控件都被当成密码框**（脱敏器把普通控件的值也抹掉）。
   本机实测（临时造一个 `ES_PASSWORD` 编辑框与一个普通编辑框逐个 ID 对照）：
   **30019** 才是「密码框 True / 普通框 False」的那个。已写进 `windows.py:101-112`。
2. **冻结原型的 AND 条件路径在本机崩** —— `build_condition()` 在**两个条件并存**
   （名字 + 控件类型）时走 `CreateAndCondition`，本机实测抛 access violation（进程直接挂）。
   → 查询一律用**单条件** + Python 侧名字过滤。**冻结原型不改**，新代码绕开它。
3. **「门控解不开」与「从未可用」在真机上分不开** —— `SystemSettings.exe` 的树本来是空的，
   但「激活窗口」也失败了，于是被记成 `gated-unlock-failed`；同一个 `cc-switch.exe`
   两次探测分别被记成 `no-tree` 与 `gated-unlock-failed`。
   **两种结论都判「不可用」✓，但归因不稳定** —— 需要人定这条归因到底该信什么。
4. **同名撞车必须去重** —— 递归子窗口时同一元素会同时出现在父窗口与子窗口的子树里；
   不去重时任务栏被数出 34 处撞车（误判 sparse），去重后 0 处（usable）。
5. **冻结原型的 `Element` 不暴露值类属性** —— 只能取它的原始 COM 指针自己读
   （vtable 下标 10 由原型自己记着的三个下标自洽推出）。
6. **工单的「候选唯一时零模型调用」在真机上验证不了** —— 真机没有「两个同名候选」可打；
   消歧链路只有单测覆盖（假指认）。
7. **「自然语言描述」需要调用方给控件类型** —— UIA 的名字条件是**精确**属性条件，
   「任务栏的开始按钮」精确查不到；退路是「控件类型条件 + 名字包含」，
   所以 `--control-type` 必须真的传下去（本轮补上了；没有它就不退，判覆盖失败）。

## 2. 设计：三条硬红线怎么落的

### 2.1 换算链路**单一来源**（架构备忘 §2.5 ②）

浏览器通道引入了一个**新的空间**（页面的 CSS 像素），所以换算必须有一个**新的唯一出处**：

| 量 | 出处 | 性质 |
|---|---|---|
| CSS 矩形 → 物理矩形 | `browser/geometry.py:53`（`css_rect_to_physical`） | **只有这一处** |
| 物理像素 / CSS 像素（比例） | `browser/geometry.py:71`（`viewport_from_window`）：**物理窗口宽 ÷ CSS 外框宽** | **量出来的**（本机 1920 ÷ 1280 = 1.5），**不是写死的 1.5** |
| 视口在物理表面空间的位置 | 同上：物理窗口矩形（Win32，PMv2 → 物理像素）+ 视口在窗口内的偏移 | 视口偏移由 CSS 尺寸与物理尺寸之差算出 |
| 矩形 → 落点（中心） | `action/geometry.py:69`（`center_point`） | **两条通道共用**（UIA 侧与浏览器侧都调它） |
| 文本匹配规则 | `action/text.py:17`（`name_matches`） | **两条通道共用** |
| 候选数上限（8）与来源串 | `action/ports.py:79`（`DEFAULT_MAX_CANDIDATES` / `candidate_limit_source`） | **所有通道同一条**（原来住在 `uia/channel.py`） |

### 2.2 脱敏排在所有通道之前（C-15）

页面结构里有可见文本（可能含敏感内容）→ 浏览器通道**同样受脱敏闸门约束**：
`browser/channel.py:264`（`_disambiguate`）：**脱敏没上线就不许把页面结构送模型**
（`_ChannelRefused` → 错误码 `channel_disabled`，**零模型调用**）。
单测 `browser/test_browser_channel.py:335`（闸门拦下 → `CHANNEL_DISABLED`，模型调用 0 次）。

### 2.3 失败类型分开记（工单 M9 AC 7 的口径）

浏览器通道的失败**复用同一套错误码与映射**（`action/errors.py` 的 `FAILURE_TYPE_BY_CODE`）：

| 情形 | 错误码 | 失败类型 | 允许切视觉 |
|---|---|---|---|
| 页面结构快照里没有这个元素 | `target_not_found` | 覆盖失败 | ✅ |
| 候选超上限（默认 8） | `too_many_candidates` | 选择失败 | ❌ |
| 消歧失败 | `ambiguous_target` | 选择失败 | ❌ |
| 页面变了、重定位失败 | `relocate_failed` | 选择失败 | ❌ |
| 脱敏闸门拦下 | `channel_disabled` | 通道级失败 | ❌ |
| 能力表判不可用 | `locate_failed` | 覆盖失败 | ✅ |

## 4. 与工单假设不符的现实（11 条）

1. **「拿到页面的可访问性快照」在扁平 DOM 上给的不是元素，是文本节点**：
   `<div>提交订单</div>` 的可见文本挂在 **`StaticText` 文本节点**上（角色 `statictext`），
   而**文本节点没有 `getBoundingClientRect`** → 矩形只能取它的**父元素**
   （`browser/cdp.py:335` 的 `_node_rect` 里 `this.nodeType===3 ? this.parentElement : this`）。
   后果：本轮选中的矩形是那个 `div.btn` 的盒子（`div` 是块级 → 整行宽），
   落点落在**整行的中心**（1140, 413）而不是文字上。
2. **具名元素会带一个同名的叶子文本节点**：Chromium 的可访问性树里
   `<button>提交订单</button>` 给出 `button`（名「提交订单」）**和**一个 `StaticText`
   （名「提交订单」）→ 不去重的话，按可见文本定位会**凭空多出一堆同名候选**（全是假的撞车）。
   本轮的去重规则在 `browser/cdp.py:318`（`_kept`）：**与具名祖先同名的叶子文本丢掉**。
3. **「扁平结构」在可访问性树里的表现是「大量没有可见文本的容器」**：
   本轮 9 个无名容器 vs 7 个有名元素 → 判 `sparse`（工单 AC 6 要求的映射 ✓）。
   ⚠️ 判据是**本轮定的**（工单只给了映射没给判据）→ 见 §5。
4. **`DOM.resolveNode` 之前必须先 `DOM.getDocument`**（`browser/cdp.py:362` 的 `_ensure_dom`）：
   否则**每个元素的矩形都读不出来**，页面结构会退化成一张**没有位置的清单**。
5. **`DOM.describeNode` 必须用 `objectId`**（不能用 `nodeId`）：用 nodeId 会报
   「Could not find node with given id」（本机实测）。
6. **注入是异步到达的**：判断「浏览器收没收到键盘事件」**只查一次**会把「还没到」
   误判成「收不到」→ **重复输入一遍**（真机上先撞到过一次：字段一度出现两个值）。
   本轮改成**查 5 次 × 100 ms**（`browser/typing.py:45`），并补了单测 `:256`。
7. **agent 进程无法把浏览器窗口置前**：Windows 的前台锁让 `SetForegroundWindow` 失败
   （连「先发一个 ALT」的经典绕法在本机也没成）→ **桌面注入的按键根本到不了浏览器**。
   → **退化路径因此被真机实测触发**（AC 4 的行为得到端到端验证）。
   ⚠️ 这条限制**桌面通道同样受着**（`action/windows.py:510` 的 `bring_to_front` 会返回 False）。
8. **Playwright 默认会模拟 1280×720 的视口** → 页面 CSS 尺寸与真实窗口对不上 →
   换算的比例会算错。必须 `no_viewport=True`（`browser/__main__.py` 与真机脚本都用它）。
9. **Chromium 的 Windows 可访问性树时有时无**：同一页面前后两次 UIA 查询，
   一次能看到页面里的 `Edit`（名「姓名」）、一次只看到 Chrome 自己的地址栏
   → **不能**拿 UIA 树给浏览器通道做交叉核对（本轮只当观察记录，没当判据）。
10. **「页面元素」不等于「控件」**：本轮选中的角色是 `statictext`（不是 button）——
    页面结构能定位到它，但它不是一个控件。工单 AC 1 说「落到同类控件上」，
    本轮的口径是「落到**同类可操作目标**上」（桌面那边是控件框中心，网页这边是元素矩形中心）。
11. **动作协议没有第二套**：浏览器通道实现的是**同一个 `ControlLocator` 端口**
    （`action/ports.py:488`）→ 缝里的动作构造、坐标处理、动作记录**是同一段代码**
    （`action/seam.py:925` 的 `_build_action`）；追踪记录用 `LocateResult.channel`
    区分「这一步走了哪条通道」（`uia` / `browser`）。

## 5. 需要人拍板的事

1. **能力表按通道分表还是合成一张多通道表**？本轮是**按通道分表**
   （UIA 一张、浏览器一张），三态与「应用 + 版本」的键共用（`src/minicode/capability.py`）。
   `CONTEXT.md` 的「能力表」词条说它记录「**各通道**可用性」—— 合成一张多通道表更贴词条，
   但那是另一次改动。
2. **浏览器通道的落点取「元素矩形中心」还是「可见文本的实际区域」**？本轮取前者
   （扁平 DOM 上那个 `div` 是整行宽 → 落点 (1140, 413) 离文字很远）。
3. **「扁平结构 → 部分覆盖」的判据认不认**？本轮判据 =
   「没有可见文本的元素数 > 有可见文本的元素数」（本机 9 > 7 → `sparse`）。
   工单只给了映射，没给判据。
4. **Chromium 的 Windows 可访问性树不可靠**（§4 第 9 条）→ 浏览器通道要不要
   **完全不复用** UIA 树做交叉核对（本轮已经没拿它当判据，但页面上的 `input` 元素
   在 UIA 树里**是有**的 → 那是不是一条可用的交叉核对通道，值得后票再查）？
5. **退化要不要升级成结构化字段**？本轮把「输入通道退化」记在 `ActionResult.notes`
   （既有机制，会进动作记录），没有单独的字段。

## 7. 测试与评测的分工

* **单测**（`browser/test_browser_channel.py`，**21 条**）：只测**外部行为** ——
  一句目标描述进去，一个选中项 + 一个物理像素落点出来；失败时给出**哪一类**失败；
  输入时给出「送达 / 退化 / 判不了」。不测内部实现细节。
* **真机**（本节 §3）：结构定位 + 浏览器自己的输入通道 + 引用时效 + 退化 + 剪贴板。
  桌面通道（UIA）不需要真机也能被单测覆盖，所以本票的**单测比例比 M3 高**。
* **端到端评测**：M14（Windows 设置 + Chrome）才是那条链路的端到端验收，本票只给前置。

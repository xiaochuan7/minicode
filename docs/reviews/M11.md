## 0. 一句话结论

**校验层落成了机器可判的规则**：**期望**判的是**变化**（工单：「某个按钮变成不可用」「某段文本出现」——
断言「动作之后 X 现在是这个状态」**且**这次动作促成了它），三种手段
（可访问性树 / 文本比对 / 像素差分）各给一个判定、**判据取并**、**模型不参与裁判**；
没有期望时走默认校验（**8×8 像素块 + 32 位精确比较 + 1% 阈值**，
轮询节奏**首次立即 → 100 ms 内 15 ms → 之后 20 Hz**，判定顺序**有反应 → 安定 → 返回**），
它只给「**有反应 / 界面无变化**」这个**信号** —— 工单那两条语义边界
（「点错打开错对话框」不得判成功、「界面本来就无变化」不得直接判失败）都落成了可复现用例。
三段耗时与三类失败按**单步**与**整任务**两个粒度分别可读。

## 2. 设计：期望、三手段、默认校验

### 2.1 期望判的是**变化**（工单的口径）

工单写的是「某个按钮**变成**不可用」「某段文本**出现**」，AC 1 也写「**状态变化 / 文本出现**」。
所以期望断言的是「动作之后 X 现在是这个状态」，**并且**这次动作**促成了**它：

| 形态 | 成立的条件 | 不成立 | 判不了 |
|---|---|---|---|
| `state_change`（可用 ↔ 不可用） | 之前是另一个状态，**现在**是期望的状态 | 之前就已经是期望的状态（**没发生变化**）／现在还不是 | 之前或现在观测不到那个控件（树覆盖不全） |
| `text_appears` | 之前**没有**这段文本，现在**有** | 本来就有（不算「出现」）／现在还是没有 | 树读不出来 |
| `text_disappears` | 之前**有**，现在**没有** | 现在还在 | 之前就没有（判不了「是不是消失了」） |

因此校验是**两段式**：动作**之前**取一次基线观测（`VerificationLayer.begin`），
动作**之后**再观测一次（`verify`），两次对照 —— 缝里 `action/seam.py:507-535` 就是这个顺序。
基线取的是**期望目标自己**的观测（不是动作目标的），所以「点『更多』之后『已保存』出现」
这种跨控件的期望也判得了。

> ⚠️ 这与 `CONTEXT.md` 的「期望 = 动作之后应当成立、可被确定性验证的**状态**」不冲突：
> 断言的仍然是「动作之后 X 现在是这个状态」，**外加**「这次动作促成了它」。
> ⚠️ **别把「期望」说成「后置条件」** —— `CONTEXT.md` 的「期望」词条把「结果、后置条件」列为 avoid。

### 2.2 三手段各判各的，判据取**并**

| 手段 | 能判 | 判不了 |
|---|---|---|
| 可访问性树 | 状态 / 存在性 | 文本的具体内容 |
| 文本比对 | 文本出现或消失 | 状态 |
| 像素差分 | **界面有没有变**（通用条件） | **具体期望** |

三条规矩各有一处落点：

1. **像素变化 ≠ 成功** —— 像素差分对**具体期望**恒给 `unknown`（`verification/layer.py:372`），
   它只在**默认校验**里出现；「有反应」这个结论**不等于成功**（`satisfied` 恒为 `None`）。
2. **判据取三者的或** —— 任一能判的手段说「成立」即成立；全都判不了 → `expectation_unknown`
   （**判不了 ≠ 不成立**，见 `verification/test_verification.py:186`）。
3. **模型不参与裁判** —— 校验层**没有任何模型依赖**，结果里的 `model_calls` 恒为 0。

### 2.3 默认校验：像素差分只给**信号**

没有期望时，动作前后抓帧做差分（`verification/diff.py:236`）：

```
基线帧（动作前那一帧）
  → 轮询：首次立即 → 100 ms 内 15 ms → 之后 20 Hz
  → 变化率 = 变化的 8×8 块 ÷ 总块数（阈值 1%）
  → 「有反应」→ 连续两帧低于阈值 =「安定」→ 返回 changed
  → 没反应且连续两帧低于阈值 → 返回 no_change（界面无变化）
```

结论只有两个：`changed`（有反应并安定）/ `no_change`（界面无变化）。
**两个都不是成功或失败的判定** —— 判成功要靠期望断言，判失败也是（§2.1）。

### 2.4 三段耗时与三类失败：**两个粒度**

| 粒度 | 在哪 | 三段 / 三类 |
|---|---|---|
| **单步** | 追踪记录 / 动作记录 | 定位、决策、执行+校验各有值（+ 单步的三段**占比**）；失败按定位 / 决策 / 执行三个字段分开 |
| **整任务** | `verification/telemetry.py:112` | 三段耗时合计 + **各自占比**；三类失败**次数 + 占比** |

**决策段耗时是轮级的量**（一次规划调用 → 一轮 → 可能产出多个动作）。
记在每个动作上会**重复计数**，因此：

* 决策层把本轮的耗时**累加**进「待记」的那一份（`decision/api.py:67`），
  由**轮内第一个动作**取走（`decision/api.py:76`）—— 反思步的耗时因此也落得到某个动作上；
* 整任务的决策段合计由决策层**单独报**（`decision/harness.py:351` → `telemetry.add_decision`），
  **不**从动作记录里再累加一次（`verification/telemetry.py:86` 的注释写明了这条）。

## 4. 与工单假设不符的现实（11 条）

1. **1% 的分母是「块」不是「像素」** —— 工单写「8×8 像素块 + 32 位精确比较」又写「阈值 1% 像素变化」。
   本轮把一帧切成 8×8 块、每块压成一个 32 位值（各通道均值打包）做**精确比较**，
   **变化率 = 变化的块数 ÷ 总块数**。取块级而不是像素级：像素级会被抗锯齿与光标闪烁淹没，
   且整屏 400 万像素的逐像素比较没有工程价值。⚠️ **这是对工单字面的偏离**，记在 §5 待拍板。
   ⚠️ 块值取的是**通道均值**：一个块里平均亮度变化不到 1/64 的改动读不出来（已知边界）。
2. **「有反应 → 安定 → 返回」需要等待上限，工单没写** —— 加了两个**工程阈值**
   （反应 2 s / 安定 2 s，`verification/diff.py:68`/`:71`），来源串按仓库规矩写「工程阈值·未验证」，
   **并且随记录落盘**（`verification/diff.py:212`）。
3. **「两帧无变化就收工」与「有期望」冲突** —— 工单的早收工规则是为**默认校验**写的；
   有期望时早收工会把「界面还没生效」误判成「没生效」→ 有期望时**不早收工**，等到超时再判
   （`verification/diff.py:347` 的 `early_exit_on_no_change`）。
4. **期望判的是「变化」，不是「状态」** —— 工单的字面是「**变成**不可用」「文本**出现**」，
   所以断言要求「动作之前不是这个状态」。这意味着**本来就在**的期望（比如任务栏那个「开始」按钮）
   判成「不成立」（§3.2 真机复现）。若改成「状态」口径，实现更宽松，但会放过
   「期望早就成立、动作其实没做功」这类**静默失败** —— 两条口径的取舍记在 §5。
5. **「某个按钮变成不可用」在仓库里读不到** —— 冻结原型不暴露 `IsEnabled`，本轮补了
   `ControlCandidate.enabled`（`action/ports.py:139`，读不出来按**可用**算）与真机 COM 读取，
   **属性 ID 实测 = 30010**（§3.1；常见写法 30022 在本机恒为 False）。
6. **「目标窗口标题」对 XAML island 元素读不到** —— Windows 设置那些元素**没有自己的窗口句柄**
   （`native_window_handle` 为 0），标题只在**锚定窗口**上 → 标题取锚定窗口的
   （`uia/windows.py:333` 的 `anchor_title`）。任务栏本身没有标题 → 记 `null`（不假装）。
7. **动作日志里已经有一个叫 `verification` 的字段** —— 那是 M0 的**落点复验**
   （`landing_delta_px` / `landing_verified`）。本轮的校验结果另起名 **`verification_result`**
   （`action/records.py:288`），两个字段不混。
8. **决策耗时是轮级的量** —— 一轮规划可能产出多个动作；记在每个动作上会重复计数 →
   **累加**后记在**轮内第一个动作**上（`decision/api.py:67`），整任务合计由决策层单独报（§2.4）。
9. **文本比对的语料来自可访问性树（仓库里没有 OCR）** —— 而且只取**控件名**（**值不进日志**，
   C-15）。因此它只认「树里有名为 X 的控件」；状态栏里的文字（控件的**值**）**看不见** ——
   已知局限，不是假装文本比对更强。
10. **真机上「执行+校验」比「定位」贵 4 倍多**（1025 ms vs 223 ms）—— 大头是**抓屏**
    （4 帧 2560×1600）+ 一次基线读树，不是差分。默认校验每步都要付这笔钱，
    M14/M15 编排多步任务时要知道。
11. **期望断言失败要一个新错误码** —— `expectation_failed`（`action/errors.py:129`），
    归**执行失败**（`:182`）。按 M21 的口径「只加不改不升版本」处理（协议版本仍是 `cua.action/1`）。

## 2. 架构决策备忘 §2.6 检查项对照（本票正文没点名 C-xx，按相关度逐条核）

**C-11 · 点击必须 move → 60 ms → down → 40 ms → up** —— 本轮**未改动**点击时序：
`click` 收敛成参数后仍走同一个 `_click_sequence`（移动与按下是两次独立注入）。
真机实测（2026-10-20，M0 起那条链路）：`pre_move=60.5ms / hold=44.4ms` ✓（`docs/00-现状.md` §6.1）。

**C-04 · 坐标空间必须显式声明，禁止用阈值猜** —— `screenshot` 的 `region` 是物理像素矩形，
缝在动作参数里显式带上 `space="physical-surface"`（与 `click` 的 `x/y` 同一口径）；
执行器**不按数值大小猜**任何空间。证据：`seam.py:497-508`、`executor.py:347-369`。

**C-15 · 界面内容会带出敏感数据** —— 新增的 `params` 字段**不落输入文本的正文**
（`_UNRECORDED_PARAM_KEYS = {"text"}`）；截图仍然**只落哈希不落原图**
（`ActionResult.captured` 的 `to_dict()` 只给尺寸与 SHA-256）。
证据：`records.py:54-61`、`protocol.py:186-210`。

**§3「越界不 clamp，直接报错」** —— `screenshot` 的 region 越出虚拟桌面时
**直接报 `clipped_by_desktop`，不夹取**（越界容差 2 px，与动作越界容差同一个常量）。
证据：`seam.py:440-449`、`seam.py:482-495`、`geometry.py:76-89`；单测 `test_action_seam.py:595-621`。

**C-02 · `ctypes` 的 `INPUT` 必须是 union** —— 本轮未触碰注入层，原型自检不变。

## 3. 与工单假设不符的现实

1. **工单说「M0 已接线这 12 个里的 10 个，只缺 `screenshot` 与 `wait`」——实际不止缺两个。**
   M0 的动作种类集合与架构备忘 §3 **对不上**：多出 `double_click` / `right_click`
   两种（它们后来被收敛成 `click` 的参数），`type` 当时叫 `type_text`。
   本轮实际动的是**三处**：补 2 种、删 2 种、改 1 个名字。
2. **端口的形状不许变** —— 区域截图塞不进既有的 `CaptureSource.capture()`（无参）。
   本轮**新增**端口（`ScreenshotPort` / `RegionCaptureSource`）而不是改既有端口的形状
   （`CONTEXT.md` 的端口条款）。
3. **动作记录原来不带参数** —— 双击与两次单击原先靠**动作种类**区分。
   收敛成 `click` 的参数后，记录必须带上参数才仍能区分（`click_count=2` vs 缺省）。
4. **`button` 的 1/3 是协议自己的口径**，不是 Win32 的 `MK_*` 标志位
   （Win32 的右键是 `MK_RBUTTON=2`）。按工单写死为 1 = 左键、3 = 右键。
5. **截图与等待没有最终落点** —— 缝原本只接受「需要一个落点的动作种类」。
   本轮把它们单列成一类（`STANDALONE_KINDS`），落点为 `None`，
   但**返回形状与既有动作一致**（动作 + 落点 + 意图 + 结果），同样产出恰好一条记录。
6. **真机区域抓取的矩形口径与冻结原型不同** —— 冻结原型的 `capture.grab_frame`
   收的是 `(left, top, width, height)`，本项目的矩形一律是 `(left, top, right, bottom)`。
   换算收到 `geometry.rect_size()` **一处**（真机核对实测：区域 (100,200,500,600)
   → 400×400、原点 (100,200)）。
7. **协议版本口径原先写死了「不在 v1 上加字段」，与本轮加 `captured` 冲突** ——
   口径已改写成「**只增不改**地加字段不升版本；改含义或删字段才升版本」
   （`protocol.py:41-46` + `docs/tickets/README.md`「协议版本口径」条）。

## 一、现状与统计问题

T1–T4 全过，但 **n=4 时 4/4 零失败的 95% Clopper-Pearson 下界只有 47%**
（0.05^(1/4) ≈ 0.4729）——这个结果在统计上和一个「成功率不到一半的 agent」
**无法区分**。要声称 ≥80% 需 **n≥14**；≥90% 需 n≥29。

当前 n=4 的诚实表述：**「四条任务在这一夜按登记口径全部通过」**，
不是「成功率 100%」。

## 二、扩样方案（执行时可照抄）

1. **任务数**：T1–T10 全部实现并实跑（T5–T10 规格在
   `docs/w4-long-tasks.md`，评测台 `scripts/w4_long_tasks.py` 共用）；
   n≥14 意味着还要补 T11–T14（规格先补再跑）。
2. **seed ≥3**：每任务跑 ≥3 个 seed（故障注入参数、窗口位置、随机延迟），
   报 **pass^k**（τ-bench 口径，arXiv 2406.12045）——同一任务 3 个 seed
   全过才算一个 pass^k 单元，**不只是 pass@1**。
3. **无故障对照臂**：同批任务**不注入故障**也跑一遍。没有对照，就无法
   证明注入的故障真的起了约束作用 —— 一个 agent 没察觉到的故障，和一次
   失效的注入，观测上是同一件事。
4. **区间口径**：报 Wilson 95% CI，不只报点估计；样本不够就说不够。

## 三、判分口径：判据清单 + 主口径（治 T4 那种歧义）

**T4 的教训**：预登记了两套读法（「终态符合意图」= pass vs「逐行精确
相等」= fail）结果两套并排写、没裁决。**主口径必须在开跑前裁定**：

* **主口径 = 确定性执行式判据**（OSWorld 风格，arXiv 2404.07972）：
  文件内容 diff、控件状态、退出码 —— 机器可验，轮不到人选读法。
  T4 若当时用「输出文件逐行 diff」，歧义自动消失。
* **敏感性分析 = 「终态符合意图」的宽口径**：单独一列并排报告，
  明确标注它是敏感性、不是主结果。**不许两个都算「结果」。**

**判据清单示例（T4 的机器可验版，预留给下一批执行）**：

| # | 判据 | 机器验证方式 | 副作用类 |
|---|---|---|---|
| 1 | 输出文件存在 | `Path.is_file()` | — |
| 2 | 换算值逐行正确 | 读文件 → 与期望序列精确比对 | 是（保存） |
| 3 | 保存有可见回执 | 记事本标题栏脏标记消失 / 文件 mtime 更新 | 是 |
| 4 | 原模板未破坏 | 模板文件逐行 diff = 原样 | — |
| 5 | 文件尾部无陈旧残留 | 输出文件行数 = 期望行数（第 6 行起无缓冲残留） | — |

用法：`CompletenessChecker([...5 条...])`；每步 `note_observation(指纹)` +
`in_progress_check`（零模型调用）；`done()` 时 `final_gate`（第二段）——
驳回时 `missing` 写「缺哪条证据」回轨迹，保留部分进展。
组件与测试见 `src/minicode/reflection/completeness.py`（9 用例全绿）。

## 四、与 Loop Breaker 的关系

* Loop Breaker（`docs/loop-breaker.md`）管「卡住怎么办」，Completeness
  管「什么时候算完」——两者正交，都接在 `w4_long_tasks.py` 的 attempt
  循环上。
* 三个数分开的账本（遭遇 / 触发 / 救回）与 pass^k 并列报告，不混。

## 五、成本与预算的诚实口径

* 加 Completeness 会把「错误的完成宣称」从 105 降到 91（VLAA-GUI 口径），
  **仍有 86%+ 的失败以错误的完成宣称收尾** —— 它改善，不解决。
* Windows Agent Arena 上去掉它掉 −9.7pp（OSWorld 只 −2.86pp）——
  本仓纯 Windows，边际价值高，这是「为什么做」的依据。
* Loop Breaker 是**长任务专用件**（买步数不买成功率，见
  `docs/loop-breaker.md` §5）。

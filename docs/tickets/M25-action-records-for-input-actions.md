## What to build

**这是一个真 bug，不是待选的口径**（2026-10-21 人已确认方向）：决策层动作程序里的 `type_text` / `press_key` 直接调动作执行器（`decision/api.py`），**不走动作执行缝** → 这两种动作**产出零条动作记录**。

它直接违反 M17 的字段完整性口径：「**动作下发过却没有动作类型 = 缺字段**」—— 动作确实下发了（真的往桌面敲了字），记录里却没有。

对外形态（M18 的 CLI / HTTP、M19 的 MCP）把这条路径**放大**了：MCP 程序能 `type_text` 却零动作记录，意味着「出了事看日志」这件事在 MCP 这一层是**假的**。

本单要做的：让输入类动作也**产出动作记录**，且**不新立第二道缝**。

- 两条路可选，**推荐 (a)**：
  - **(a)** 把 `type` / `key` 纳入动作执行缝（`action/protocol.py::SEAM_ACTION_KINDS`），由缝统一产动作记录 —— 缝是**唯一测试缝**（ADR-0007），所有下发路径都该经过它。
  - (b) 在 `decision/api.py` 那侧直接产追踪记录 —— 改动小，但**等于承认第二条缝**，与 ADR-0007 冲突。
- ⚠️ `type` / `key` **已经在 12 个已锁的动作种类里**（M21 锁的是**种类集合**，不是「哪几种已接线」）；本单不新增动作种类，只把它们**接线**。

## Acceptance criteria

- [ ] 输入类动作产出动作记录：跑一段含 `type_text` / `press_key` 的动作程序 → 动作日志里**每一步都有动作记录**，动作类型分别是 `type` / `key`，落点/窗口句柄等字段按动作种类的合格口径（`type` / `key` **不需要落点**）。
- [ ] 不违反 M17 的字段完整性：动作下发过就**必有**动作类型；用 M17 的回放口径核对这份日志 → **零缺项**。
- [ ] 不新立第二道缝：输入类动作**走动作执行缝**（`SEAM_ACTION_KINDS` 纳入 `type` / `key`），`decision/api.py` 不再直接调执行器产记录；全仓检索断言**没有第二处**直接产动作记录的路径。
- [ ] 缝的既有契约不破：`SEAM_ACTION_KINDS` 是「缝的能力」的唯一定义（`action/protocol.py`），**动作执行缝自己**与**对外形态层**（`minicode/serve`）**都引用它** —— 纳入新种类后两处**自动一致**，不许各写一遍；M18 的「缝不接的种类」那条断言同步更新。
- [ ] M21 的锁断言同步：动作种类**集合仍是 12 个**（`ActionKind` 的取值一个不多一个不少）；「已接线 9 / 延后 3」这两个**计数**随接线变化，断言改成与新实现一致（**锁的是集合，不是计数**）。
- [ ] 对外形态同步：MCP / HTTP / CLI 发起含 `type` / `key` 的程序后，能在动作日志里读回这两步的记录（不再出现「动作做了、日志里没有」）。
- [ ] 文档同步：`docs/00-现状.md` 的决策层那节与 `CONTEXT.md` 的「动作记录」词条同步（**动作记录是动作日志的来源**——这条现在对输入类动作不成立）。

## 已在工单里写死的口径

以下几处在规格与相关决策记录之间存在互斥表述，本轮已按下列措辞**统一改到文档与工单**（改过的位置见各文件的修订清单）：

- **动作种类集合 = 架构决策备忘 §3 的 12 个**（M21）：`cua.action/1` 的动作种类以 screenshot / click / move / drag / type / key / scroll / wait / zoom / inspect / execute_code / ask_user 这 12 个为准；**双击与右键是 `click` 的参数**（`click_count` / `button`），不是独立动作种类。M0 已接线其中 10 个，**缺口只有 `screenshot` 与 `wait`**（M21 补齐，并加一条断言把这份集合锁死，防再漂移）。M10 的阻塞边因此加上 M21——harness 要用**完整协议**。
- **协议版本口径**（M21）：`cua.action/1` **只增不改**地加字段（如 `ActionResult.captured`）**不升版本**；**改已有字段的含义或删字段**才升版本。（M21 的 AC 4 写死了「不升版本」——那是在「只加字段」的前提下。）
- **唯一性拒绝与消歧**（M3、M4）：**候选不唯一时先做消歧**——在 UIA 候选集内让模型**只做指认**（候选唯一时零模型调用；指认必须落在候选集内且恰好一个）。消歧失败、**候选数超过上限**（默认 8）、或指认不唯一 → 走 L4 错误处理。**任何情况下都不切视觉。**
- **消歧的实现形态**（M4）：模型**只答「候选清单里的第几行」**（行号 → 元素 id 的映射在本地做）；**请求里不出现「输出坐标」这类措辞，也没有任何坐标换算提示**；送模型的是**已脱敏**的候选清单与那一帧画面（**脱敏器是模型侧文本的唯一出口**）。**脱敏没上线 → 这条通道被拒绝启用**（明确错误、零模型调用）。
- **两类失败的判定口径**（M4）：**候选集为空 = 覆盖失败**（可切视觉）／**候选集非空但选不出 = 选择失败**（禁止切视觉）；两类**标识不同、互不混淆**，**只有覆盖失败**被标记为允许切视觉。「名称匹配不上」若还有退路（控件类型条件查询）就还没到覆盖失败。已同步进 `docs/spec.md`、架构决策备忘 §2.5 ① 与 ADR-0004。
- **每步回显**（M4）：回显给的是**模型自己发出的东西 + 实际发送的图片尺寸**——**视觉通道**是坐标，**UIA 通道的消歧是选中项**（候选行号 + 控件名）。**UIA 通道的模型不产坐标，回显里不许伪造成坐标回显**。
- **标度判定与落点等价**（M5）：**落点等价判据**——标定探针给出候选标度族；只有在**存在使物理落点分歧 > 标定容差（1 px）的替代标度**时，视觉通道才不可用。分歧 ≤ 容差的等价标度族**允许继续**（等价列表必须落盘），但**标度判定**如实记为**多解**。**前提**：探针必须含最右边缘目标——0~999 与 0~1000 的物理分歧随 x 线性增长、最大值在右边缘，探针不覆盖最坏情况则本判据悄悄失效。
  > 📌 **「替代标度」= 探针排除不掉的那些标度（候选族），不是全部候选**（M5 实现时澄清）：否则 0~999 这种永远存在的候选会让视觉通道**永远**不可用（2560 宽探针上它与 0~1000 的分歧恒为 2.87 px > 1 px）。**等价标度列表**是**事实**（探针分辨不出的那一族），**准入判定**是**决定**（那一族里有没有会让落点挪出容差的标度）——两个维度分开报，不许混成一个字段。
- **可分辨安全系数**（M5）：**等价标度列表**的判据是「落点分歧 ≥ **2 × 标定容差** 才算探针能分辨」；分辨力不足时按**等价**处理（进列表、如实报多解），不假装能分辨。理由：工单 M5 AC 2 的两条断言（「2560 宽 + 容差 2.0 → 0~999 进等价列表」「1280 宽 + 容差 1.0 → 判为等价」）与「分歧 ≤ 容差」的 1× 判据**互斥**（真实分歧是 2.87 px 与 1.43 px，1× 判据下两条都不成立）；2× 判据让两条断言都成立，且真实配置（2560 宽 + 1 px）仍能分开 0~999 与 0~1000（2.87 ≥ 2.0）。**硬闸门仍用 1× 容差**（架构备忘 C-03 原文）：候选族里存在分歧 > 1 px 的标度 → 视觉通道不可用。
- **等价列表含判定标度自己**（M5）：等价标度列表 = **{判定标度} ∪ {探针排除不掉的标度}**；「唯一命中」= 列表里只有判定标度自己。工单 M5 AC 5 要求「两种绝对标度同入等价标度列表」，因此判定标度必须在列表里。
- **两条调用路径各标定一次**（M5）：**文本调用**与**图像调用**各产出一份标定记录、各自独立存储、**互不借用**（任一路径没记录或标定失败，另一条路径的标度不许顶上来）。存储按 **(模型, 调用路径)** 取用。⚠️ 文本路径没有画面，测的是模型在**纯文本**上下文里的坐标习惯，**不能**替代图像路径的标定。
- **绝对像素候选的基准是「模型实际看到的那张图」**（M5）：**服务端可能把大图缩小**（本机实测：MiniMax 端点把 2560×1600 缩到约 2048×1280），模型回的绝对像素落在**缩小后那张图**上。按「我们发出去的那张」当基准会判成另一个标度（实测误差 571.79 px）；把缩小后的尺寸**声明**进来（量出来的、不是猜的）后，判定标度从 `absolute_capture` 变成 `absolute_model_input`，误差降到 2.66 px。
- **截图只落哈希**（M0）：**M0 管「落盘留什么」**（只留哈希，不落原图）；**M20 管「哪些窗口根本不许拍 / 不许发」**（发送前的黑名单 + 剪贴板读取审批）。两层不重叠。
- **0.07% 这个阈值**（M7）：它是 **数据集统计**（ScreenSpot-Pro 目标平均占图面积，论文给出）、**未验证的阈值**——必须做成运行时参数并记录取值来源（M7 已落地：门控参数 `GateParams`，默认值带来源串，单测钉死凡出现 0.07% 必带这两个标注）。
- **门控有三态，不只有两态**（M7）：**命中 / 不命中 / 不可判定**。「不可判定」= 该条件的输入缺失（如粗定位**只给点不给框** → 目标占比判不了；模型不报置信度 → 置信度判不了；没做第二次独立粗定位 → 一致性判不了）。不可判定的条件**不触发、也不否决其余三条**，且**必须显式记进追踪记录**（`gate_undecidable`）——静默判不了是最难查的一类失败。
- **门控参数是运行时参数，取值来源必须被记录**（M7）：每个阈值配一个 `*_source` 串（占比 / 置信度 / 一致性容差 / 偏离容差），随门控判定一起落盘。没有可靠来源的阈值，来源串写「工程阈值·未验证」，**不许写成已验证结论**。
- **「允许切视觉」是运行时开关**（M7）：`on_demand`（门控开 = 按需触发，工单 M7 默认）/ `always`（门控关 = 无条件精定位，工单 M8 的对照组）。测量台用 `--gate-mode` 切两臂；两臂的样本必须**同一批**才可比。**不要叫它「策略/开关」** —— `CONTEXT.md` 的「门控」词条把这两个说法列为 avoid。
- **失败类型与红线只有一份映射**（M9）：错误码 → **失败类型** → **允许切视觉**，
  映射在 `src/minicode/action/errors.py`（`FAILURE_TYPE_BY_CODE` + `allows_visual_fallback`），
  **红线只有一处**：只有**覆盖失败**（`coverage`）允许切视觉。
  失败类型有五值：`coverage`（覆盖失败）/ `selection`（选择失败）/ `execution`（执行失败）/
  `channel`（通道级失败：查询超时、通道被拒绝启用）/ `decision`（决策失败：动作程序被拒）。
  ⚠️ 工单 M9 AC 7 字面写的是「三类」；本轮**多列了两类**（channel / decision）——
  理由：**查询超时既不是覆盖失败（我们并不知道目标在不在树里）也不是选择失败（压根没有候选）**，
  **决策失败是 `CONTEXT.md` 里的既有概念**；硬塞进前三类就正是 AC 7 禁掉的「混淆」。
  ⚠️ 别与 `CONTEXT.md` 的「三类失败」（定位 / 决策 / 执行，**埋点轴**，记在追踪记录的 `failures` 里）混用 ——
  两套正交。
- **「名称匹配不上」怎么判**（M9）：**候选集空不空**是判据（README 上面那条 M4 口径的延续）：
  条件查询**找到了候选**却没有一个与描述对得上 → **选择失败**（禁止切视觉，工单 M9 AC 2）；
  条件查询**一个都没找到** → 覆盖失败（允许切视觉；含 0 节点 = 通道产不出候选）。
  ⚠️ 工单 M9 AC 2 的措辞是「名称匹配不上**一律**禁止切视觉」，与 README 的
  「退路（控件类型条件查询）也找不到 = 覆盖失败」在**没有退路**的情形下有出入 ——
  本轮按 README 口径（晚出的统一口径）实现，**待人拍板**（`docs/reviews/M9.md` §5）。
  → **2026-10-21 已拍板**（见本节下面「名称匹配不上按候选集空不空判」那条）；M9 AC 2 已改写。
- **门控命中率的定义**（M7）：**开启精定位的样本数 ÷ 总样本数**；**回落率 = 回落次数 ÷ 开启精定位的样本数**。这两个数与**同一张表的分数**必须来自**同一批样本**（报告与分数共用同一批 outcome）。
- **偏离粗定位也算精定位失败**（M7）：精定位结果离粗定位超过设定量级（默认 128 px = 512 裁剪窗口边长的 1/4，**未验证**）→ **回落到粗定位结果**。⚠️ 它量的是「离粗定位多远」，**不是**「离真值多远」——粗定位本身就偏时两者会同向漂移（实测漏过一次 207 px 的误选）。
- **粗定位为空或越界时开的是「整屏第二遍」**（M7）：不是围绕粗点的裁剪窗口（没有粗点就没有窗口中心）；它**不是逐字重发**同一条请求（提示词里带上了「上一次没能给出可用的位置」），也**显式记进回显**（`stage="whole_screen"`）—— 不是静默重试。它失败则**报定位失败**（没有可回落的结果，不落点、不挪到别处）。
- **门控未命中时最终落点 = 整屏粗定位点**（M7）：这是坐标契约（「视觉通道内最终落点只在 crop 尺度上产生」）的**一条例外**，只在这一条路径上成立 —— 记在 `docs/00-现状.md` §3 与 ADR-0006 的补充说明里。
- **「开启精定位」只指 crop 精定位**（M7）：**整屏第二遍不算**（它不是 crop 精定位，也永不回落）→ 门控命中率的分子只数 crop 精定位。
- **评测脚本的坐标口径**（M7，决策记录 `docs/adr/0008-eval-script-coordinate-formats.md`）：内部一律**原图像素**，各家脚本的坐标期望**只在 wrapper 返回前转一次**；转换的唯一一处是 `src/minicode/eval/formats.py`。
  - **ShowUI 的网格值 = 1000**（不是 999）：实际脚本 `main/eval_screenspot.py::get_bbox` 写的是 `int(item * 1000)`，系统提示词写「scaled from 1 to 1000」。底稿的「0–999/1000 两说」到此为止。
  - **ShowUI 与 CCF 的 GT bbox 都是宽高形式**（`[x,y,W,H]`），SSPro 官方与 ZoomClick 副本是 `[x1,y1,x2,y2]`；point 的形状又各不相同（归一化 / 像素 / 网格）——**GT 与 point 形状是两两独立的**，宽高形式当 xyxy 读会让命中结论反过来。
  - **「接了官方脚本但分数全 0」是能自己造出来的**（像素点喂给归一化脚本 → 命中率恰好 0，不报错）→ **防假象自检是必做项**：GT 中心当预测点，命中率必须 ≈100%。
- **两套命名分属不同域**（M7、M8）：**模型侧**叫「量纲分母」（只能来自运行时标定）；**目标评测脚本侧**的坐标格式常量（如 0–999 网格、`[x,y,W,H]` 宽高形式 bbox）是**输出格式**，不是量纲分母。目标脚本的取值**以脚本实际值为准并钉进单测**，不许凭二手记录取值（底稿里 ShowUI 的网格值是 0–999/1000 两说且该仓本轮未 clone 核实）。
- **冻结原型的结构例外**（口径 5）：允许对三个原型做**一次**包化改动——只动包结构与导入路径，不改任何逻辑、不改任何数值；包化前后那 50 个单测**逐个通过且输出逐字节相同**。该例外记在 `docs/00-现状.md` 的原型表里，**不写 ADR**（不满足「难逆转」，够不上 ADR 门槛）。
- **「视觉兜底层」保留**（M9）：这是规格原文的复合词，指通道的角色；**通道切换一律叫「切视觉」**，不叫兜底。
- **决策层的产出形态 = 一段动作程序**（M10，ADR-0005）：模型针对当前观察产出**一段程序**（可含 if/for、可调用定位与动作接口），harness 在**受控环境**里执行，把标准输出、异常与新截图回灌给模型；**多步任务一次跑完，不用每步问一次用户**。逐条吐动作是**被否掉的形态**（README 可核的两组数方向相反）。
- **协议里没有「完成」**（M10）：动作协议的取值集合里**不存在** finished / terminate 之类的完成动作；**模型自称完成不算数**（harness 只把这类表述计数，不据此停止），**终止只由 harness 侧的停止条件承载**（程序请求交还给人 / 轮次上限 / 后票的期望断言）。
- **思考预算（effort）分工**（M10）：**规划步与反思步 = high**，**动作步 = low**（动作步的模型请求在动作路径里，如消歧指认，`uia/pointer.py` 的 `DEFAULT_EFFORT`）；**每次请求都必须显式给档位**，请求日志逐条带档位字段，**未传档位的调用数恒为 0**。
- **上下文成本的口径**（M10）：**完整截图只留最近 2~4 张**，更早的帧压成**结构摘要**（尺寸 + 截图哈希 + 那一轮发生了什么）；**成本主控杆是历史上下文里的截图长度**，不是模型单价。验收记录要给**连续多步的输入 token 增长曲线**（图片项在张数上限处封顶，文本项仍线性增长）。
- **受控执行**（M10）：动作程序**只能调用动作协议暴露的动作**（白名单：`click` / `find` / `type_text` / `press_key` / `wait` / `screenshot` / `ask_user`）；**任意系统调用与任意文件写入在执行前就被拒**（`import` / `open` / `eval` / `exec` / 双下划线属性 / 含双下划线的字符串常量），错误码 `program_rejected`，**被拒时零动作下发**。⚠️ 这是**白名单 + 静态扫描**，**不是操作系统级隔离**（真要当不可信代码跑要另做进程级隔离，后票）。
- **决策层不进单测缝**（M10）：决策层（模型产出程序、循环推进、上下文裁剪）**没有单测覆盖**，其验收落在**端到端评测**上 —— 这是**明确承担的分工**（缝只有动作执行缝一条）；受控执行环境的契约由 `action/program.py` 的单测承担（测的是动作协议里 `execute_code` 这一类动作的执行契约）。
- **harness 增益的引用纪律**（M10，检查项 **C-13**）：只许引用官方仓库 README 正文里的两组数（换 harness **+19.6 分 / 步数 −53%**、代码执行 vs 同等 GUI+CLI 权限 **+6.1 分 / 步数 −14.8%**）；另一组更宽的区间（**+15.5~+33.6 分 / 步数 −55~63%**）**不在 README 正文**，**只允许出现在「禁用/未核」说明句里**，其余每一处都必须带 **arXiv 2610.22200 的消融表号** —— 全库扫描守卫已落进 `src/minicode/model/test_citation_discipline.py`。
- **「分布不劣于」的判据**（M6）：工单 AC 9 的「精定位那一级的分布不劣于粗定位」= **中位数与 p90 都不劣**（最大值只报告、不作判据：单点抖动不该判不合格）。「分布」一律按**一组目标**统计，不报单点数字。
- **「≤16 px 的小图标」按逻辑像素读**（M6）：ScreenSpot-Pro 的口径是 1920×1080 画面里的 16 px 图标；本机 150% 缩放下 = **24 物理像素**。判据取控件框**最短边** ≤ 16 逻辑像素（本机可枚举到的最小目标：`显示桌面` 12×48 逻辑 px、天气小组件的文字 23×16 逻辑 px）。
- **准入门只管生产路径**（M6）：M5 的硬闸门（标定失败 / 存在分歧的替代标度 → 视觉通道不可用）**只对生产路径生效**；工单 M6 AC 9 的分布回归**测量台**如实报告准入判定，并**用标定判出的标度**继续测量（它只回答「两级 grounding 的落点误差分布」这一个问题）。生产路径上，标定没过就是**不可用** —— 测量台不改变这一点。
- **粗定位只给点、不给框**（M6）：两级 grounding 的裁剪计划保证的是**粗定位点完整落在窗口内**；「目标是否完整包含」按**目标半径**判定（`target_fully_contained` 属性），没给半径时该属性按「点在内」为真。
- **视觉通道的模型输入尺寸来自标定记录**（M6）：服务端把整屏大图缩小时，模型回的绝对像素落在**缩小后那张图**上（M5 的口径）。整屏那一级的换算基准 = **标定记录里的 `model_input_width/height`**（探针与整屏图同尺寸 → 同一套缩图规则）；裁剪那一级默认 1:1（crop 尺寸），可由构造参数显式声明。**每步回显报的是「模型实际看到的那张图」的尺寸**（不是原图宽）—— 模型要靠它对账自己的坐标。
- **期望判的是「变化」，不是「状态」**（M11）：工单的字面是「某个按钮**变成**不可用」「某段文本**出现**」，
  AC 1 也写「**状态变化 / 文本出现**」→ 断言的是「动作之后 X 现在是这个状态」
  **且**这次动作**促成了**它（动作之前它不是这个状态）。
  「本来就在」判成**不成立**（真机复现：任务栏那个「开始」按钮本来就在 → 期望「文本出现」不成立）。
  ⚠️ 这比「只判状态」严格 —— 它能抓住「期望早就成立、动作其实没做功」这类**静默失败**。
  ⚠️ 代价：校验因此是**两段式**（动作**之前**取一次基线观测、动作**之后**再观测一次，两次对照）；
  基线读不出来 → **判不了**（不是「不成立」）。
  ⚠️ **别把「期望」说成「后置条件」** —— `CONTEXT.md` 的「期望」词条把它列为 avoid。
- **三种验证手段各判各的，判据取并**（M11）：可访问性树判**状态 / 存在性 / 矩形**；
  文本比对判**文本出现或消失**；**像素差分只判「界面有没有变」**（通用条件），
  **不判具体期望**（「像素变化 ≠ 成功」）。任一能判的手段说「成立」即成立；
  全都判不了 → 「**判不了**」（**判不了 ≠ 不成立**）。**模型不参与裁判**（校验层零模型调用）。
- **「界面无变化」不是失败**（M11）：默认校验（没有期望时）只给**信号**
  ——「有反应 / 界面无变化」；**无变化 ≠ 失败**、**有变化 ≠ 成功**。
  只有**期望明确不成立**时才算失败（错误码 `expectation_failed`，归**执行失败**）。
- **变化率的单位是「块」**（M11）：一帧切成 **8×8 像素块**，每块压成一个 **32 位**值做**精确比较**，
  变化率 = **变化的块数 ÷ 总块数**，阈值 **1%**。
  ⚠️ 工单字面写的是「1% **像素**变化」—— 本轮取**块级**（抗噪；像素级会被抗锯齿与光标闪烁淹没），
  **待人拍板**（`docs/reviews/M11.md` §5）。
  → **2026-10-21 已拍板**（见本节下面「变化率取块级」那条）；M11 AC 2 已改写。
- **轮询节奏与早收工**（M11）：**首次立即 → 100 ms 内 15 ms 节奏 → 之后 20 Hz**（50 ms）；
  判定顺序**有反应 → 安定 → 返回**；**变化率低于 1% 且持续两帧** → 报「界面无变化」。
  ⚠️ 早收工只对**默认校验**成立：**有期望时**不早收工（否则「界面还没生效」会被误判成「没生效」）。
  两个等待上限（反应 2 s / 安定 2 s）是**工程阈值·未验证**。
- **三段耗时与三类失败有两个粒度**（M11）：**单步**（追踪记录 / 动作记录：三段各有值 + 单步的三段占比、三类分开记）
  与**整任务**（三段合计 + 各自占比、三类失败次数 + 占比）。
  ⚠️ **决策段耗时是轮级的量**（一次规划 → 一轮 → 可能产出多个动作）：
  它**累加**后记在**轮内第一个动作**上（同一轮的后续动作记 0），
  整任务的决策段合计由**决策层单独报**（不重复计数）。
- **期望断言的失败类型是「执行失败」**（M11）：新错误码 `expectation_failed`（只加不改，协议版本不升），
  归**执行失败**（它在「执行+校验」这一段里没达成目标）。
- **UIA 的 `IsEnabled` 属性 ID 是实测出来的**（M11）：**30010**（2026-10-21 在本机造两个原生按钮
  —— 一个可用、一个 `EnableWindow(FALSE)` —— 把 30000~30060 逐个读过去，唯一给出
  「可用=True / 不可用=False」的 ID）；⚠️ 常见写法 **30022 在本机读出来恒为 False**（是别的属性）。
  读不出来时按**可用**算（「读不到 ≠ 不可用」）。出处：`src/minicode/uia/windows.py`。
- **浏览器通道的「点击」走「浏览器自己的输入通道」**（M13）：CDP 的 `Input.dispatchMouseEvent`，
  **不走桌面鼠标注入**；动作协议仍是同一套 12 个动作，落点仍是**物理表面空间**（物理像素）。
  ⚠️ **文本输入是另一条路**：先走**桌面注入**（与桌面通道同一套动作语义 → 同一个 `type` 动作，
  粘贴通道带剪贴板备份与恢复），**浏览器收不到键盘事件时**才退到浏览器自己的输入通道

- **页面元素 → 控件候选**（M13）：两条通道产出**同一种形状**（`ControlCandidate`）→
  脱敏器、消歧（模型只做指认）、动作记录**全都只有一套**；「与桌面通道同语义」不是口号，
  是**同一个 `ControlLocator` 端口**被两个通道实现。

- **CSS→物理的比例是量出来的**（M13）：比例 = **物理窗口宽 ÷ CSS 外框宽**

- **退化必须留一笔**（M13）：退到浏览器自己的输入通道是**退路**，用了就在结果里记

- **能力表按通道分表**（M13）：UIA 一张、浏览器一张，**三态与「应用 + 版本」的键共用**

  重新感知之后坐标会变，而「同一个动作」指的是「同一件事」（点同一个目标）。
- **换策略的阶梯**（M12）：换裁剪尺寸 → 换定位级别 → 改键盘 → **请求人工**；
  **阶梯用尽 = 交人**（停止原因写明是「换策略用尽」，不是「轮次上限」）。
- **可重试的动作种类**（M12）：**移动 / 滚动**天然可逆；**点击**看目标 ——
  命中**不可逆词表**（发消息 / 支付 / 删除等）就不重试；

- **退避表 = 200 / 500 / 1200 ms，上限 3 次**（M12，工单 AC 3 写死）；

- **目标级期望 ≠ 单步断言**（M12）：单步断言不成立 → **这一步失败**

  （那是「还没到」，归反思层管），**成立则任务达成**（停止原因 `expectation_met`）。
  目标级期望**跟着每一步走** —— 「由 harness 决定它落在哪一步」的实现口径。
- **提权 / 安全桌面 = 零动作交人**（M12，C-07）：检测到就**不下发任何注入**，

- **模型自评置信度不作放行条件**（M12）：实测存在**高置信度的错误**，

  因此危险动作的放行判据里**没有任何置信度输入**（单测扫源码把住这条）。
- **危险动作审批与 dry-run 属于 M16**（M12 AC 9）：本单只做

- **端到端评测的判定口径**（M14）：判定只有四个取值 ——
  `pass` / `fail` / `skip` / `pending_human`。
  **跳过永远不算通过**（自动通过率的分母只算「通过 + 失败」）；
  **人工代确认单独统计**（标注「人工代确认」的任务**不自动执行**，记 `pending_human`）；
  **「判不了」落在 `fail`**（判不了不是「不成立」，但**不许被记成通过**）。
- **每步都要有结构断言**（M14）：没有结构断言的步骤**建不出来**

  工单 AC1 的字面读法会让**定位阶段就失败的步骤**永远不合格（那种步骤
  没有下发动作 → 没有动作类型、没有落点、没有窗口句柄）。本轮按
  **不适用就不算缺**实现（口径见 `docs/reviews/M17.md` §5 ①，**待人拍板**）。
  → **2026-10-21 已拍板**（见本节下面「字段完整按动作种类的合格」那条）；M17 AC 1 已改写。

- **标定的三层与准入判据**（M22，2026-10-21 拍板，**改了 C-03**）：①**标度判定**（探针唯一命中 / 多解——事实）②**落点等价**（等价标度族内各标度给出的物理落点分歧——事实）③**准入**（决定）。
  **准入 = 能定案（唯一 or 落点等价）且等价族内最大落点分歧 ≤ 落点容差 2.0 px**；存在分歧 > 2.0 px 的替代标度 → 视觉通道不可用。
  ⚠️ **不再要求「探针唯一命中且 max_error ≤ 1.0 px」**——实测证明它对真 VLM 不可达：模型自身在 2560 宽画面上的定位误差 **2.66~4.03 px**（M5）、同一张探针五轮真调最大误差 **2.14~22.24 px**（M6），都 > 1 px；而我们要用 1 px 的探针分辨 0~999 vs 0~1000（右边缘分歧 **2.56 px**）——**信号比噪声小**。
  **防线未放松**：2.56 px > 落点容差 2.0 px → 仍会被拦下（前提：探针含最右边缘目标）。
  **三个容差各归各的**：判定容差 1.0 px（探针分辨力）、落点容差 2.0 px（等价族分歧）、动作越界容差 2.0 px（动作层）——**三个独立常量**。
  **探针分辨力判据**（探针自己分不分得出候选标度）：落点分歧 ≥ **2 × 判定容差** 才算能分辨，否则按等价处理——**准入不靠它**，它只决定等价列表怎么划。
  **视觉通道的落点精度线按通道分**：UIA 通道 ≤2 px（实测 0.0 px）；视觉通道的线按实测分布定（M9 三轮 2.2~6.7 px、M7 crop 精定位中位数 15.03 px）——**「≤2 px」是 UIA 通道的量级**。→ M22。
- **门控结论必须用留出集**（M23，2026-10-21 拍板）：M8 的「门控开 59.5% ≥ 门控关 57.1%」是**在同一批样本上调一致性容差（128→16 px）得到的**——**同批调参 + 同批评估 = 过拟合，该结论作废**。M8 自记的噪声量级（两臂仍有 35/42 条粗定位点不同、最大差 3062 px、11 条命中与否翻转）与要测的效应（+2.4 pp）**同量级**。
  **判据**：阈值只在样本 A 上调，**结论只在样本 B 上成立**；B 上的差值 **≤ 噪声量级 → 判「不成立」**。A/B 切分按样本 ID 固定切分、每条样本归属落进报告。M8 原数字必须标注「不可作结论」。→ M23。
- **放大的坐标契约 = 图内坐标 + 物理原点**（M14 实测，2026-10-21 拍板）：**Anthropic 的 zoom 契约（模型报整屏坐标）在本机模型上不成立**——提示词里的区域原点用的是模型坐标系，而模型在放大图里报的是**图的像素**（1:1 物理像素），两套口径混用 → 答案系统性越界 → 动作被拒（不夹取）。改用 crop 那一套后实测偏差 **14.0 px**（对包围盒中心 **1.1 px**）。
  **放大与裁剪现在共用同一套坐标契约**（都是图内坐标 + 原点偏移），区别在**用途与取景来源**：放大是主动要看清某片视野（回源重抓），裁剪是定位环节取的景。→ `CONTEXT.md`「放大」词条、架构备忘 §1.3.1(a)、M6/M14 的 AC 都已改写。
- **「名称匹配不上」按候选集空不空判**（M9，2026-10-21 拍板）：条件查询**找到了候选**但都对不上 → **选择失败**（禁止切视觉）；条件查询**一个都没找到** → **覆盖失败**（允许切视觉）。M9 AC 2 已改写。
- **变化率取块级**（M11，2026-10-21 拍板）：一帧切 8×8 像素块、每块压成 32 位值做精确比较，变化率 = 变化的块数 ÷ 总块数，阈值 1%。工单字面「1% **像素**变化」不可用（抗锯齿与光标闪烁会淹没）——M11 AC 已改写。
- **「字段完整」按动作种类的合格**（M17，2026-10-21 拍板）：需要落点的动作种类必须有落点（物理表面空间），不需要落点的种类（`screenshot` / `wait`）必须没有落点；**定位阶段就失败的步骤没有动作类型是如实的**（动作压根没构造出来），**动作下发过却没有动作类型 = 缺字段**。M17 AC 已改写。
- **「缝接哪几个动作种类」是协议层的一个具名常量**（M18，2026-10-21 拍板）：
  `action/protocol.py::SEAM_ACTION_KINDS`（= `POINT_KINDS | STANDALONE_KINDS | OBSERVATION_KINDS`）
  与 `NEEDS_TARGET_KINDS`（= `POINT_KINDS`）——
  **动作执行缝自己**（`action/seam.py`）与**对外形态层**（`minicode/serve`）**都引用它**，
  同一个集合不许写两遍（两处各写一遍时，读者要回到另一处才能确认两边一致）。
  ⚠️ **放大（`zoom`）不在 `NEEDS_TARGET_KINDS` 里**：它的落点来自 `params["region"]`，
  目标描述只进意图串 → 不带 target 的放大是**合法请求**。- **对外形态只有一个入口实现**（M18，2026-10-21 拍板）：命令行与 HTTP **共用**
  `minicode.serve.service.ActionService` 这一份执行实现（两个前端只做「解析 → 调它 → 渲染」）；
  真机接线也只有一份（`minicode.uia.desktop`，`uia/__main__.py` 与 `serve/real.py` 共用）——
  **不许两份接线各说各话**。
- **坐标不由动作请求给**（M18）：请求里只有「目标描述」，**给了坐标也不认**——
  坐标口径只有动作执行缝那一份（架构备忘 §2.5 ②）。
- **版本对不上 → 明确报错，不按旧语义猜**（M18 AC4）：请求必须带 `protocol`
  （`cua.action/1`）；对不上 → `protocol_version_mismatch` + **零动作下发**。
  ⚠️ **缺 `protocol` 字段也算对不上**（`invalid_request`）——不许默认按当前版本猜着跑。
- **HTTP 状态码与协议错误码是两层**（M18）：**请求层**被拒（版本不匹配 / 形状不对 /
  动作种类不认识）→ HTTP **400**；**动作层**失败（目标找不到、点不动…）→ HTTP **200**，
  成败与**协议错误码**在响应体里 —— 不把协议错误码翻译成 HTTP 状态码。
  ⚠️ 「动作失败」仍是 200 的理由：请求**被受理并执行了**，失败是动作层的事实。
- **请求载荷的键名与响应字段名**（M18）：请求里是 `protocol`（`{"protocol": "cua.action/1", ...}`），
  响应里是 `protocol_version` —— **一个进、一个出**，名字不同（本轮的有意选择）。
  ⚠ **版本号只有一个真值来源**：`action.protocol.PROTOCOL_VERSION`。
- **本轮的 CLI 与 M17 的 `minicode.audit` CLI 是两件事**（M18，回应 M17 §5 ④）：
  `minicode.serve` 是**对外的产品接口**（发起动作、读回结果与动作日志）；
  `minicode.audit` 是**本地离线工具**（只读日志、只写导出文件，不发起任何动作）。
  ⚠️ 两者**都读动作日志**（同一个 `ActionLog`），但**只有 `serve` 会下发动作**。
- **MCP 侧是薄适配**（M19，2026-10-21）：MCP 的三个工具 = 服务里**已有**的三种调用
  —— `minicode_action` → `ActionService.execute`、`minicode_program` → `execute_program`、
  `minicode_observe` → `observe`；**动作语义、坐标口径、错误码各只有既有那一份**。
  ⚠️ **动作种类清单与程序白名单不许在 MCP 侧再写一遍**：
  前者取 `action/protocol.py::SEAM_ACTION_KINDS`，后者取 `action/program.py::PROGRAM_API_NAMES`
  （M18 的「同一个集合不许写两遍」在 MCP 侧同样成立）。
- **动作程序由调用方给**（M19）：宿主（DSH / Claude Code）的模型写那段程序，
  minicode 只在**受控环境**里执行它（`action/program.py`）——MCP 这一层
  **不生成**程序、**不调模型**（那会把「对外形态」变成「决策层」）。
- **观察是定点的，且必须过脱敏**（M19）：协议里的 `inspect`（读控件树）动作种类
  **至今未实现**（`action/protocol.py::DEFERRED_KINDS`），而**全树 dump 被 C-09 禁止**
  → 观察走**定点查询**（必须带名字条件，缺了 → `invalid_request`），
  控件树**只经脱敏器**出去（脱敏没上线 → `channel_disabled`，**一个字符都不给**，C-15）。
  ⚠️ **观察不经过动作执行缝**（它是只读的，不产动作记录）——这与 ADR-0007 的
  「唯一测试缝」冲突。**2026-10-21 已拍板**：把 `inspect` 补成协议里的动作、
  观察改走动作执行缝 → 修票 **M26**。`inspect` 本来就在 12 个已锁种类里，
  本单**只把它从「延后」挪到「已接线」，不新增动作种类**（M21 锁的是**集合**）。
- **MCP 的 stdio 形态下，危险动作永远批不下来**（M19）：审批人在**命令行**里问人，
  而 MCP 的标准输入是**协议流**（不是终端）→ 非交互一律不批（fail-closed）→
  十一类危险动作在 MCP 这一层会被 `approval_denied` 拦下、**零动作下发**。
  → **待人拍板**（`docs/reviews/M19.md` §5 ②：走 MCP elicitation，还是危险动作只走 CLI / HTTP）。
- **MCP 的协议流只走标准输出，且必须是 UTF-8**（M19）：准备阶段的横幅（拿锁、接线）
  一律走**标准错误**；Windows 上**管道默认 GBK**，协议流必须固定成 UTF-8
  （中文目标描述会变乱码）。
- **敏感窗口的黑名单是发送前的硬闸门**（M20，2026-10-21）：标题命中敏感词表
  **或**是对话框类名的窗口**根本不许拍、不许发** —— 抓帧之前就拦下，
  动作记录里记一笔「**被敏感窗口策略拦下**」。
  ⚠️ **它与 M16 的审批闸门的关系**（2026-10-21 已拍板 → 修票 **M24**，✅ **已落地**）：
  **M16 的十一类不变**（「截含敏感窗口的屏」那一类**保留**，不删——删了就是合同里少一类
  危险动作）；**M20 的黑名单接进 M16 的闸门**，顺序是 **M20 先、M16 后**：
  ① **黑名单先行** —— 命中的动作**在抓帧之前**就被拒（**零抓帧、零像素**），
     **不走到审批闸门**（不会产生审批请求），错误码 `sensitive_window_blocked`；
 ② **审批退成二次确认** —— 黑名单**没**命中、但请求属于「截含敏感窗口的屏」那一类
     → **仍产生 M16 的审批请求**（带意图 + 目标），没批则**零动作下发**，
     错误码 `approval_denied`。
  **两层是两个不同的错误码，不合并**（合并就丢掉了「是哪一层拦的」）。
  ⚠️ 这与 M20 AC 1「根本不许拍」**不冲突**：命中黑名单的那一帧**压根没拍**，
  批了也**拍不成**。
- **判的是「这一帧里看得见的窗口」，不只是前台那一个**（M20）：抓的是**整屏**帧 ——
  前台背后的密码管理器窗口照样在那一帧里，只判前台 = **静默漏判**。
  端口 `approval/ports.py::WindowInspector` 因此有**两个方法**
  （`foreground` 给 M16 的审批问、`visible_windows` 给 M20 的闸门问）。
- **隐私策略文档由实现生成**（M20）：`docs/privacy-policy.md` 是
  `python -m minicode.privacy` 从 `privacy/policy.py` 渲染出来的 ——
  每条条款带一个**实现位置**（`模块:符号`），单测钉住「仓库里那份 = 现在渲染的那份」。
  ⚠️ **涉及脱敏的边界引用脱敏器自己描述的那一份**
  （`redact/redactor.py::redaction_boundary`）—— **同一处规则，不写两套**。
- **OCR 是「文本比对」这一手段的第二个来源，不是第四种验证手段**（M27，2026-10-21 拍板）：
  校验层仍然只有**可访问性树 / 文本比对 / 像素差分**三路（`means` 的键还是这三个），
  OCR 的判定落在**文本比对**那一路上；**三层断言的形态不变**
  （状态变化 / 文本出现 / 文本消失 / 文本比对）。
  ⚠️ **接了 OCR 之后，画面这一路是权威的**：树覆盖不全时「树里没有」**不能**说
  「期望不成立」——**判据是**：OCR 读到了 → 按画面判；OCR 读不出 → **判不了**；
  **没接 OCR 端口** → 保持 M11 的原口径（树里没有 = 不成立）。
  「读到但一个字都没读出来」也判**判不了**（空读数可能是识别失败，拿它说「不成立」是危险的）；
  **代价**：OCR 只能证明「它在那儿」，不能单凭空读数证明「它不在这儿」。
  OCR **只读**（不产生动作、不注入输入）；每次读数记**区域坐标 + 读到的文本 + 区域来源**
  （可人工核对），每步记 `truth_source`（**画面量的** / **树里取的**）。
  术语见 `CONTEXT.md` 的「OCR 读数」与「真值出处（truth_source）」两条。
- **浏览器通道的落点取「可见文本的行盒中心」**（M28，2026-10-21 拍板）：
  「可见文本的实际区域」= 浏览器给的**行盒**（`Range.getClientRects`，行高），
  **不取屏上墨迹的中心** —— 墨迹中心随字体渲染与抗锯齿抖动，行盒是稳定的布局盒。
  ⚠️ 两者相差约 3 CSS px（实测：行盒中心 vs 落点偏差 **(0.0, 0.19) px**；
  从画面量的墨迹中心 vs 落点偏差 **(0.5, 1.31) px**）——**两条都 ≤2 物理像素**。
  ⚠️ **没有文本子节点的元素**（`<input>` / `<button>` 等，它们的可见字是 placeholder /
  按钮标签，**不是文本节点**）→ 落点取**它自己的矩形中心**（元素框本身就是它的真值，
  **不算回退**）；**文本子节点存在但量不到**（文本被裁、字体未加载）→ **判不了**，
  **不静默回落到矩形中心**。

## 联网后补发 Issue 的流程

本目录是权威副本；**联网后**才把工单镜像成 GitHub Issue，流程按 `docs/agents/issue-tracker.md`：

> 📌 **完成的标记只有一条**：commit message 里的 `feat(M<N>)`（例：`feat(M2): 脱敏器上线`）。
> **不回填验收勾框、不加「已完成」态**。补发时按 `git log --oneline` 里的 `feat(M<N>)` 提交判断哪些工单已完成，**已完成的不再补发**。

1. 按依赖顺序发 issue：标题前缀 `M<N> `，正文用本目录对应文件的 `## What to build` / `## Acceptance criteria` / `## Blocked by` 三节原文，打 `ready-for-agent` 标签。
2. `gh` 不在 PATH 上，用全路径调用：`& "$env:ProgramFiles\GitHub CLI\gh.exe"`。
3. **阻塞边用 GitHub 原生依赖关系**：
   `gh api --method POST repos/xiaochuan7/minicode/issues/<子单号>/dependencies/blocked_by -F issue_id=<阻塞者的数据库id>`
   数据库 id 的取法：`gh api repos/xiaochuan7/minicode/issues/<阻塞者号> --jq .id`（不是 `#号`，也不是 `node_id`）。
4. **父子关系用 `sub_issues`**，它表达「这张工单属于哪个里程碑」，**不是**阻塞关系。两件事别混；要表达父子关系时才用 `sub_issues`。

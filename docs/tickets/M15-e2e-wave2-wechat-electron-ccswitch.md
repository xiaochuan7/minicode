## What to build

把目标应用任务清单里微信（WX-1~WX-3）、DSH/Tabbit（E-1~E-3）、cc-switch（CC-1~CC-3）与一条跨应用搬运（CC-3）跑通。

微信这一波是「门控 + 弹窗」的活体测试：树被门控时先解开并退避重试再判定不可用；出现模态弹窗时零动作下发并交人。Electron 这一波验证「扁平树 + 输入通道退化」：收不到键盘事件时能自动退到另一条输入通道。cc-switch 是完整树的基准形态：这里 UIA 通道应当判定为可用。

## Acceptance criteria

- [ ] WX-1 通过：门控状态下先尝试解开 + 退避重试；重试成功记能力表为可用，仍不可用记为不可用并按覆盖失败切视觉；进入聊天后窗口标题 == 联系人名。
- [ ] WX-2 通过：中文与 emoji 正确注入（代理对正确）；发送后该文本出现在会话里；一次发送只产生一条消息（不可逆动作没有被自动重试）。
- [ ] WX-3 通过：模态弹窗出现后零动作下发；返回「交接给人」；交接产物含当前窗口标题、最后一步动作、已发坐标与已执行动作清单。
- [ ] E-1 通过：落点落在该控件框内、偏差 ≤2 px；保存后设置面板里该项的值 == 目标值（结构断言）；追踪记录能读到通道与失败类型。
- [ ] E-2 通过：导航后页面标题 == 目标标题；结构与视觉都可用时选结构那条并记录选择理由；坐标与动作语义跨技术栈不变。
- [ ] E-3 通过：输入成功且内容正确；某条输入通道失效时自动退到另一条并记录这次退化；剪贴板被恢复。
- [ ] CC-1 通过：UIA 通道判定为可用；落点落在条目控件框内、偏差 ≤2 px；切换后「当前配置」显示为新条目。
- [ ] CC-2 通过：核对用可访问性树 / 文本比对，不是靠画面变了；核对不通过时判执行失败并回报。
- [ ] CC-3 通过：三步动作各自有断言；任一步失败能定位到哪一步（三类失败分开统计）；全程没有把坐标挪到别的窗口（目标窗口被遮挡时先置前再操作）。
- [ ] 报告口径：7 个任务逐个给出通过 / 失败 / 跳过与原因；人工代确认项单独统计。

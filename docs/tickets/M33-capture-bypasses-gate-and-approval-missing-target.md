## What to build

M24 把敏感窗口黑名单接进了 M16 的审批闸门（**黑名单先行、审批二次确认**），
但有**两处闸门管不到的地方**还留着：

1. **抓帧可以绕过闸门**：`action/executor.py::_screenshot`（`:408`）**直接**调
   `port.screenshot(region)` 抓帧，**不问任何闸门** —— 没有隐私闸门，也没有审批闸门。
   它在缝的 standalone 路径上会被 `check_capture` 挡住，但**任何直接调执行器
   screenshot 动作的路径**就是一个绕过两层的口子。
2. **审批请求的目标落到默认「整屏」**：`action/seam.py` 的 `run()`（`:338`）与
   `_run_zoom()`（`:761`）调 `check_capture` 时**没传 `target_description`**，
   于是审批请求里绑定的目标永远是「整屏」—— 与 M16「绑定意图 + 目标」的合同冲突
   （同一个缝上的另一处 `check_capture`（`:866`）**是传了**的，口径不一致）。

本单把这两处**一起**修。

## Acceptance criteria

- [ ] **抓帧必须过闸门**：任何走到 `screenshot` 动作的路径都要先过**隐私闸门 + 审批闸门**
      （顺序与缝上一致：隐私闸门在审批与抓帧之前）；命中黑名单 → **零抓帧、零像素**，
      错误码是**敏感窗口策略那一类**（**不是**审批未获批）。
- [ ] **不许有第二条抓帧路径**：单测断言「执行器抓帧之前问过闸门」；
      全仓检索截图端口的调用点，**只有**闸门之后的那一处（不许有绕过闸门的直调）。
- [ ] **审批请求带真实目标**：`run()` 与 `_run_zoom()` 调 `check_capture` 时
      **传 `target_description`**（与缝上其它调用点一致）→ 审批请求里绑定的目标是
      这一次实际要抓的那块，**不是**默认的「整屏」。
- [ ] **两类错误码仍可分辨**：黑名单拒绝 ≠ 审批未获批，**不合并**
      （合并就丢掉了「是哪一层拦的」）。
- [ ] **不改变动作语义**：动作种类集合（**12 个**）、协议版本、坐标口径、错误码集合都不变。
- [ ] **边界不回归**：M16（十一类逐类要审批）、M20（敏感窗口 → 零抓帧零注入）、
      M24（黑名单先行 + 审批二次确认）的既有单测**一处不改地通过**。
- [ ] **文档同步**：`docs/00-现状.md` 的「抓帧前的闸门顺序」那一节写明
      **没有第二条抓帧路径**。

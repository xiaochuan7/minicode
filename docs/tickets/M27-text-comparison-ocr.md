## What to build

本层现在只有三种验证手段：可访问性树、文本比对、像素差分。**文本比对**目前只认控件名/控件值，所以有一批值**读不出来**，于是永远落在「判不了」：

- Windows 设置的**缩放百分比**（下拉框的 Value 是空的，百分比不在控件名里）——M14 的 W-1② 因此不成立
- 界面上的**时钟/数字读数**（随位数变化而动，从树里读不稳定）
- **微信聊天区的内容**（本机微信的树只给外壳，聊天内容根本不在树里）——WX-1 因此不成立

本单给**文本比对**加一条 OCR 通道：读不到树里的值时，从画面上读。

## Acceptance criteria

- [ ] **OCR 是文本比对的一种实现，不是新的一种验证手段**：三层断言的形态不变（状态变化 / 文本出现 / 文本消失 / 文本比对），只是「文本比对」这一路多了一个来源（画面 OCR）。
- [ ] **OCR 读得到缩放百分比**：Windows 设置的显示页上，OCR 读出的缩放值与界面显示一致（W-1② 成立）；读不出时**判不了**（不是「不成立」）。
- [ ] **OCR 读得到界面读数**：W-3 那一步的时钟/数字读数能被 OCR 读出，且**每步记录真值来源**（`truth_source` = 画面量的，与「树里取的」区分开）。
- [ ] **OCR 读得到微信聊天区标题**：进入某个联系人的聊天后，OCR 能读出聊天区的标题（WX-1③ 成立）。
- [ ] **OCR 不可用时判不了，不是不成立**：没有 OCR / OCR 读不出 → **判不了**（三档里的第三档），绝不判成「期望不成立」。
- [ ] **OCR 结果要能复核**：每次 OCR 读数都记**区域坐标 + 读到的文本 + 区域来源**（可人工核对）。
- [ ] **只读**：OCR 只读画面，**不产生动作、不注入输入**；不改变「只测外部行为」的口径。
- [ ] **真机验证**：Windows 设置（缩放值）、DSH 界面（数字读数）、微信（聊天区标题）三处各跑一次，报告里如实写每处的真值来源与读数。

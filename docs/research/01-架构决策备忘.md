## 0. 结论速览

**三个决定：**

1. **坐标问题不是"归一化 vs 像素"之争。** 在 2560 宽屏上，0~1000 归一化的量化误差只有 **±1.28 物理像素**【底稿 02 L13/L330；算术自洽：2560/1000=2.56 px/单位，±0.5 单位=±1.28 px】，不是瓶颈。真正的误差源是另外三个：整屏降采样把小图标抹掉、**DPI 1.5× 空间错配（最大 1280 px，常见落点 667~1000 px）**【底稿 02 L385–L392 四类错法 A/B/C；严格式误差 = (scale−1)×坐标 = 0.5×坐标，x=2560 时为 1280 px】、模型自身 grounding 能力。→ 结论：**模型端固定用 0~1000 归一化（Qwen3-VL 原生训练空间），工程端全程物理像素，整屏只做粗定位，最终落点在 crop 上二次定位产生。**

2. **架构主线是"结构优先 → 视觉兜底"，不是"视觉优先"。** Windows 上 UIA 可访问性树能给出**精确到物理像素**的控件 bbox，零漂移、零模型成本【官方：learn.microsoft.com「The UI Automation API does not use logical coordinates」，底稿 04 L597–606】。这是你相对 Linux 榜单方案独有的工程红利：OSWorld 官方榜 111 条去重记录里只有 2 条用了 a11y 树、109 条为 No【官方·榜单：os-world.github.io 的 `osworld_verified_results.xlsx`，2026-10-19 拉取，底稿 03 L231】。
   > ⚠️ **不得反推**：OSWorld 是 **Linux 桌面**榜，AT-SPI 覆盖度与 Windows UIA 不可比；这 2 条 a11y 条目恰恰说明"a11y 在 Linux 榜上不加分"，**不能反推 UIA 在 Windows 上没用**【底稿 08 L34 复核意见】。→ 结论：**UIA 树是第一定位手段，VLM 是覆盖率兜底。**
   > ✅ **同一张榜上的正面证据（比那 2 条 a11y 条目更硬）**：OSWorld 官方论文 Table 5 的四组对照——**纯截图 GPT-4V 5.26% / 纯 a11y tree GPT-4 12.24% / 截图+a11y 12.17% / SoM 11.77%**：**纯 a11y 树是全场最高、纯截图全场最差、SoM 反而不如「截图+a11y」**（论文归因于高分辨率下元素过多、坐标级动作无法用 SoM 表达）。【专题·dom-vs-pixel L21/L27，引 OSWorld 官方论文 Table 5】→ **这就是「结构优先」的同榜实证**，比"榜上只有 2 条用 a11y"更直接。
   > 🔴 **但必须同时记住覆盖率上限**：Apple 对 **4,068 个 iPhone app / 77,637 块屏幕**的人工标注显示——**59% 的屏幕至少有一个可见元素在 a11y 树里无匹配、4% 的屏幕树全空、94% 的 app 至少含一块这样的屏幕**（Apple 已排除游戏且匹配宽松，属保守估计）。【专题·dom-vs-pixel L34，引 arXiv 2101.04893】→ **UIA 树是「第一手段」不是「全覆盖手段」：能力表必须能表达「树在但覆盖不全」这一态（SPARSE），视觉兜底不是可选项。**

3. **2026 的胜负手在 harness，不在 checkpoint。** 阿里 OpenGCUA 用**同一批 8 个模型、只换 harness**，OSWorld-v2 平均部分分 **45.3 → 64.9（+19.6）**，步数 **−53%**（GPT-6 Astra 102→34 步），最强−最弱模型差距 39.1→18.0【官方·仓库：<https://github.com/Tongyi-MAI/OpenGCUA> README，2026-10 读；底稿 03 L387–L390、底稿 08 L35 逐字核验】。
   - **README 正文可核的两组数**：① 换 harness **+19.6 分 / 步数 −53%**；② **代码执行 vs 同等 GUI+CLI 权限 = +6.1 分 / 步数 −14.8%**（3 模型均值）——后者证明收益来自"把循环/分支写进代码"，**不是**"多给一个 shell"【底稿 08 L35 引 README 原文 "adds value beyond shell access"】。
   - 🔴 **引用纪律（检查项）**：**"+15.5~+33.6 分 / 步数 −55~63%"这组区间不在 OpenGCUA 官方 README 正文**（README 全文只给 +19.6/−53% 与 +6.1/−14.8%），底稿 03 全文 0 命中该区间【底稿 08 L35/L170；底稿 03 L371–L412】。该区间若要写进任何文档，**必须先回查 arXiv 2610.22200 消融表并标出表号**；本规格只采信 README 两组数。→ 结论：**决策层要写成"模型生成一段 Python 动作程序"，而不是"模型逐条吐 action"。**

**一个不做的事：** 不引入 OmniParser v2 做实时 grounding。其官方模型卡自报 ScreenSpot-Pro 准确率仅 **39.6%**【官方·模型卡：<https://huggingface.co/microsoft/OmniParser-v2.0>，2026-10-19 读；底稿 04 L710–711】、端到端 **0.6 s/帧(A100) / 0.8 s/帧(RTX 4090)**【同上】、本机 6GB 上 **1.5–4 s/帧（估算·未实测，底稿 04 L715 自标）**；2026 第三方结论是**所有被测模型在 SoM 下 OSWorld-G 均 <30**【底稿 03 L361】。许可口径为**混合**（**仓库 CC-BY-4.0**；**模型权重许可需另查 HF model card**；检测器是 **YOLOv8 导出 ONNX**（~11.6 MB，第三方实测）【底稿 04 L708/L712】）——闭源商用前必须逐项核许可。

**模型落点（MiniMax M3.1 Flash）：** M3.1 Flash 原生多模态、1M 上下文、**$0.15 / $0.60 / $0.015 每百万 token**（输入/输出/缓存输入）【官方·博客 <https://www.minimax.io/blog/minimax-m31f> + 官方·文档 `platform.minimax.io/docs/guides/text-generation`，2026-10-19/20 核验，底稿 08 §4.1】；OSWorld 2.0 **自评 61.7**——**是 partial score（平均部分分）不是 binary 完成率，且 OSWorld 官方榜无 M3.1 Flash 条目**【底稿 08 L99–L108：2026-10-20 重拉官方榜 xlsx 逐行扫描，全榜唯一 MiniMax 条目是上一代 `MiniMax M3` = 75.19%】。→ **当"大脑"（规划 + 观察 + 动作程序生成）性价比全场最高，但不要让它兼任 grounding**：通用大模型在点级定位上动作类型正确率可达 85.9%、grounding 正确率仅 52.4%【底稿 03 L317/L361 一手转述】，"spatial grounding 仍是首要瓶颈"。→ **大脑用 M3.1 Flash，定位用 UIA + crop 精定位**（详见 §4.4）。

## 1. 你问的坐标问题：0~1000 vs 像素 vs 裁剪后像素

### 1.1 三个**互相独立**的误差源

| # | 误差源 | 量级 | 归属层 | 能不能靠"换坐标格式"解决 |
|---|---|---|---|---|
| E1 | 坐标格式量化 | **±1.28 px**（0~1000 @2560 宽） | 模型输出 | —— 已经很好了 |
| E2 | 整屏降采样把小目标抹掉 | 16 px 图标 → **7.9 px** | 预处理 | ❌ 换格式无用，要靠 crop |
| E3 | DPI 空间错配（截图物理 / 点击逻辑） | **最大 1280 px**（=0.5×2560），常见落点 **667~1000 px** | 执行层 | ❌ 换格式无用，要靠 DPI 感知 |
| E4 | 模型自身 grounding 能力 | 目标越小越差 | 模型 | ⚠️ 只能靠 crop 提升有效分辨率 |

**E1 算术**（2560×1600，0~1000 归一化）：1 单位 = 2.56 物理 px，±0.5 单位 = ±1.28 px；crop 到 512 宽后降到 ±0.26 px【底稿 02 L13 / L330 / L598】。
**E2 算术**：Qwen2.5-VL HF 默认 `max_pixels = 28×28×1280 = 1,003,520` → 降采样系数 **β = √(4,096,000/1,003,520) = 2.02×**，模型输入 **1260×784**，回算 scale X=2.032 / Y=2.041 → 16 px 图标进模型只剩 **7.9 px**【底稿 02 L114–115 / L349–L369；底稿 08 L65（把 2.03× 改 2.02×）】。Qwen3-VL 默认 `max_pixels = 16,777,216`（factor=32，patch=16）→ 2560×1600 **不缩放**，`image_grid_thw=(1,100,160)`，视觉 token = 50×80 = **4000**【底稿 02 L145–160；底稿 08 L66】。
> ⚠️ **两个 `max_pixels` 不可混用**：Qwen2.5-VL/UI-TARS 血统是 **28×28×1280（1,003,520）**，百炼 `gui-plus` 是 **32×32×1280（1,310,720）**——见 §1.2 坑 3。

**E3 算术**：抓图用物理像素、点击走逻辑像素 → 偏 1000 px；反向 → 偏 667 px；**理论最大偏差 = 0.5×2560 = 1280 px**。**这是灾难级，不是"偏几个像素"。**【底稿 02 L385–L392 列出的 A/B/C/D 四种错法；底稿 08 L67/L173 复核：667/1000 是代表值，最大值是 1280 px】

### 1.3 落地方案：两级 grounding + 全程物理像素

```
        ┌── L2 视觉定位层 ──────────────────────────────────┐
粗定位  │  整屏截图 2560×1600 (物理 1:1)                    │
        │      ↓ 缩放到模型输入尺寸 (保持宽高比)               │
        │  模型输出 0~1000 归一化坐标                         │
        │      ↓ ×(W_m/1000) → 模型输入像素                  │
        │      ↓ ×(W_c/W_m) → 截图像素 (= 物理像素)            │
        │  得到粗点 p0 (±30 px 足够)                          │
        │      ↓ 以 p0 为中心取 512×512 物理像素窗口 (越界 shift/shrink) │
精定位  │  原图裁剪 512×512，**1:1 不缩放**                   │
        │      ↓ 模型输出 0~1000 (相对 crop)                  │
        │      ↓ ×(512/1000) → crop 内物理像素 (±0.26 px)     │
        │      ↓ + crop 原点 → **最终物理像素坐标**            │
        └───────────────────────────────────────────────────┘
```

> 🔴 **`W_m` 的定义（必须写进代码注释，不得硬编码任何 `max_pixels` 常量）**
> **`W_m` = 你实际发出的那张图的宽**，不是原图宽、不是模型"应该看到的"宽。
> · `W_c` = 截图宽（= 物理像素宽 = 2560）。
> · **Anthropic 路径**：`W_m` 必须取 `resize_and_encode()` 返回的 `(sent_w, sent_h)`；不预缩放则服务端会再缩（长边 ≤1568 px 且 ≤1568 tile），模型坐标落在**你没观测过的空间**里【官方·quickstart `anthropics/anthropic-quickstarts` → `computer-use-best-practices/computer_use/image.py`，底稿 08 L121 逐字核验】。
> · **百炼 gui-plus 路径**：`W_m` = `smart_resize` 后的宽（本机 1440），**不是** 2560，也**不是**按 28×28×1280 算出来的 1264。
> · **禁止**在代码里出现 `28*28*1280` / `32*32*1280` 这类常量——它们随模型与版本变，抄错是静默偏移（见 §1.2 坑 3）。

**为什么这个方案成立**（四条硬证据）：
- crop 后量化误差 ±1.28 → **±0.26 px**（512 宽时 1 单位 = 0.512 物理 px）【底稿 02 L598】；
- crop 后 16 px 图标**保持 16 px**（进模型不被抹成 7.9 px）；**且 512×512 = 262,144 px 在 `28×28×1280`(1.00M) 与 `32×32×1280`(1.31M) 两个阈值下都不会触发二次缩放**——这是方案成立的前提，必须写进注释【底稿 08 L69】；
- **公开工作证明"缩小搜索面积"有效**（同一论文的对照实验）：ScreenSpot-Pro（arXiv 2504.07981，2025-04-04）里 OS-Atlas-7B 单轮 **18.9%** → ReGround（裁剪 1024² 后重预测）**40.2%** → ScreenSeekeR（GPT-4o planner 级联搜索）**48.1%**（相对提升 254%，**无需额外训练**）；论文原文结论是 *"strategically reducing the search area enhances accuracy"*【论文：<https://arxiv.org/abs/2504.07981>，2025-04-04】。⚠️ 最佳 crop 尺寸**随模型而变**（OS-Atlas 1024²、UGround 768²）→ 本方案的 512 是本机取值，不是普适最优。
  > 📌 **但要知道天花板在哪**：ScreenSpot-Pro **官方榜第一 82.7%（`Indeed-UI-32B-zoomin`）**，而研究基线低得多（UI-TARS-1.5-7B **42.19**、OS-Atlas-7B **18.9**、GPT-4o **~0.8**）；**目标框平均只占图 0.07%（ScreenSpot 是 2.01%，约 30× 难）**。【官方·grounding 榜，底稿 03 L278】→ 48.1% 与 82.7% 的差距说明"**crop 后重预测**"这条路上还有大量空间没吃到——**这也是本方案只把 crop 当第一级精定位、还要配校验层的原因**。
- **免训练的两阶段 zoom-in 也被验证**：R-VLM（ACL 2025，arXiv 2507.05673）整图出粗框当 region proposal → 按粗框裁约 5× 宽高区域 → 放大回全分辨率重预测，ScreenSpot avg **53.4 → 66.3（+12.9）**、Desktop Icon **30.0 → 52.8（+22.8）**【论文：<https://arxiv.org/abs/2507.05673>（2025-07-08），底稿 02 L432】。
- **小目标才是分水岭，不是坐标格式**：UI-TARS 官方 README 自评表里 ScreenSpot-v2 上 UI-TARS-1.5 **94.2** vs OpenAI CUA 87.9 vs Claude 3.7 87.6（只差 5~6 点），但 ScreenSpot-Pro 上 **61.6 vs 23.4 vs 27.7**（差 2~3 倍）【官方·README，底稿 02 L457–L464】。

**最终落点只在 crop 尺度上产生**——整屏归一化坐标只用来"选哪块区域"，永远不直接点击。

### 1.3.1 精定位实现：能抄什么、要自己写什么、坐标系契约怎么选

> "The API's vision encoder tiles images into 28x28 patches and caps both the long edge (1568 px) and the total tile count (1568). If we send an image that violates either, **the server resizes it *again* before the model sees it, and then the model emits click coordinates in a space we never observed, producing systematic click drift (~14% on a 16:10 MacBook screen)**."

➡️ **本机是 2560×1600（16:10），长边 2560 > 1568，必然触发服务端二次缩放**——**这正是本方案"发图前必须自己缩到预算内并记住 sent 尺寸"的原因**（§1.5 的 sent→physical 反算）。**不要让服务端替你缩。**

| # | 我们的选择 | 官方现状 |
|---|---|---|

| ④ | **精定位失败的判定条件 + 回落动作**（回落到粗定位） | 官方**完全没有失败/回落概念**，只把错误回灌给模型 |

**（k）🔴 crop 精定位**不能无条件做**——实测证据是"平均更差"。**

CCF（<https://github.com/LufeMC/gui-g2-3b-ccf>）在 ScreenSpot 上的实测分项：**整体 −0.3pp**（Icon **+2.2**、Web **+3.9**、但 Text **−2.3**、Mobile **−5.2**）。【实测·仓库，2026-10-20 clone 直读】
→ **无门控地做 crop 精定位，会做出一个"平均更差"的层**：它在本来就准的 text 目标上引入抖动（模型在放大图里重新找一个本来已经找对的文字），在 mobile 上损失更大。

**所以本方案的精定位必须是「按需触发」，不是「每步必做」：**
1. **触发条件**（命中任一才开 crop pass）：粗定位目标**框面积占全屏比例很小**（ScreenSpot 的经验阈值是 **0.07%** 量级）／粗定位**输出为空或越界**／粗定位**置信度低**／双模型**一致性检查不一致**（`zoom_consistency_router.py` 的思路）。
2. **门控与回退**：抄 `cursor_ccf.py` 的门控与失败回退（有 220 个单测可当回归基线）。
3. **判据与官方对比**：Anthropic 官方**完全没有**门控与失败概念（只把错误回灌给模型），**这一层是本方案必须自研、且是最容易做错的一层**。

### 1.4 运行时自适应标定（防文档与实际行为不一致）

启动时跑一次**标定探针**，把标度变成运行时数据而不是硬编码常量。

**探针必须用 2560×1600（与本机真实分辨率一致），不能用 1280×720。**
> 理由（原型实测 + 独立复核推导）：同一个 raw 值 `n`（0~1000 量纲）在 **0~999 与 0~1000** 两种分母下的物理差 = `n × W × (1/999 − 1/1000)` = `n × W × 0.0010010`。
> · **2560 宽探针**：n=1000（右边缘）时 **x 轴分歧 = 2.56 px**；按原型探针几何（margin 96、目标 64 px，右下角目标 x=2432 / y=1472）算出的 **欧氏距离 = 2.86 px**【本机实测(2026-10-19)，`proto/coord/` 桩运行输出】→ **1 px 容差下有 2~3 倍余量，稳健可辨**。
> · **1280 宽探针**：x 轴分歧仅 **1.28 px**（欧氏 ≈1.30 px）→ **只有 1.3 倍余量**，模型定位本身抖动 ±1 px 时就可能翻车；**2 px 容差下更是完全检测不出来**。
> 【推导：底稿 08 L71 的独立复核；原型 `gui-cu/proto/coord/`（`calibrate.py` 的分歧估算函数与实测输出）】
> ⚠️ **因此把判定容差从 2 px 降到 1 px**：2 px 容差下 1280 探针的 1.30 px 分歧与容差同量级、**必然漏判**；1 px 容差下 2560 探针仍留有 2~3 倍余量。**探针过小或容差过宽 = 标定静默失败。**
> ⚠️ **标定容差（1 px）与动作协议的越界容差（2 px）是两个不同的常量，不许共用**——前者是"能不能区分两种标度"的判据，后者是"点击是否越界"的判据（见 §3）。
> 📌 **为什么容差必须这么小**（这决定了标定失败为什么必须硬拒）：Windows 的「**点击即命中**」容差通常只有 **2–4 px**；而 0~1000 归一化映射回 2560 宽时 **1 个归一化单位 = 2.56 物理像素**，半分辨率下小图标的中心偏差可达 **5–10 px**——**已经比命中容差还大**。→ **容差一旦放宽到"差不多能点中"的量级，标度错误就永远暴露不出来**，所以本方案宁可"标定失败拒跑"，也不肯"猜一个标度继续跑"。【底稿 05 L160，【底稿·二手】】

1. 生成 2560×1600 合成图，在已知物理位置画 4 个高对比目标（四角各一）；
2. **四个目标必须包含一个贴在最右边缘的**（n≈1000）——x 轴分歧随 n 线性增长，只有边缘点才达到 2.56 px 的上界（中部 n≈780 时只有 2.00 px）；【底稿 08 L71/L196 的明确建议】
3. 问模型要这 4 个点的坐标；
4. 判定模型实际使用的标度：`0~1` / `0~999` / `0~1000` / `截图像素绝对` / `模型输入像素绝对`；
5. 存进 `CoordinateAdapter` 的运行时配置，后续所有换算走它；
6. **标定结果必须落盘**（标定时间、探针图哈希、判定标度、容差、各候选的 max_error），否则"静默 ≠ 不记录"——出问题无法复盘。【底稿 07 §2.9 漏掉 #9】

**三条实现约束（原型实测得出）：**

- **越界判定必须分两层，先判模型空间。** 把 0~1000 的 `953` 当 0~1 读时，模型空间那层会立刻判定越界；只判物理空间的话，误差要到上千像素才暴露。标定器必须**捕获 `CoordinateError` 记为 `inf`**，否则第一个候选就把整个流程中断。
- **两种"绝对"标度在"模型输入尺寸 == 截图尺寸"时不可区分。** 同一组数字误差都是 0，结果完全相同，但调用方需要知道。标定结果要显式暴露**标度判定**（唯一命中 / 多解）与**落点等价**（容差内等价 / 分歧）两个维度——**不可区分就如实报多解并给出等价标度列表，不要假装唯一**。
- **落点等价判据（C-03 硬闸门）。** 标定探针给出候选标度族；只有在**存在使物理落点分歧 > 标定容差（1 px）的替代标度**时，视觉通道才不可用（回落 UIA 通道或直接报错）。分歧 ≤ 容差的等价标度族**允许继续**（等价列表必须落盘），但**标度判定**如实记为**多解**。**前提**：探针必须含最右边缘目标（C-03 已要求）——0~999 与 0~1000 的物理分歧随 x 线性增长、最大值在右边缘，探针不覆盖最坏情况则本判据悄悄失效。静默错位是 GUI agent 最难查的 bug，这一条不能松。

**第四条（补）——每步回显模型自己发出的坐标与实际发送尺寸。**
> 官方做法是回显**模型发出的**坐标（不是缩放后的真实像素）并附上图像尺寸：`f"({x}, {y}) in {sent_w}x{sent_h} image"`，让模型能在下一次推理时对账自己的坐标。【官方·quickstart image.py；底稿 07 §2.11 漏掉 #11】
> 对本方案尤其有用：第二级在 512×512 crop 内定位时，回显"（x,y）在 512×512 图内"能让模型自己发现标度搞错。成本 = 一个字符串。**必须实现。**

**为什么必须这么做**：官方文档自相矛盾（Qwen3-VL grounding **docs 页写 0–1**，cookbook/技术报告写 **0–1000**；cookbook 内部分母又分 **999 与 1000**；且 mobile 路径用 999、computer_use 路径用 1000）。读文档不可靠，**运行时实测才可靠**。【底稿 02 L166；底稿 05 L120；底稿 06 L418/L434–435；底稿 08 L44/L47】

> 可运行实现已交付：`gui-cu/proto/coord/`（`coordinates.py` / `calibrate.py` / `crop_refine.py` / 49 个 unittest，全绿，exit=0）。
> ⚠️ **接入时必改一处**：原型 `calibrate.py` 的 `tolerance_px` 默认值是 **2.0**，与本文 §1.4 要求的 **1 px** 不一致（原型默认与 §3 动作协议的越界容差共用了一个常量）。**必须把标定容差拆成独立常量并设为 1.0**（见 §2.6 检查项 C-03）。

### 1.5 工程端统一坐标协议（Windows）

**唯一真值空间 = 物理像素 × 虚拟桌面原点。** 进程首行必须：

```python
import ctypes
ctypes.windll.user32.SetProcessDpiAwarenessContext(ctypes.c_void_p(-4))  # PER_MONITOR_AWARE_V2
# ↓ 必须早于 import pyautogui（它 import 时就调 SetProcessDPIAware，会锁死 DPI 模式）
```

> **为什么必须 PMv2 而不是别的**：`SetProcessDPIAware`(Vista) / `SetProcessDpiAwareness`(8.1+，**只能设 V1**) / `SetProcessDpiAwarenessContext`(10 1703+，**唯一能设 V2**)。微软**推荐用 manifest**（`dpiAwareness=PerMonitorV2` + `dpiAware` 回退），API 方式"supported but not recommended"，且**必须在创建任何 UI 之前调用**，失败码 5/87。【官方·文档 learn.microsoft.com/windows/win32/hidpi，底稿 04 L78–L120】
> ⚠️ `mss` 在 `MSS()` 构造时会调 `SetProcessDpiAwareness(2)`（**V1 不是 V2**），且 pyautogui 在 import 时调 `SetProcessDPIAware()`（**System-aware**）——**谁先 import 谁定死进程 DPI 模式**。所以本项目规则是：**入口第一行显式设 PMv2，mss / pyautogui 都在其后 import**。【本机读源码 + 底稿 04 L177/L491–L496】

**本机实测(2026-10-19)**（在目标机上跑的，底稿 04 §A6.1 L350–L363）：

| 进程 | `GetSystemMetrics(SM_CXSCREEN)` | `GetDeviceCaps(LOGPIXELSX)` |
|---|---|---|
| PowerShell（未声明感知） | 1707 × 1067 | 96 |
| Python（PMv2） | **2560 × 1600** | 144 |

→ **所以：不要把缩放系数写死成配置项**（czdcode 旧项目写死了 `dpi_scale: 1.25`，本机实际 1.5）。DPI 感知之后，进程内部拿到的就是物理像素，**整套换算里根本不需要出现缩放系数**。

> 🔴 **必做自检断言**（写在启动路径上，返回 1707 就直接中止，不要继续跑）：
> `GetSystemMetrics(SM_CXSCREEN)` 必须返回 **2560**（物理）；返回 1707 说明 DPI 感知没生效 → **整条坐标链不可信**。【底稿 02 L567；底稿 06 L786】
> 且多屏场景**必须**用 `SM_XVIRTUALSCREEN / SM_YVIRTUALSCREEN / SM_CXVIRTUALSCREEN / SM_CYVIRTUALSCREEN`，**不能**用 `SM_CXSCREEN`（微软官方页脚已警告 `SM_CXSCREEN` 不是 DPI aware）。【底稿 04 L59/L221】

**但坐标适配层仍要保留一个缩放字段**，语义必须明确：
- 默认值 **1.0**，表示"截图与物理像素 1:1"（PMv2 感知路径下的正常状态）；
- **只有走 DPI-unaware 抓图路径**（例如某个第三方库内部重新声明了感知，或用了 GDI 虚拟化）才需要填非 1.0；
- 非 1.0 时**必须打警告日志**——因为它意味着某个环节没做对，而不是"正常配置"。
- 换算链路的**唯一真值来源**必须是这个字段，不能在别处再写第二份缩放逻辑（旧项目正是在文档里写了 `physicalX = pixelX / dpiScale`、代码里故意不换算，靠一句注释兜住——**这是换算链路分叉的经典病灶**）。【底稿 01 L206–L215（czdcode `CoordinateTransform.java:71-74`）】

**鼠标下发**（`SendInput`，`mouse_event` 官方已标注 superseded）：

```
nx = round((x - VX) * 65535 / (VW - 1)) + VIRTUALDESK      # 绝对坐标 + MOUSEEVENTF_VIRTUALDESK
ny = round((y - VY) * 65535 / (VH - 1)) + VIRTUALDESK
```
**本机实测(2026-10-19)**：6 个目标点 × 12 次采样（绝对移动 → 立即 `GetCursorPos` 回读 → 取众数误差），`round(x*65535/(W-1))` **误差全 0**（12/12 命中）；`x*65535//W` 稳定 −1 px；`x*65536//W` 右下角 −1 px。【底稿 04 L365–L375】带 `MOUSEEVENTF_VIRTUALDESK` 映射到整个虚拟桌面，不带则只映射到**主显示器**【官方·<https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-mouseinput>，底稿 04 L202–L208】。
> ⚠️ **分母必须是 `(dimension − 1)`**，否则最后一个像素永远点不到；且**禁止用相对移动做校正**——微软文档明确相对移动会被鼠标加速曲线放大到 4 倍。【官方·<https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-mouseinput>，底稿 04 L348/L799】

> 🔧 **一个会静默失败的坑**：`ctypes` 的 `INPUT` 必须用 **union**。写成两个独立 struct 成员时 x64 下 `sizeof=64`（正确值 40），`SendInput` 因 `cbSize` 不匹配**直接返回 0 且不报错**——所有点击静默失效。同类问题：ctypes 默认按 `c_int` 返回，`HDC`/`HBITMAP` 在 64 位下会被截断。【本机实测(2026-10-19)，底稿 04 L379–L384；x64 实测 `sizeof(MOUSEINPUT)=32`、`sizeof(KEYBDINPUT)=24`、`sizeof(INPUT)=40`，x86 为 28】
> 🔧 **并且必须检查 `SendInput` 的返回值**：微软官方原文——*"If the function returns zero, the input was already blocked by another thread. **Neither GetLastError nor the return value will indicate the failure was caused by UIPI blocking.**"*【官方·<https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput>】→ **返回值 0 有两种原因（UIPI 阻断 / cbSize 错），且 `GetLastError` 都不指示**，所以"只看返回值"不够，还必须同时断言 `sizeof(INPUT) == 40`（x64）。

**多显示器与哨兵值（执行层四个硬事实，漏一个就是"点空"或"点错屏"）**【底稿 06 L792–L808；均为公开 issue 与工具文档，**未在本机复现**，按【底稿·二手】级别对待】
- **虚拟桌面原点不在主屏左上角**：左侧/上方的屏坐标是**负的**（左侧 1920 px 屏 → x 起点 **−1920**）→ 多屏必须用 `SM_XVIRTUALSCREEN` 系列（76/77/78/79）并把归一化基准设为**整个虚拟桌面**；只按主屏归一化会把 0 送到副屏最左边缘。
  → **协议层规定：模型坐标永远留在 frame 内（正数），负坐标只存在于执行层**——VLM 只能输出正数，负偏移的符号处理必然出错。【底稿 06 L792–L801/L806】
- **`-32000` 是哨兵值，不是坐标**：UIA 元素 bounds 在副屏上会返回 **−32000**（Windows 对最小化窗口的 `GetWindowRect` 哨兵），此时点击"成功"但落空。**Indirect Display Driver（IDD）虚拟显示器**（华为 / 向日葵 `OrayIddDriver`）会让 D3D/WGC 抓到 **0×0** 截图并返回 −32000 坐标 → **遇到 0×0 截图或 −32000 坐标必须跳过该 adapter**，或改用不需要坐标的 UIA `Invoke`/`set_value`/`key`。【底稿 06 L804–L805】
- **`MAKELPARAM` 会把负坐标回绕**：它按无符号 16 位打包，负的窗口局部坐标回绕成 ~65500 → 点击落到右下角而不是左上。【底稿 06 L803】
- **pyautogui 的四函数空间不一致**：`size()` 返回**逻辑**分辨率、`screenshot()` 返回**物理**像素、`locateOnScreen()` 在**物理**空间、`moveTo()/click()` 按**逻辑**空间解释 → 官方归纳的原话是 *"clicks at exactly the wrong spot"*（200% 缩放时点到目标位置的 1/4）；且 pyautogui ≥ 0.9.53 对越界点击**静默 clamp** 到 `max(0, coord)`，**会破坏多屏负坐标**。→ **硬规则：绝不把 `locateOnScreen()` 的结果直接喂给 `click()`**；本项目的坐标下发统一走 `SendInput`（§2 L0），pyautogui 只作辅助。【底稿 06 L770–L788】
  > 📌 **与 C-01 的关系**：上面这张表描述的是**进程 DPI 感知没生效时**的行为；一旦 C-01 断言通过（`SM_CXSCREEN == 2560`），`size()` 才与物理像素一致。**所以 C-01 不通过时，pyautogui 的 `size()` 就是逻辑分辨率——这正是"必须先断言再干活"的理由。**

## 2. 分层架构

```
┌─ L5 安全与审计 ── 动作日志 / 危险动作审批 / 幂等重试 / 可回放
├─ L4 校验与纠错 ── expect 验证 / 无变化检测 / 反思重规划 / 循环熔断
├─ L3 决策层 ────── 任务分解 → 生成 Python 动作程序 → 执行 → 读结果
├─ L2 视觉定位层 ── 两级 grounding（整屏粗 + crop 精）/ 运行时标定
├─ L1 结构感知层 ── UIA 树（控件名/类型/物理 bbox）/ OCR 兜底
└─ L0 设备与坐标层 ─ DPI 感知 / mss 截图 / SendInput 键鼠
```

### L0 设备与坐标层
- **截图**：`mss`（GDI BitBlt）做默认 —— 物理像素、免用户授权、**~5–30 ms/帧**（底稿 04 内部对区间有 10–30 vs 5–30 两说，以 **5–30 ms** 为准并按"未实测"处理；原型实测一帧 55.4 ms/6.7 ms 两次采样见 `proto/exec/README.md`）。`WGC` 只在必须抓**被遮挡/硬件加速/最小化**窗口时上（需用户点一次系统选择器 + 有黄色边框，交互成本高）。**禁止用 `PrintWindow` 兜底**——硬件加速/DirectComposition/分层窗口会返回黑或空白。【底稿 04 L432–L450】
- **鼠标**：`SendInput`。点击序列必须是 `move → 60ms → down → 40ms → up`（`MOVE → sleep(60ms) → DOWN → sleep(40ms) → UP → sleep(60ms)`）。**理由有三条**【底稿 04 L739–L749】：① 很多 UI 要先收到 `WM_MOUSEMOVE`（让 hover 生效、菜单弹出）才认 click，瞬移+零间隔常常只触发 hover；② Windows 双击默认时间 **~500 ms**、矩形 **~4 px**，所以两次独立单击间隔要 >500 ms、而双击要 <500 ms 且位移 <4 px；③ 提权弹窗切 Secure Desktop 要几十到几百 ms 建好桌面再注入。
- **键盘**：`SendInput` 扫描码；中文用 `KEYEVENTF_UNICODE` 或**剪贴板通道**（Set-Clipboard + Ctrl+V）绕过 IME 干扰。
  > ⚠️ **每个字符单独一次 `SendInput`**——down+up 放同一个数组里可能**一个字符都不产生**；`KEYEVENTF_KEYUP` 只加在 up 事件上；非 BMP 字符（emoji）要拆 surrogate pair；**Chromium/Electron 可能 `SendInput` 返回"成功"却完全收不到 keydown**（连 Ctrl+V 剪贴板方案也失败）——这类应用改走 CDP `Input.dispatchKeyEvent` / `Input.insertText`。【底稿 04 L885–L896】
  > ⚠️ **剪贴板通道必须写前备份、动作后恢复**（`finally` 里恢复），否则污染用户环境。【底稿 04 L902】
- **滚轮**：`MOUSEEVENTF_WHEEL` 的一次滚动量是 **`WHEEL_DELTA = 120`**【底稿 04 L802】，而多数 GUI 框架的"滚动一格"是 **1 行** → **本项目统一按 ×50 换算**（旧项目与 OpenCUA 官方 agent 都硬编码了这个修补）【底稿 01 L438；底稿 07 L63/L320】。
  > ⚠️ **滚轮惯性**：Windows 平滑滚动（触控板 / 部分应用）会把滚轮效果延长，表现为"滚了还在动" → 滚完 **sleep 300–600 ms** 再截图；或改用 `WM_MOUSEWHEEL`（消息注入）/ `IUIAutomationValuePattern` / `ScrollPattern`。【底稿 04 L869】
- **UAC 提权弹窗（Secure Desktop）无法截图也无法控制**——这是硬边界，不是 bug。普通完整性级别的进程**截不到图（黑屏）、UIA 返回 0 个窗口、`OpenInputDesktop` 返回 ACCESS_DENIED、注入输入无效**。【底稿 01 L437（UAC Secure Desktop 不可见不可交互）；底稿 04 L451/L969；底稿 06 L756】
  > **两条可选路线（都必须由用户明确拍板，不许代码默认开启）**：
  > ① **正规做法：停机交接给人**——检测到 UAC/提权窗口就返回 `uac_or_secure_desktop` 并停止动作，把轨迹交给人。【底稿 06 L762】
  > ② **降低安全性换可控**：组策略 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System` → `PromptOnSecureDesktop=0`——**明确降低安全性，必须用户书面同意**；更优的替代是**让被控程序以管理员身份常驻运行，agent 本身不提权**。【底稿 04 L969】

### L1 结构感知层（Windows 专属红利）

**先分清两个维度：渲染引擎（Win32/WPF/Electron/Chromium/Canvas）× 宿主形态（原生/浏览器/Electron 应用）。** 之前的表述把两者混为一谈，导致"Chromium 一律失效"这种过度绝对的说法。**本机实测（2026-10-19，`proto/exec/selftest.py`）的分层事实：**

| 宿主 | UIA 树 | 实测 | 结论 |
|---|---|---|---|
| 原生 Win32 / 控件 | ✅ 完整 | 任务栏 `Shell_TrayWnd` 命中 Button，rect=(10,1528,238,1600) 物理像素 | 首选路径 |
| Chromium / Electron | ⚠️ **有，但扁平** | 拿到 205~345 个元素，含 `Document`（整个网页）、`Hyperlink name='Overview'`、`Edit name='地址和搜索栏'`；**ClassName 直接就是页面 CSS 类名** | 可用；但**无 AutomationId**，只能按可见文本定位 → 精确定位仍应走 CDP |
| UWP / WinUI（XAML island） | ❌ **完全没有** | Windows 设置的 `ApplicationFrameWindow` / `CoreWindow` / XAML island 全部 `total=0`，桌面级 `Name=设置` 也 0 命中 | **只能走截图 + OCR/VLM** |
| Canvas 自绘 / 游戏 | ❌ 无 | — | 同上 |

> ⚠️ **本表与底稿 04 的"一刀切"说法并存，必须读懂再用**：底稿 04 §B2 写的是「Win32/WinForms/WPF/UWP **能用**、Electron/Chromium/游戏/Canvas **基本不能用**」（**官方·pywinauto 文档级**）；本表是**本机实测(2026-10-19)** 的逐应用结果。两者不冲突，差别在：
> · **UWP/WinUI**：官方层面 UIA **支持**（底稿 04 L616），但**本机实测的"Windows 设置"这一 XAML island 应用无树** → 结论是「**按 app 逐个探测，不能按"应用类别"一刀切**」；
> · **Electron/Chromium**：官方层面**默认不暴露无障碍树**（Electron 需 `app.enableAccessibility=true` 或 `--force-renderer-accessibility`），本机实测拿到的**扁平树**说明"能挂载 ≠ 有语义控件"——**候选数多不等于可精确 grounding**；
> · **浏览器网页内容**：树存在但结构扁平（Chromium 经 MSAA/IAccessible2 桥接到 UIA），**AutomationId 动态、role 泛化、部分元素缺 BoundingRectangle** → **按"不可用"处理，落到视觉兜底**；
> · **判定姿势不变：递归子窗口 + 看 UIA ClassName，不数候选数**。【底稿 08 §六 四层仲裁；底稿 03 L322–L347】

- UIA 的 `BoundingRectangle` **是物理像素**（前提：进程已 PMv2 感知）——官方原文 *"The UI Automation API does not use logical coordinates."*【官方·learn.microsoft.com，底稿 04 L597–606】。
- **性能三个数字必须分清，不可混用**：
  | 场景 | 数字 | 来源等级 |
  |---|---|---|
  | **无条件全树 `FindAll`（~1000 元素）** | **≥8 秒**（建 cache request 约 9 秒） | **社区实测**（StackOverflow 帖，底稿 04 L627）——**不是本机实测**，底稿 04 把它标"实测"属证据强度误读 |
  | **带属性条件的桌面级查询**（`ControlType=Button`，401 命中） | **416 ms** | **本机实测(2026-10-19)**（`gui-cu/proto/exec/README.md`，复现入口 `proto/exec/selftest.py`）——**底稿 04/06 均无此数** |
  | **UIA 查询一般延迟**（Notepad/Run 对话框） | **1.6~1.9 s** | 【底稿 06 L617/L836】 |
  → **结论不变：UIA 完全可以进主链路，不必为性能放弃它。** 但**超时阈值必须放宽到 ~5 s**，且**每次查询后必须检查是否返回 0 节点**——"静默退化成返回 0 节点"是最危险的失败模式【底稿 06 L617/L836】。
- **判定可用的正确姿势**：**递归子窗口 + 看 UIA ClassName**（不是数候选数）——czdcode 旧项目实测：豆包主窗口只有 3 个边框按钮，真正的 162 元素/18 个中文候选藏在一个**不可见子窗口**里；树没挂出来时"窗口边框上的最小化/最大化/关闭照样能读到"，只按"候选数 ≥ 3"判会得到**假阳性**——"这种失败不报错，比直接报不可用难查得多"。【本机实测(2026-10-19)，底稿 01 L336–L340】
  > 注：本机微信当前版本是 `mmui::MainWindow`（153 元素 / 40 个可用交互控件），**不是**"裸 Qt 外壳 3 个边框按钮"——那条判据针对的是另一个版本，**说明这类判据必须按 app + 版本维护，不能写成通用结论**。
  > **本机 4 应用 UIA 能力基线（可直接用作回归基准）**：Edge **126** / 微信 4.1.15 **26** / 夸克 **23** / 豆包 **18** 个可交互候选。【本机实测(2026-10-19)，底稿 01 L322–L328】
- **唯一性规则**：命中多个同名候选时**用 id（AutomationId / runtime id）区分**；**候选不唯一时先做消歧**：在 UIA 候选集内让模型**只做指认**（候选唯一时零模型调用；指认必须落在候选集内且恰好一个）。消歧失败、**候选数超过上限**（默认 8）、或指认不唯一 → 走 L4 错误处理并回报候选集，而不是随便挑一个。**任何情况下都不切视觉。**（czdcode 旧项目实测微信登录窗里**有两个**叫"通讯录"的控件，早期版本用名字做键直接撞车，真机上动作被拒。）【本机实测(2026-10-19)，底稿 01 L202–L206 / 底稿 07 §2.5】
  > **配套规则（从旧项目继承）**：**元素 id 每次观测重新生成**（只在一次 `readCandidates` 调用内有效）；**执行前必须重读控件树重新定位**，定位不到就失败——**宁可不动，也不能把动作打到看起来相似的另一个控件上**。【底稿 07 A17/A18】
  > 🔴 **为什么"执行前必须重读"是承重项，不是有益项**（2026 年的量化证据）：**过期结构会劫持 agent**——arXiv 2607.04334 定义了 "Perception-Fusion Gap"，用 735 个探针（其中 225 个来自线上站点的**零编辑**结构/渲染分歧）测出：四家厂商模型"**像素读对了却听结构的**"比例 >0；**在未编辑的 stale snapshot 上跟随过期结构最高 0.88**；多步任务中**首步一次错信念即导致失败，自恢复率 ≤ 0.03**。→ **"树里写着什么"与"屏幕上画着什么"不一致时，模型几乎总是信树**——所以每次动作前必须重新读树，而不是复用上一次的快照。【专题·dom-vs-pixel L46，引 arXiv 2607.04334（2026-07）】
  > 📌 **浏览器侧是同一件事的官方版本**：Playwright MCP 官方文档写明元素引用的作用域是 *"Scope: unique within a single snapshot / **Lifetime: Valid until the page changes**"*，页面一变就报 `Ref <ref> not found in the current page snapshot`。【专题·dom-vs-pixel L47，引 <https://playwright.dev/mcp/snapshots>】→ **UIA 的 runtime id 也要按同样语义对待：一次观测内有效，跨动作必须重取。**
  > **Invoke 优先、坐标点击降级，且降级要记事件**：`InvocationResult` 区分 `invoked` / `clickedByCoordinate` / `failed`；不支持 Invoke 的判法是直接 `GetCurrentPattern(10000)` 试拿模式对象，拿不到就是不支持。【底稿 07 A19/A20】
- **已知门控**：微信等应用的 UIA 在特定状态下被门控（旧项目实测四种解锁手段；**注意底稿 01 自己的表里列了 6 组脚本**，"四种"是标题措辞，取用时按 6 组核对）；Qt 应用在启动期 UIA 树未就绪，**必须重试**（Qt 源码级：`QCoreApplication::startingUp()` 时直接 return false）。【底稿 01 L363–L378；底稿 07 A2/A7】
- **只做定点查，不做全树 dump。** UIA 调用必须在**独立线程**，否则死锁/卡死；用 `IUIAutomationCacheRequest` + `FindAllBuildCache` 一次拉回，避免逐属性读；**先读名字**（绝大多数元素没有名字，读到空就放弃，省掉后面 4 次 COM 往返）。【官方·<https://learn.microsoft.com/windows/win32/winauto/ui-automation-threading-issues>，底稿 04 L630/L629；底稿 01 L456–L457】
- **树 dump 进上下文有体量上限，不是"越大越好"**：NEC 论文（arXiv 2605.29397，2026-05）实测 **WorkArena L1 单页原始 HTML 就有 40K–500K tokens**；它系统对比 11 种 HTML 缩减方法，a11y tree 已是标准启发式基线之一，并用 GEPA 优化剪枝程序做到**每步延迟 2.2×、成功率保留 84%**（WebLinx 3.1× / 保留 89%），单页 AXTree pruning 仅 **0.27 s**。【专题·dom-vs-pixel L48/L58】→ **本项目的 UIA 树 dump 必须有字段白名单（§2 L5 / C-15）+ 元素数上限 + 分层裁剪，不能整棵树进上下文。**
- 原型踩坑记录（`proto/exec/README.md`）：`CoCreateInstance` 前必须 `CoInitializeEx`（否则 `0x800401F0`，看起来像"类没注册"）；`SysAllocString*` 在 `oleaut32.dll` 不在 `ole32.dll`；`PROPERTYID`/`VARIANT` 按值传参，用 `byref` 会得 `E_INVALIDARG`。
- **能力表按应用静态缓存**：判定"这个 app 的 UIA 能不能用"**每次应用启动判一次，不是每步判**（否则每步都付一遍探测成本）；能力表就是 M1 的验收交付物（§6 M1 ④ / C-08）。【底稿 07 L484】
- **UIA 访问层的库选型**：性能敏感路径用 **`comtypes` 直连 `IUIAutomation`**（或 pywinauto 的 comtypes 后端），**不要用纯 Python 的 `uiautomation` 包装**——社区那个"1000 元素 ≥8 秒"**很可能是包装层开销，不是 UIA 的固有成本**（与 C-09 的三个数字直接相关）。【底稿 07 L508–L509】

### L2 视觉定位层
见 §1.3。补充：crop 窗口默认 512×512，可选 Lanczos 放大到 1024（记 `upscale` 因子，回算时除）；边界处理用 shift/shrink，**不裁切目标**。

### L3 决策层（harness = 代码执行）
**不**采用"模型逐条吐 action、harness 逐条执行"的循环。改为：模型针对当前观察生成**一段 Python 程序**（可含 if/for、可调用 pyautogui 与 shell），harness 执行后把 stdout/异常/新截图回灌。

依据（OpenGCUA，arXiv 2610.22200；**以下只列 README 正文可核的两组数**）：
- **同一批 8 个模型只换 harness**：OSWorld-v2 平均部分分 **45.3 → 64.9（+19.6）**，步数 **−53%**（弱模型增益最大：GLM-5.3-Flash +35.2、DeepSeek-V4.1-Flash +29.8），最强−最弱模型差距 39.1 → 18.0。【官方·仓库 README，底稿 08 L35 逐字核验；底稿 03 L387–L390】
- **代码执行 vs 同等访问权的 GUI+CLI 批量执行**：**+6.1 分、步数 −14.8%**
  → 说明收益**不是**"有个 shell"带来的，而是**把循环/分支的控制权写进代码**，让中间结果决定下一步而不用再问模型一次。【底稿 08 L35 引 README 原文 "adds value beyond shell access"】
  > 🔴 **本节刻意不写 "+15.5~+33.6 / 步数 −55~63%"**——那组区间**不在 OpenGCUA 的 README 正文**，来自论文消融表且本轮未核到表号。**要引用必须先回查 arXiv 2610.22200 的消融表并标出表号**；否则按检查项 **C-13** 判不合格。【底稿 08 L35/L170；底稿 03 L371–L412 全文 0 命中该区间】

另两个可借鉴的 harness 设计（来自 OpenGCUA）：**按需截图**（不是每步都截全屏）、**持久 todo 状态**（任务进度不进对话历史，靠外部状态文件）。

### L4 校验与纠错层（最容易被忽略、但决定成败）

**三种验证手段，按可靠性排序**【底稿 06 L613–L619】：**UIA / 可访问性树**（查 `enabled/checked/value`、是否存在、矩形是否变化 → 抓状态型错误；代价是 **1.6~1.9 s 延迟**，且"**静默退化成返回 0 节点**"是最危险的失败模式，见 C-09）＞ **OCR / 文本比对**（抓文本型错误；慢、中文小字易错）＞ **像素差分**（判"画面到底变了没有"；最快最通用，但**变化 ≠ 成功**）。

- **每动作可带 `expect`**：期望的确定性验证（OCR 文本出现 / UIA 状态变化 / 区域像素变化阈值），执行后自动断言。
- **像素差分的可执行参数**（Windows 10/11 实测的社区最佳实践，**【底稿·二手】**）：动作前抓 **baseline** 帧；动作后轮询 = **首次立即 + 100 ms 内 15 ms 节奏 + 之后 20 Hz**；比较用 **8×8 像素块 + uint32 精确比较**（1080p 静态帧约 1 ms）；判定顺序 = **reaction（有任何变化）→ stillness（`quiet_time` 内不再变化）→ 返回**。【底稿 06 L621–L624】
  > ⚠️ **两条语义边界必须写进模型提示词**（一手，settled-computer）：**"no visible change" ≠ "failed"**（可能本来就已聚焦/已置位）；**"a pixel change is not proof of success"**（点错打开错对话框也会"settle"）→ **变化检测只能当必要条件，不能当充分条件**。【底稿 06 L654–L658】
- **无变化检测**：连续 N 步截图差分 ≈ 0 → 判定卡死 → 触发反思（换策略/换定位方式）。**阈值取 1% 像素变化**（settled-computer 用 1%；gptme `wait_for_change` 用 1% 阈值、**0.5 s 轮询**）；⚠️ 光标闪烁、动画、时钟会造成假阳性 → 需要**区域级**差分 + 连续多次。【底稿 06 L648–L649】
  > **动画/视频区域**：约 **1.5 s 残余 bail** 并给出该区域的 bbox；**连续两次 bail 后自动忽略该区域**（带过期时间）；**闪烁的光标会被判成"有反应"** → 文本框里的"无变化"判定不可靠。【底稿 06 L626–L627】
- **循环熔断**：harness 强制步数上限 + 重复动作检测——把最近 K 个动作的 `(action_type, 归一化坐标, 参数)` 做成哈希集合；**同一动作连续 ≥3 次且帧无变化** → 判定卡死，强制换策略（换 crop 尺寸 / 换定位级别 / 改键盘 / 请求人工）。【底稿 06 L650】
  > 📌 **为什么这一层不能省（一个可算的例子）**：旧项目实测"**单步正确率 p，10 步不校验后路径仍正确的概率 = 0.88¹⁰ = 28% / 0.78¹⁰ = 8.3%**"——**错误会复利**。把 p 从 0.88 提到 0.78，10 步后的存活率从 28% 掉到 8.3%，**多花一次调用换来的正确率提升会被步数放大成数量级差距**。【底稿 07 L126（引旧项目 `ARCHITECTURE.md:80-81`）、底稿 01 L572】
- **进度停滞检测**：把"已完成的子目标数"或"最近一次 UIA/文本状态改变时刻"当进度信号；**超过 T 秒/轮无变化 → 升级**（提级到更强模型 / 缩小 crop / 换 API）。【底稿 06 L651】
- **停止条件由 harness 强制**（轮次硬上限，官方示例 `max_iterations = 10`），不靠模型自觉。【底稿 06 L652】
  > 🔴 **反模式（必须避免）**：只做"动作 → 截图 → 交给模型"而**不做任何机器侧断言**——arXiv 2606.31270 指出 *"redundant action loops are the most common failure mode identified by the LLM"*。【底稿 06 L637–L638】
  > ✅ **可落地的判据组合**：(a) 帧差分判"有没有反应"；(b) 目标区域 OCR/文本比对判"是不是想要的结果"；(c) UIA 判"状态对不对"——**三者的 OR 判据与停止条件联动，且刻意不让 LLM 当裁判**（避免假阳性）。【底稿 06 L640–L642】

### L5 安全与审计
- 动作日志（时间/动作/参数/执行前截图/执行后截图）→ 可回放。
- 危险动作（删除、支付、发送、装软件）走 `requires_approval` 人工确认。
- 幂等与重试：区分"动作失败"（可重试）与"状态已变"（不可重试，否则重复扣款）。
  > **可执行的重试策略**（底稿给的最小可用集）：**只重试可逆动作**（移动鼠标 / 滚动 / 聚焦可重试；发送消息 / 支付 / 删除**不可自动重试**）· **重试带退避 + 上限（3 次，200 / 500 / 1200 ms）** · **每次重试前必须重新感知**（UI 在两次尝试间可能已变，**复用旧坐标 = 误点**）· **用状态机而不是脚本**（目标写"页面已加载"而不是"点了第 3 个按钮"，重入时按状态而非序号继续）· 记录 `action_id`，回放时跳过已成功的步骤。【底稿 04 L1041–L1046】
  > **不可逆动作前先 dry-run**：先截屏 + 展示将要点击的元素，等确认。【底稿 04 L1035】
- 🔴 **UIA 树进 LLM 上下文前必须脱敏。**
  > 这不是理论风险，是**真实发生过的事故**【本机实测(2026-10-19，czdcode 旧项目)，底稿 01 L294–L296 引 `ARCHITECTURE.md:91-93` 原文；底稿 07 §2.1 复述】：

## 2.5 三条跨层硬规则（实现时最容易做错的地方）

**① L1 → L2 的切换只认「coverage failure」，不认「任何错误」。**
> 旧项目踩过这个坑：一旦把"切视觉"当成通用兜底，每步都会走视觉，兜底从"罕见"退化成"每步 1.5~5 秒"，架构优势全丢。
> **coverage failure 的定义**：UIA 通道**无法为该目标产出任何候选**（无 provider / 树被门控 / 目标根本不在树里）。
> **不是 coverage failure 的情况**（这些必须走 L4 的错误处理，**禁止切视觉**）：候选不唯一（先按 §L1 的**消歧**处理）、候选被遮挡、候选尺寸异常、UIA 树读取超时、名称匹配不上。
> 【底稿 07 §2.2 L156–L168：「**只有 coverage failure（目标不在候选集）才换通道**，selection failure（候选里有但选错）**不换通道**」；三类失败的原始三分法见底稿 07 §2.3 L170–L182。视觉通道平均成本 ≈ 0 的依据（本机 4 应用实测 UIA 给出 18–126 个候选、coverage 失败罕见）见底稿 07 L162】

**② 换算链路必须单一来源。**
> 缩放系数、标度、crop 偏移都只能有一个真值来源。旧项目在文档里写了 `physicalX = pixelX / dpiScale`、代码里故意不换算、靠一句注释兜住——**这类分叉会让文档与代码各说各话**。§1.3 的换算式与 §1.4 的标定值必须是同一个对象的两个方法，不能各写一遍。
> 【底稿 07 §3.2 L356–L374：「把丢弃 #2 的理由从"旧项目写死了 1.25"升级为**换算链路必须单一来源**」；旧项目原样见底稿 01 L206–L215（`CoordinateTransform.java:71-74`）】

**③ 三段耗时 + 三类失败必须拆开埋点。**
> 否则任务掉了**不知道该改 L1 / L2 / L3 / L4 哪一层**。
> **三段耗时**：定位（UIA 查 / 视觉推理）｜ 决策（模型）｜ 执行+校验（动作 + 截图 + 断言）。
> **三类失败**：定位失败（没找到/找错）｜ 决策失败（选错动作/参数错）｜ 执行失败（动作无效/界面未响应）。
> 每步日志必须同时记录这三项。旧项目缺这个埋点，是它"调了半年不知道该改哪"的根因。
> 【底稿 07 §2.4 L187–L199（三段耗时；旧项目原文"否则提效幅度无法归因，也就无法证明 Jev 到底有没有赚回那 134ms"）、§2.3 L170–L186（三类失败作为独立指标）；底稿 01 L540–L541 的推断：「"失败"的根因是**没有可对比的数字**，不是"技术没做出来"」】

**④ crop 精定位必须按需触发，不能每步必做。**

## 3. 动作协议（最小可实现集）

统一在**截图像素空间**（整数，左上原点）。每帧携带物理变换元数据，DPI/多屏在抓图层解决，不污染动作层。
> 协议形状（12 动作 + `cua.action/1` JSON Schema + 结果错误码枚举）已由底稿给出可直接实现的规范，见【底稿 06 L876–L1037】；本节只做**本项目的取舍**。

| 动作 | 参数 | 说明 |
|---|---|---|
| `screenshot` | `region?` | 抓图；region 用物理像素 |
| `click` | `x,y,button=1,click_count=1` | 左/右/双击；**执行时序必须走 C-11 的 move→60ms→down→40ms→up** |
| `move` | `x,y` | 悬停（菜单需要真实 move） |
| `drag` | `from(x,y),to(x,y)` | |
| `type` | `text` | 走 UNICODE 或剪贴板通道（剪贴板必须备份/恢复） |
| `key` | `combo` | 如 `ctrl+s` |
| `scroll` | `x,y,dx,dy` | `dx/dy` 以**行**为单位；下发前按 **×50** 换算到 `WHEEL_DELTA = 120` 的刻度（见 §2 L0）；滚完等 **300–600 ms** 再截图（滚轮惯性） |
| `wait` | `ms` | |
| `zoom` | `rect` | **必须 `source: native` 回源重抓**，不放大旧图（复用降采样帧会得到糊图） |
| `inspect` | `selector` | 读 UIA 子树（结构优先） |
| `execute_code` | `python` | 决策层生成的动作程序 |
| `ask_user` | `reason` | 需要人工介入（对应 UI-TARS 的 `CallUser()`） |

规则：
- **越界不 clamp，直接报错**（容差 **2 px**）+ `safe_area` 白名单区。
  > ⚠️ **两个容差常量不许混用**：这里的 **2 px** 是**动作越界容差**；§1.4 标定探针的 **1 px** 是**标度可分辨性容差**。原型 `proto/coord/calibrate.py` 目前把两者合成了一个 `tolerance_px=2.0` 默认值，**接入时必须拆开**（见 §2.6 C-03）。
  > 物理层越界也**不许**自动挪到最近的显示器——那等于"点到别的窗口"，可能造成不可逆后果，应报 `clipped_by_desktop`。【底稿 06 L1041–L1066】
- 每动作可带 `expect` 做确定性验证；**无 `expect` 时也要做默认校验**（帧差分：变化率 <1% 且持续 2 帧 → `no_visible_change`），但"无变化 ≠ 失败"、"像素变化 ≠ 成功"（点错也会"settle"）。【底稿 06 L1087/L655–L658】
- 危险动作 `requires_approval: true`。
- 停止条件由 harness 强制（轮次硬上限 + 同一动作哈希连续 ≥3 次且帧无变化 → 强制换策略）。**注意：协议里没有 `finished`/`terminate` 这个动作值**——终止只能由 harness 侧的停止条件承载，模型"自称完成"不算数（`a model's terminate(success) action is not proof of real-world success`）。【底稿 06 L1090/L1145；底稿 03 L440】
- **执行前必须重读控件树重新定位**，定位不到就失败——**宁可不动，也不能把动作打到看起来相似的另一个控件上**；元素 id 每次观测重新生成。【底稿 07 A17/A18】
- **每步回显模型自己发出的坐标 + 实际发送尺寸**（`f"({x}, {y}) in {sent_w}x{sent_h} image"`），让模型能对账自己的坐标。【底稿 07 §2.11】

**结论：能用，但分工要摆对。**

| 角色 | 建议 | 理由 |
|---|---|---|
| **大脑**（规划 / 观察 / 动作程序生成） | ✅ **M3.1 Flash 首选** | 1M 上下文可同时装下多帧截图 + UIA 树 dump；$0.15/$0.60 的价格让"多问几轮"几乎免费；OSWorld 2.0 61.7（**partial score · 厂商自评 · 官方榜无该模型条目**）说明它有桌面操作能力，但**不等于 61.7% 的任务能完成** |
| **grounding**（给点/框） | ⚠️ **不单独交给它** | 通用大模型的点级定位是已知瓶颈：某 32B 级模型动作类型正确率 **85.9%**，但 grounding 正确率仅 **52.4%**；61.7 是**平均部分分**（partial score · 厂商自评 · 官方榜无该模型条目），会掩盖 grounding 失败【底稿 03 L317/L361】 |
| **兜底复核** | ✅ 用 | crop 内二次确认可以由它做（此时输入是 512×512 小图，定位难度大幅下降） |

**因此推荐的三层定位链不变，只是把"粗定位"这一层的主语换掉：**

```
目标"保存"按钮
  │
  ├─ ① UIA 树查（结构，零漂移，0 成本 0 延迟）        ← Win32/WinForms/WPF 首选；UWP/XAML 逐 app 探测
  │     命中 → 直接用控件 BoundingRectangle（物理像素）
  │
  ├─ ② M3.1 Flash 整屏粗定位（0~1000 归一化）        ← 覆盖率兜底
  │     → 换算到物理像素，容差 ±30 px
  │
  └─ ③ 在 ② 的点上开 512×512 物理像素 crop 二次定位     ← 最终落点，±0.26 px
        二次确认可由 M3.1 Flash 做，也可换本地 Qwen3-VL-2B/4B
        （GGUF Q4_K_M 4B 约 2.7GB，本机 6GB 塞得下）做**更快**的 crop 定位
```

**三个具体的坑（接入前必须处理）：**
1. **effort 默认 max 会烧钱烧时间。** 动作步设 `effort=low|medium`，只在规划/反思步用 `high`。GUI agent 的动作步不需要长思考链。【检查项 C-12】
2. **1M 上下文不是让你无脑塞。** 历史仍按 §4.3 走"结构摘要 + 按需截图"，否则成本 ×2.83。
3. **M3.1 Flash 的 grounding 标度同样要过 §1.4 的运行时标定。** 官方文档自相矛盾（grounding docs 页写 0–1，cookbook 写 0–1000，且分母 999/1000 并存），**同一个坑不因为换了模型就消失**。【检查项 C-03 / C-04】

**接入主链路的前置条件（阻断项，需你回答）**
> **你手上的 M3.1 Flash 是"可编程调用"的 API（M Plan / 按量 API / 后续开源的权重），还是仅限 DSH/交互式使用？**
> · 若是**可编程 API** → 可进主链路当"大脑"，主链路 = M3.1 Flash + 百炼 gui-plus 复核。
> · 若是**仅交互式** → 它只能当"人工参考模型"，**主链路仍需走百炼 `gui-plus` / `qwen3.8-max`**，本节结论降级为"备选"。
> （官方 API 文档已提供 Anthropic-Compatible / OpenAI-Compatible 两条路，所以"能不能编程调用"只取决于你手上拿到的是哪一条通道，不取决于模型能力。）【底稿 08 §4.1/L91/L108】

## 5. 三个候选架构（供选择）

### 方案 A（**推荐**）：结构优先 + 两级视觉 + 代码执行 harness
- 定位：UIA 树优先 → 覆盖不到时 VLM 整屏粗定位 → crop 精定位
- 决策：`gui-plus` / `qwen3.8-max`（或 M3.1 Flash，若为可编程 API）生成 Python 动作程序
- 执行：`SendInput`（`sizeof(INPUT)==40` 断言 + 返回值断言 + move→60ms→down→40ms→up）；截图 mss
- 成本：**¥32.37~64.58/月**（6000 步，gui-plus 默认降采样 → 全分辨率）【底稿 05 L188/L191】；每步 1~2 次模型调用 + 1 次 UIA 查
- 优势：坐标漂移源头只剩 crop 内（±0.26 px）；DPI 问题在 L0 一次性消灭；Windows 上 UIA 红利独占；成本可控
- 代价：UIA 覆盖不到的 app（UWP/XAML 自绘、Canvas、Electron）仍需视觉兜底，代码量比方案 B 大
- **本方案的具体落地实例就是 `03` 文档的方案 ②**：`microsoft/UFO`（**MIT**、Windows 原生、UIA + Win32/WinCOM/MCP 混合动作）当骨架 + `Windows-MCP` / `winapp CLI` / 自写 COM 当 UIA 通道 + 百炼 `gui-plus`（或 `qwen3.8-max`）当大脑 + **自建 crop 精定位回路与校验层**这两件缺口。【底稿 03 L131/L136；底稿 05 L188/L191】
  > 📌 **骨架的外部背书（论文自报，WAA 无官方榜、不可横比）**：UFO²+GPT-4o 在 WindowsAgentArena 上 **27.9%**、UFO²+o1 **30.5%**（Navi 基线 19.5%、人类基线 74.5%）【底稿 03 L131/L256/L271】。→ **把它当"这条路被验证过"的证据，不当"能打多少分"的证据。**

### 方案 B：纯视觉最小实现
- 只做 mss + VLM + SendInput，坐标全走 §1.3 两级
- 优势：实现最快，通用性最好（任何 app 都能上）
- 代价：每步都调模型（延迟高、成本高）；小目标仍会错；没有 UIA 的零漂移优势
- 适合：M0 阶段先跑通
- ⚠️ **前置硬要求**：即便走纯视觉，**C-01/C-02/C-03/C-05/C-11 仍然全部适用**——纯视觉只是不用 UIA，不是"不用标定"。

### 方案 C：直接用 UI-TARS-desktop
- **不推荐**：仅单显示器；远程 Operator 已废弃；实际四个 provider 全是云端；UI-TARS-2 至今**没有权重**（仅技术报告 arXiv 2509.02544；官方榜复现值 **53.10**，但拿不到权重）；"UI-TARS-1.5-2B"这个模型**不存在**（2B 是 v1 的 `UI-TARS-2B-SFT`）。【底稿 03 L558/L95/L222；底稿 08 L120】
  > ⚠️ 上述"仅单显示器 / 云端 provider / 文档维护不佳"是**单一博客来源**（Gigazine 2026-06-28），属【媒体·需交叉验证】级别，不是一手证据【底稿 03 L667】。
- 适合：只当参考实现读，不当依赖

## 7. 从 czdcode 继承什么 / 丢掉什么

> 本节已按 **底稿 07「继承性复核 · czdcode → 新项目」**（2026-10-20，只读复核本文 §7）的逐条意见改写（原版有 3 处名不副实 / 不适用，见底稿 07 §4.1 / §4.3 / §4.5；底稿 07 §5 给了可直接替换的改写稿）。本节各条的**事实**均可回到底稿 01（一手代码与交接文档转述）或底稿 07 的逐行裁决。

**A. 结构性原则（继续有效，但有前提）**

1. **模型不直接产生"最终点击坐标"**，只产生候选与粗定位，最终落点由系统换算。
   > ⚠️ **限定条件（这是旧项目复核提出的最大异议，我接受）**：这条**只对 UIA 通道成立**。视觉通道里模型确实要吐坐标。→ 因此**必须把本条与 §1.4 绑定：按落点等价判据，只有存在使物理落点分歧 > 标定容差的替代标度时，视觉通道才不可用**。原版措辞"结构性免疫"会让后来人误以为视觉通道也免疫，从而低估标定的承重。【底稿 07 §4.1 L397–L415、§6 L530；底稿 01 L549–L550】
2. **UIA 可用性判定 = 递归子窗口 + 看 ClassName**，不是数候选数。【底稿 01 L566–L567；底稿 07 §4.2 L416–L422】
   > 配套三条：① 尺寸下限阈值必须可配置（否则会把最有价值的隐藏子窗口滤掉）；② Chromium 系（`Chrome_WidgetWin_*`）**不适用**裸 Qt 规则；③ 裸 Qt 外壳判定优先于候选数判定。【底稿 07 L473–L476】
3. **规则精确名匹配命中 62.5%，0 token / 0 ms** → 值得作为"零成本第一层"，排在 UIA 之前。
   > ⚠️ **必须带限定**：**n = 8 的方向性参考**（旧项目 8 条用例命中 5 条），不是统计结论；配套两条硬规则——**没有候选就不调模型**、**无法唯一定位就拒绝执行并升级，不猜**。【底稿 01 L405/L570；底稿 07 L122、§4.4 L434–L444（"应升格 + 加限定"）】

**B. 机制细节（可移植，新项目直接实现）**

4. **候选唯一性**：同名候选用 id（AutomationId / runtime id）区分；**候选不唯一时先做消歧**（模型只在候选集内指认，候选唯一时零模型调用）；消歧失败、候选数超过上限（默认 8）或指认不唯一 → 走 L4 错误处理并回报候选集；**任何情况下都不切视觉**。**重名候选是一等公民**——选项键用元素 id、值用语义描述并标注"同名候选中第 N 个"。【底稿 07 L482–L483、§2.5 L200–L212；底稿 01 L202–L206】
5. **应用门控**：微信等应用的 UIA 在特定状态下被门控（旧项目实测四种解锁手段，需活着的辅助技术进程）；Qt 应用启动期 UIA 树未就绪，**必须重试**（读 UIA 前先激活窗口 + 指数退避重试，**再**判定"不可用"，否则会把"还没就绪"误判成"这个 app 不支持 UIA"并永久切视觉）。【底稿 01 L363–L378；底稿 07 §2.6 L213–L229、§2.7 L230–L241】
6. **切视觉只认 coverage failure**（定义见 §2.5 ①），其余错误走 L4，**禁止一刀切回落**。【底稿 07 §2.2 L156–L168、§5 L491–L492】
7. **能力表按应用静态缓存**——"该不该用 UIA"**每次应用启动判一次，不是每步**；能力表就是 M1 的验收工具（见 §6 路线图 M1 ④）。【底稿 07 L484、L496–L497】
   > **可直接复用的 5 个只读探测脚本**（旧项目根目录 16 个 PowerShell 中最有用的一组）：`.t1-capability.ps1`（批量能力表）、`.probe-A.ps1`（UIPI + RawView + FromPoint 三合一排障）、`.prep-at.ps1`（讲述人环境准备）、`.probe-B1/B2.ps1`（SPI_SETSCREENREADER）、`.uia-probe2.ps1`（**Chromium 懒加载需前台激活 + 等 4 s**）。【底稿 07 L496–L499】

**C. 知识资产（不抄代码，抄知识）** ← 丢 Java 时最容易丢的部分

8. **`RECT` / `BoundingRectangle` 是 4 个 `int`，不是 4 个 `double`。** ctypes 写错 → 按 double 读会得到 **1e-311** 量级的非规格化数、四舍五入后**全是 0**，表现为"候选全都没有坐标"——而且 0,0 看起来像一个合法的左上角，**纯静默失败**。【底稿 01 L221/L569；底稿 07 L505】
9. **39 项 UIA 控件类型 ID 对照表**（旧项目自建；注意 `ListItem=50007` / `List=50008` **与直觉相反**）。【底稿 07 L506、§6 L528】
10. **COM / GUID / BSTR 六个坑**（旧项目代码注释即文档）：vtable 槽位顺序（COM 接口只做尾部追加、不重排，Win10/11 都成立）· COM 现开现关（Release 少了泄漏、多了立刻访问已释放指针，**JVM 在没有 Java 栈帧的地方直接崩**）· `CoUninitialize` 必须配对 `CoInitializeEx`（`RPC_E_CHANGED_MODE` 会拆掉别人的 apartment）· CLSID 与 IID 不能混用（否则 `0x80040154 REGDB_E_CLASSNOTREG`）· `GUID` 文本序 vs 二进制端序（手工再交换一次就双重交换）· `MAX_NODES = 2000` 封顶 + **先读名字**（读到空就放弃，省掉后面 4 次 COM 往返）。【底稿 01 L442–L457；底稿 07 L532】
    > 为什么重要：Python 生态没有现成中文排错文档，**这些坑的每一个症状都是静默的**。
11. **UIA 访问层的库选型**：性能敏感路径用 `comtypes` 直连 `IUIAutomation`（或 pywinauto 的 comtypes 后端），**不要用纯 Python 的 `uiautomation` 包装**——**"1000 元素 ≥8 秒"很可能是包装层开销，而不是 UIA 的固有成本**。这直接关系到 C-09 的口径。【底稿 07 L508–L509】

**D. 仅对旧栈有效（不迁移）**

12. **多问题打包成一次调用**（6 问打包 = 1 问，134 ms vs 拆开 710 ms）—— 这是**旧决策模型 System One 协议专有的 wire format**，标准 chat-completions（百炼 / M3.1）不支持该机制，**不迁移**。原版把它列为"继承"是错的。【底稿 01 L571；底稿 07 §4.3 L423–L430】
13. **决策模型回溯类 88% / 前向路由仅 33%** —— 同为 System One 专有，且旧项目自己写明"不能推广到大方向判断"，**不迁移**。【底稿 01 L403/L572；底稿 07 §4.5 L446–L450】
    > 📌 **附一条与"自评把握度"有关的教训（与 §2 L3/L4 相关）**：confidence 是**分布尖锐度**不是 P(正确)；实测存在 **conf = 0.95 的高置信度错误**；**答对时 P 均值 < 答错时 P 均值（均值倒挂）** ⇒ 绝对值不可当把握度、**排序可用**；二元阈值不可默认 0.5（实测最优 0.4）。→ **置信度不得作为危险动作的放行条件**。【底稿 07 L379/L386–L389、L516】

**丢掉（4 条）**

1. **Java + Maven + JLine3** 这套栈 → **建议 Python**（UIA/截图/SendInput 生态最厚，OpenGCUA 的动作层也是 Python）或 **Node/TS**（若要挂进 DSH 插件体系）。**但 C 组知识资产必须带走。** 这条需要你拍板。【底稿 07 L503–L507】
2. **写死 `dpi_scale` 这类缩放系数** → 真教训**不是**"写死了 1.25"，而是**换算链路必须单一来源**（见 §2.5 ②）。【底稿 07 §3.2 L356–L374；底稿 01 L206–L215】
3. **影子模式占位值（θ=0.70）** —— 自认没测过的东西不能当测过的；若将来引入任何"模型自评把握度"机制，继承 czdcode 的 **fail-open** 规则（低置信度 → 升级；**高置信度绝不用于放行危险动作**）。【底稿 07 L376–L393】
4. **把 UIA 树原文直接塞进模型上下文** —— 现在有脱敏硬要求（L5 / C-15）。【底稿 07 §2.1 L138–L155】

## 9. 需要你拍板的 4 件事

> 每条都写成了**有明确默认答案的决策项**——不回答就按"默认"执行，不允许悬着开工。

1. **技术栈**：**默认 Python**（UIA/截图/SendInput 生态最厚，OpenGCUA 的动作层也是 Python）；若要挂进 DSH 插件体系则选 Node/TS；继续 Java 不推荐。**注意：无论选哪个，§7 的 C 组知识资产（39 项控件类型 ID 表、COM 六个坑、RECT 是 4 个 int）都必须带走。**

4. **是否要 MCP 化**：把桌面控制暴露成 MCP server（DSH/Claude Code 这类宿主能直接调用），还是先做成独立 CLI + HTTP？**默认先做独立 CLI + HTTP**——MCP 化会显著降低接入成本，但会晚一步，且协议层要先稳定。

> ⚠️ **本机场景比 14% 更严重**：Anthropic 约束为长边 ≤1568 px 且 ≤1568 tile（≈1.176M px），本机 2560×1600（4.096M px）需缩到约 1372×822，**缩放比 ≈1.87× → 坐标空间错配可达 ~46%（估算·未实测）**。所以"照抄 image.py"的理由应从 14% 升级为"**本机实际 ~46%**"。【底稿 08 L121；底稿 02 L333 的 fit 结果 1356×848 / scale 1.887 / 16 px 图标剩 8.5 px 交叉验证】

> · **推荐基线（经验值，不是硬上限）**：官方原文 *"Start with **1280x720**… It uses about **80%** of the pixel budget"*；Opus 4.7 另推荐 **1080p**；**应避免**：原生分辨率（"the most common cause of poor click accuracy"）、**低于 960×540**、4.6 家族上的 **1920×1080 及以上**。

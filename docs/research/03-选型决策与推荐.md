## 0. 一句话结论

**推荐「方案 ②：复用现成骨架 + 自建两件别人没有的东西」。**
具体是：**UFO²/UFO³ 的 harness 骨架 + Windows-MCP / winapp CLI 的 UIA 通道 + 百炼 `gui-plus` 或 Qwen3.8 做大脑 + 自己写「crop 精定位回路」和「校验/反思层」**。

理由一句话：**2026 年的胜负手在 harness 而不在 checkpoint**（OpenGCUA 用同一批 8 个模型只换 harness，OSWorld-v2 平均部分分 **45.3→64.9（+19.6）**、步数 **−53%**；README 另给"代码执行 vs 同等 GUI+CLI 权限 = **+6.1 分 / −14.8%**"——**README 正文只有这两组数**，"+15.5~+33.6"那组区间不在 README 里，要用必须回查 arXiv 2610.22200 的消融表【官方·仓库 README，底稿 08 L35】），而**你的机器上唯一今天就能跑、且原生 Windows、且用 UIA 绕开 150% DPI 难题的完整 harness 就是 UFO²**（UFO²+GPT-4o 在 WAA 上 27.9%、UFO²+o1 30.5%，Navi 基线 19.5%、人类基线 74.5%——**WAA 无官方榜，不可横比**【底稿 03 L131/L256】）。所以正确姿势不是"从零重写"（那是 czdcode 失败的原因），也不是"直接用别人的成品"（那些都卡在单显示器/闭源/海外 API），而是**拼装 + 只补两个缺口**。

## 2. 三个可选方案（你来选）

### 方案 ①：直接用 UI-TARS-desktop / Agent TARS
- **组成**：字节 Apache-2.0 全栈（Electron 客户端 + `@agent-tars/cli` + MCP server），挂豆包或百炼模型。
- **你要写什么**：几乎不用写，但要适配它的单显示器假设与它的 0~1000 坐标换算。
- **成本**：¥32.37~64.58/月（百炼 gui-plus，6000 步/月）【底稿 05 L188/L191】。
- **优点**：开箱即用、动作层是 nut.js 的 SendInput 级注入、v0.3.1（2026-10-08）刚发（⚠️ **版本号与日期未核**：8 份底稿没有 UI-TARS-desktop 的发版记录；底稿 03 L296 记的是 WAA 的媒体自报条目）。
- **代价**：官方明确**只支持单显示器**；150% DPI 下截图与点击坐标不一致它不替你解决；UI-TARS-2 至今无权重（你拿到的只是上一代 1.5-7B 或 v1 全家族）。
  > ⚠️ "只支持单显示器 / 四个 provider 全是云端 / 远程 Operator 已废弃 / 文档维护不佳"是**单一博客来源**（Gigazine 2026-06-28），属【媒体·需交叉验证】，不是一手证据【底稿 03 L558/L667】；star 数是**约数**（底稿见到的区间 28.9k~39k）。
  > 📌 UI-TARS-2 在 OSWorld 官方榜上有一条独立条目 **53.10**（`UI-TARS-2-2509` / 100 步 / 2025-10-14 / 第 43 名），**官方榜复现值高于论文自报的 47.5**——但**权重仍然没有**【底稿 03 L222、底稿 08 L120】。
- **什么时候选它**：你只想快点看到东西动起来，暂不打算自建。
- **什么时候别选**：你要长期演进、要接 UIA 结构层、要跨应用可靠性——这些它都不提供。

### 方案 ②（**推荐**）：拼装 + 自建两个缺口
- **组成**：
  - **骨架**：`microsoft/UFO`（MIT，Windows 原生，UIA + Win32/WinCOM/MCP 混合动作，官方文档直接给 `API_TYPE: "qwen"` 直连百炼（⚠️ **该配置项名在 8 份底稿中查无出处 → 标【未核】**；可核的是"UFO² 全开源、MIT、纯 Windows 出身、UIA+Win32 双后端"【底稿 03 L131/L136】））
  - **UIA 通道**：`Windows-MCP`（MIT）或 `sbroenne/mcp-windows`（controls-first）；或微软自家 `winapp CLI`（MIT，public preview，UIA pattern 不注入输入）
    > 📌 **"控件优先 8/8 vs 纯截图 7/8、中位少 34.9% 输入 token"这组基准数字在 8 份底稿中查无出处，本版已删**。可核的替代说法是：**有 UIA / SoM 元素清单时，模型只输出元素 ID、坐标由基础设施给出，模型不再需要像素精度**——这是 OSWorld 的实证（"a11y 树在当前模型能力下起决定性作用"，arXiv 2404.07972，2024-04-10）【底稿 02 L509】；以及单方自测的一组对照——**a11y 引用式 13/13 任务完成、0 误点；截图坐标式 7/13 完成、27 次误点**（⚠️ **单方自测，未经第三方复现**）【底稿 03 L332】。
  - **浏览器那一半**：`microsoft/playwright-mcp`（9.10，全表第一）
  - **大脑**：百炼 `gui-plus`（¥1.5/¥4.5，100 万 token/90 天免费）或 `qwen3.8-max`；**MiniMax M3.1 Flash** 若你有可编程 API 通道
  - **自建缺口 1**：**两级 grounding 的 crop 精定位回路**（`01` §1.3.1）——**全行业只有 Anthropic 把 zoom 做进了官方协议**（OpenAI / Gemini / GLM / UI-TARS / Qwen-CUA 的动作清单里都没有）【底稿 08 L121】。
    - ✅ **不用从零写**：官方评测仓库 `ScreenSpot-Pro-GUI-Grounding` 自带 **5 个可运行的 coarse-to-fine 实现**，`models/methods/ground.py` 的形状与本方案完全一致（整屏 → 粗 bbox 中心裁 1024² → crop 内第 2 遍 → 映射回全图），把 1024 改成 512 即可；**评测脚本也现成**，能和这 5 个基线在同一套 eval 上跑表。
    - ⚠️ **缺口确实存在**：`UFO²/UFO³` 全仓无 crop/zoom（16 处命中全是把 UIA 元素框裁出来做 CLIP 匹配），精度完全靠 UIA 控件框 + LLM 选对编号；`UI-TARS-desktop` 也没有。**用 UFO 当骨架，这层必须自建。**
    - ✅ **好消息**：UFO 的坐标系是 **UIA 物理像素**，正好是我们 zoom region 的目标坐标系，**不需要额外缩放换算**。
    - ⚠️ **坐标系契约必须自己定**：Anthropic 的契约是"模型在放大图里仍报**整屏坐标**"（zoom 图从不是坐标系）；**Qwen3-VL / M3.1 Flash 没被训过这套**，必须走"**crop 内坐标 + 原点偏移**"（`proto/coord/crop_refine.py` 已实现并测过）。**两套混用必错。**
  - **自建缺口 2**：**校验/反思层**（expect 断言、无变化检测、循环熔断、三段耗时埋点）
- **成本**：¥32.37~64.58/月（只 UIA 命中时几乎为 0，因为 UIA 通道不调模型）【底稿 05 L188/L191】
- **优点**：坐标漂移源头只剩 crop 内（±0.26 px，512 宽 crop 时的量化误差）【底稿 02 L598；`01` §1.1 E1】；DPI 问题在 L0 一次性消灭；UIA 红利只有 Windows 有；**每件东西都可替换**（换模型、换 UIA 实现都不推倒重来）
- **代价**：工程量最大，要自己把几个项目的接口缝起来
- **什么时候选它**：你要做的是**产品**而不是 demo，要长期演进
- **什么时候别选**：你只想验证"这套到底行不行"——那就先跑 M0

### 方案 ③：MCP 化起步，最快见效果
- **组成**：`open-computer-use`（MIT，2.5k star）或 `Windows-MCP` + `playwright-mcp`，暴露成 MCP server，DSH / Claude Code 直接调。
- **你要写什么**：模型接入 + 一层业务封装。
- **成本**：几乎零。
- **优点**：两周内能看到 agent 真的点鼠标；**"CLI 优先、视觉兜底"的分层天然就在**。
- **代价**：动作集被裁剪（无按住键/修饰键点击）；纯像素通道的坐标漂移仍在；成熟度未经长期验证。
- **什么时候选它**：你要先确认"这事儿到底做不做得成"，或你就是要一个能用的工具而不是一个平台。
- **什么时候别选**：你需要可靠性、审计、审批、可回放——这些都得自己加。
- **来源与口径**：
  > · `open-computer-use`（MIT，2.5k star）与 `Windows-MCP` 的**版本、star、安装方式在本 8 份底稿中查无出处 → 标【未核】**（底稿 03 L410 记的是另一个项目 `open-codex-computer-use`，**不可混用**）；⚠️ **底稿 03 L453 的原文是「`windows-mcp` 就有这个 bug」**——它出现在 DPI 坑清单里，说的是 **Windows-MCP 自身存在「物理坐标与逻辑分辨率混用」的缺陷**（150% 下整体错位），**不是**「它比纯坐标稳」。→ **Windows-MCP 不能无条件当本机首选 UIA 通道，接入前必须先按 `01` §1.5 自查坐标空间**【底稿 03 L453】。
  > · "**CLI 优先、视觉兜底**的分层"有可核出处：底稿 03 L412 明确"在 Windows 上落地版本就是：**UIA 树 + PowerShell/CLI + 应用 API 优先，截图/坐标点击作为最后兜底**"；旧项目同源结论见底稿 01 L517–L521（UIA ~10 ms / DOM-CDP ~10–30 ms / 视觉 1.5–5 s，视觉"仅 coverage failure 时"启用）。
  > · ⚠️ **本方案同样受 `01` §2.6 的 C-01 / C-02 / C-03 / C-05 / C-11 约束**——它只是"少写代码"，不是"免掉 DPI 感知与标定"。
  > · ⚠️ **"两周内能看到 agent 真的点鼠标"是主观估计，不是实测排期**；M0 原型已就绪（`proto/exec/selftest.py` 本机 5 PASS / 0 FAIL【本机实测(2026-10-19)】），起步成本比文档印象低，但"两周"本身无出处。

## 3. 我的推荐：方案 ②，五条理由

1. **"从零重写"就是 czdcode 失败的原因。** 旧项目 **27,919 行 / 231 个文件 / 69 个测试文件**【底稿 01 L58，引 `CZD_CODE_PORTFOLIO_HANDOFF.md:14-16`，2026-08-17 审计时刻】；其交接文档把 "Benchmark results / Latency numbers" 列为"无真实数据"【底稿 01 L541，引 `:651-652`】，且**影子模式只有接口没有落盘观察者**（`DecisionObserver` 无任何实现类）【底稿 01 L286–L288】。**这次只自建两个缺口（crop 精定位 + 校验层），其余全部复用成熟实现。**
   > **来源与口径**：三处事实（规模、"无真实数据"自述、影子模式空实现）均为【底稿 01】逐行核到的**旧项目一手材料**，等级=**一手代码/交接文档转述**。⚠️ **"规模大 ⇒ 会失败"是本方案的推断，不是底稿结论**——底稿只说"有实测数据支撑的只有 Vision 那条线"【底稿 01 L541】。**对应验收项：C-15**（旧项目把 UIA 树原文直接塞进上下文，本项目必须先过脱敏，见 `01` §2.6）。
2. **UFO² 是本机唯一"今天就能跑"且原生 Windows 的完整 harness**，它的设计范式（UIA 树 + 原生 API + MCP 混合动作 + Speculative Executor 一次预测多动作并用实时 UIA 校验）**和 `01` 的架构结论完全同构**——说明这条路是被验证过的，不是臆想。**背书**：UFO²+GPT-4o 在 WindowsAgentArena 上 **27.9%**、UFO²+o1 **30.5%**（对比 Navi 基线 19.5%、人类基线 74.5%）【论文自报；WAA **无官方榜**，不可横比】【底稿 03 L131/L256/L271】。
   > **来源与口径**：可核的是 **UIA + Win32 双后端（可配）+ 原生 API + MCP 的混合动作空间**、MIT 全开源、论文 arXiv 2504.14603【底稿 03 L131/L136】；WAA 三个数（27.9 / 30.5 / 74.5 / 19.5）均为**论文自报**且 **WAA 没有官方在线榜**、口径混乱不可横比【底稿 03 L256/L258–L271】。⚠️ **"Speculative Executor 一次预测多动作并用实时 UIA 校验"在 8 份底稿中查无出处 → 标【未核】**。⚠️ **"本机唯一今天就能跑"是本机可达性判断**（UFO² 官方文档给 `API_TYPE` 直连百炼，而百炼本机 200 OK【底稿 05 L292】），**不是官方声明**。**对应验收项：C-08 / C-09**（UIA 能力表与查询超时，UFO² 接入前先做逐 app 探测）。
3. **UIA 红利是 Windows 独有的，且 OSWorld 官方榜 111 条去重记录里只有 2 条用了 a11y 树**（其余 109 条为 No）【官方·榜单 osworld.github.io，2026-10-19 直拉，底稿 03 L231】。⚠️ **但 OSWorld 是 Linux 榜**，AT-SPI 覆盖度与 Windows UIA 不可比，**这 2 条恰恰说明"a11y 在 Linux 榜上不加分"，不能反推 UIA 在 Windows 上没用**【底稿 08 L34】。这个优势只有你能吃到，用纯视觉方案等于主动放弃。
4. **可替换性 > 一次性到位。** 大脑（M3.1 / 百炼 / 魔搭）、UIA 通道（Windows-MCP / winapp CLI / 自写 COM）、浏览器（playwright-mcp）都能单独换；而"自己写 harness + 自己做 grounding"这套如果写死模型协议，换模型就是重写。

## 5. 选型时最容易踩的三个坑

1. **把"评分高"读成"适合这台机器"。** 榜单前列里 Anthropic/OpenAI/Google 全部本机不可达（**本机实测(2026-10-19)**：`platform.claude.com` 返回 "App unavailable in region"（地域封禁）、`openai.com/api/pricing` **403**、`ai.google.dev` **连接超时**）【底稿 05 L13/L295–L297】——**只有这三个主机名是底稿 05 直连实测表里真测过的**，任何其他端点（如 `api.anthropic.com`）都不算本机实测——**这不是"慢"是"接不上"**。
2. **把"grounding 准确率高"读成"能完成任务"。** ScreenSpot-Pro 官方榜第一 **82.7%**（`Indeed-UI-32B-zoomin`），但**研究基线低得多**：UI-TARS-1.5-7B **42.19**、OS-Atlas-7B **18.9**、GPT-4o **~0.8**；**难度的量化是目标框平均只占图 0.07%（ScreenSpot 是 2.01%，约 30× 难）**【官方·榜单，底稿 03 L278】。而 2026 第三方结论更狠：**所有被测模型在 SoM 下的 OSWorld-G 均 <30**，E2E 原生 grounding 明确优于 SoM【底稿 03 L361】。同时"高分"本身也会衰减：ScreenSpot-Pro 分数从 ScreenSpot-v2 的 ~90% 掉到 **40–60%** 量化了这种精度衰减【底稿 03 L317】。**→ 这正是为什么必须有 crop 精定位 + 校验层，而不是只挑一个 grounding 分数高的模型。**
   > ⚠️ 原文这组里的"icon 73.84% / text 92.12% / Windows 公共控件 icon 65.96%"与"OSWorld-Human 论文 23% 的失败是规划正确但 grounding 给错坐标、66% 步数浪费在 grounding 循环"**在 8 份底稿中均查无出处**，已删。可核的替代说法是**"不信任模型自称的成功"**（Qwen-CUA README 原文：*"a model's `terminate(success)` action is not proof of real-world success"*）【底稿 03 L440】，以及 OSWorld 2.0 的任务长度崩塌曲线（<45 分钟任务 20–24% binary；>163 分钟所有模型 binary 归零）【底稿 03 L246】。
3. **把"结构化优先"误解成"不用视觉"。** 学术界不存在"只用 UIA 不用像素"的 agent：**OpenAdapt 实测结构层 21/21 vs 纯图像匹配 6/21**（⚠️ **未核**：OpenAdapt 在 8 份底稿中查无出处；原文把它标成"底稿 03 第 405 行（OpenAdapt 五级定位阶梯）"，**指错了**——第 405 行实际是"其他相关工作"清单，**该引用已删除**）；**CLI-Anything 论文"状态不透明、无 headless 后端时必须回落像素"同样未核**（8 份底稿无该论文条目）。**还有一条被忽略的失败模式——过期结构会劫持 agent**：arXiv 2607.04334（2026-07）用 735 个探针测出，四家厂商模型"**像素读对了却听结构的**"比例 >0；**在未编辑的 stale snapshot 上跟随过期结构最高 0.88**，多步任务里**首步一次错信念即导致失败、自恢复率 ≤ 0.03**。→ **"结构化优先"的代价是必须每次重读树**（这也是 `01` §2 L1 与 §3 写死"执行前必须重读控件树"的原因）【专题·dom-vs-pixel L46】。
> **正确形态是：结构化做候选生成与语义，像素做最终确认与兜底**——这一点在底稿里有可核的支撑："在 Windows 上落地版本就是：UIA 树 + PowerShell/CLI + 应用 API 优先，截图/坐标点击作为最后兜底"【底稿 03 L412】

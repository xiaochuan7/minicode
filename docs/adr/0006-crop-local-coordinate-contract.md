# 坐标系契约选「crop 内坐标 + 原点偏移」，而不是 Anthropic 的「整屏坐标」

crop 精定位的坐标契约定为：模型在裁剪窗口里报 **crop 内坐标**，由 harness 加裁剪原点偏移映射回全屏。理由：Anthropic 的契约要求模型在放大图里**仍报整屏坐标**（放大图本身从不是坐标系），那套契约的前提是模型被训练过；本项目所用的 Qwen3-VL / M3.1 Flash 没有被训练过，实测也确认模型用的是 0~1000 归一化坐标。两套混用会让落点偏一整个裁剪窗口，而且是静默偏移。

## Considered Options

- **Anthropic 契约（放大后仍报整屏坐标）**：若将来改用 Claude/Anthropic 作为定位模型，契约需要整体翻转，届时才切换。

## Consequences

- 裁剪窗口与坐标基准的换算责任落在 harness 一侧，且换算链路必须只有一个真值来源。
- 放大（动作）与裁剪（定位环节）是两件事，坐标契约不同，不可混称。
- **补充（2026-10-20，工单 M7）**：工单 M7 落地了 C-16 的**门控**（命中才开第二遍精定位），
  于是「最终落点只在 crop 尺度上产生」多了一条**例外路径**：**门控未命中**时，
  系统直接拿**整屏粗定位点**落点（省一次模型调用）。这条例外只在这一条路径上成立，
  且它**不改变本契约的换算链**（粗定位点与 crop 内坐标一样是物理表面空间里的点）。
- **补充（2026-10-22，人已拍板）**：**粗定位允许同时出框出点，落点取框中心**。
  - 理由：官方通用 API 协议**问的是框**（`models/gpt4x.py`：输出 `[[x0,y0,x1,y1]]`，
    `click_point = [(bbox[0]+bbox[2])/2, (bbox[1]+bbox[3])/2]`；ScreenSpot-Pro 论文 Table 3 题注：
    "For models inferencing boxes, we consider the center point of the generated box as the prediction"）——
    **我们原来问点是自创的**。问框还能顺带解锁门控的 `target_area_ratio`（此前 42/42 不可判定）。
  - **框可以退化成点**（模型只给点时，框退化为该点，中心即该点）。
  - ⚠️ **本契约不变**：框 → 点的换算只在**一处**做（`ground/channel.py`），
    坐标仍然全程**物理表面空间**；「crop 内坐标 + 原点偏移」这条不变。
- **补充（2026-10-22，门控降级）**：门控降级为**记录器**之后，「门控未命中时直接取整屏粗定位点」
  这条例外路径**不再作为默认**——crop 精定位**默认无条件执行**，落点默认产生在 crop 尺度上；
  例外只剩「精定位失败 → 回落」这条（回落原因与回落率照旧落盘）。
  「兜底要罕见」仍然成立，但它的落点是**通道切换**（`docs/spec.md` §11 第 1 条）与**危险动作审批**。
- **补充（2026-10-26，发布整理）**：后续运行期标定在 8 次真实会话（K=21）里判出的量纲是
  `absolute_model_input`（模型报**它看到的那张图**的像素），而不是 0~1000 归一化。
  因此模型端量纲**不写死**，唯一权威是运行时标定（见 `ARCHITECTURE.md` §3.2）。
  本决策（crop 内坐标 + 原点偏移）不受影响。
